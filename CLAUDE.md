# CLAUDE.md — Pinhead Order Studio

## Проект

Pinhead — внутренняя ERP/CRM-система для типографии (печать на одежде).
Пользователи: менеджеры, дизайнеры, производство, директор.
Цель: оформление заказов через визард, управление на Kanban-доске, аналитика, интеграция с Bitrix24 и 1С.

## Логика продукта (решение заказчика, 2026-07-17)

Два раздела с переключением в шапке (единая админка):
1. **✏️ ТЗ (Order Studio)** — создание технического задания к заказу.
   Формат ТЗ: docs/erp/tz-format-analysis.md. Генерация ТЗ-PDF — здесь (позже).
2. **🏭 Производство (ERP)** — заказ попадает сюда ПОСЛЕ создания ТЗ
   и движется по цехам до сдачи.

Поток: **ТЗ → Производство**. Текущий приоритет — производство (ERP):
поля ТЗ (размерная сетка, нанесения, упаковка/бирки) живут в производственном
заказе, цеха видят полное ТЗ в карточке. Этап-мост «ТЗ → авто-создание
производственного заказа» и генерация PDF — следующая очередь.

## Правила кода

- `useShallow` для объектных селекторов Zustand — обязательно
- `toast.error` при каждой Supabase ошибке
- `return null` из async при ошибке (не fallback объект)
- Optimistic update только с rollback
- НЕ optimistic delete — ждать ответ Supabase
- CSS токены из `:root` (--type-*, --space-*, --z-*)
- Autofocus на первом поле формы
- Не добавлять npm-зависимости без обсуждения
- Не `!important` в CSS
- Supabase ключи строго из `.env` (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)
- RLS: политика пишется НА КОМАНДУ (`for select/insert/update/delete`), а не `for all`
  рядом с отдельной `select` — иначе Postgres проверяет обе на каждый SELECT
  (advisor `multiple_permissive_policies`). `auth.uid()`/`auth.role()` в предикате
  оборачивать в `(select …)` — иначе вызов идёт на каждую строку (`auth_rls_initplan`)
- `is_admin()`, `erp_is_manager()`, `erp_is_member()` вызываемы через REST, и advisor
  на это ругается — **так и оставляем**: выражения RLS исполняются от лица вызывающего,
  и отзыв `EXECUTE` сломает сами политики. Утечки нет: функции без аргументов и
  возвращают булево о самом вызывающем. Не «чинить»
- При logout вызывать `storageClearAll()` — чистит все app-ключи
- Удаление пользователя: soft-delete (active=false), не hard delete
- Auth: ProfileStatus state machine (active/pending_approval/disabled/no_profile)
- Dev-mode created_by: фильтровать 'dev' → null (и в saveOrder, и в duplicateOrder)
- deleteSkuPhotoByUrl: проверять результат, показывать toast.error при ошибке
- ERP: доступ только через `useErpAccess` (право из матрицы + принадлежность цеху),
  кнопки этапа — через `useStagePermissions` (у каждого действия своё право);
  приоритет очереди — `reorderStageQueue`, перенос между цехами — `moveStageToDepartment`
  с подтверждением последствий; прогресс считается в штуках (`erp/utils/progress`)
- ERP: финальный ОТК (`qc`) — последний этап производственного маршрута, зависит от
  ВСЕХ терминальных этапов (нанесение на готовом = параллельные ветки); маршрут без
  производственных этапов ОТК не получает. Галочка «Финальный ОТК» живёт только
  в форме — этапы материализуются при создании заказа
- ERP: боковая карточка заказа ведётся в адресе (`?order=`) — открытие пушит запись
  истории, закрытие снимает её же, «Назад» и ✕ совпадают
- ERP, необратимое действие этапа: последствия считает чистая утилита с тестами и
  формулирует их текстом — `utils/stageDone` (закрытие с недосдачей),
  `utils/stageDefect` (возврат брака через промежуточные этапы). Записывать факт
  «по умолчанию весь тираж» / молча откатывать маршрут нельзя
- Справочники ERP (`erp_dictionaries`) — подсказка, а не ограничение; значения отключаются,
  а не удаляются. Статусы в справочник не выносятся — они часть маршрутной логики
- Материальный гейт — из данных: `erp_departments.gate_material_kinds` (какие виды
  материала блокируют запуск участка), правится в админке. Пусто = не гейтится
  (fail-open). Константы вида «ткань → закрой» в коде не держать
- Группы очереди: `awaiting_materials` (нет материалов) отделена от `waiting`
  (ждёт предыдущий этап, ТЗ или закупку) — это разные решения руководителя.
  На канбане у обеих и у `blocked` свои дорожки, «Ожидают материалы» — перед «Готово»
- Производственный план (`/plan`) — РУЧНОЙ инструмент: система план не составляет
  и остаток сама не переносит, она показывает отклонение, а новую дату ставит
  человек. Раскладка живёт в `erp_calendar_slots`; «убрать из плана» —
  `status='cancelled'`, не DELETE (факт и переписка остаются, повтор идёт upsert-ом)
- План ставит роль `production_head` (право `plan.manage`), факт вносит цех
  (`plan.fact` + принадлежность цеху). Диспетчеру `plan.manage` НЕ даётся —
  иначе снятая у одного галочка отключает работу другого
- Мощности цехов (`capacity_per_day`) не возвращать: удалены осознанно миграцией
  20260716170000, загрузка выражается в штуках
- Матрица прав действует и НА СЕРВЕРЕ: `erp_has_permission(право)` +
  `erp_role_of_caller()` — дословное зеркало `resolveErpRole` из
  `utils/permissions.ts`. Расхождение двух реализаций даёт худший отказ («кнопка
  есть, сервер отвечает 42501»), поэтому его сторожит тест `serverPermissions.test.ts`,
  читающий саму миграцию. Отсутствие права в матрице на сервере = запрет
  (на клиенте там работает `DEFAULT_PERMISSIONS`, но это защита от неудачной загрузки)
- Одна UPDATE-операция под разными правами разделяется ТРИГГЕРОМ по изменившимся
  колонкам (`erp_calendar_guard` для плана, `erp_stage_guard` для этапов,
  `erp_order_guard`/`erp_order_item_guard` для заказа и позиции), а не
  политикой: RLS работает на уровне строки. Пустой `auth.uid()` в таком страже —
  это service_role, его пропускаем: он и так минует RLS, и запирать починку
  через SQL нельзя
- **Страж и клиентский гейт ставятся ОДНИМ коммитом.** `erp_orders` UPDATE стоял
  на `erp_is_member()` без разбора колонок — рабочий цеха мог через REST сменить
  срок и менеджера любого заказа. Но и клиент инлайн-правки не гейтил: страж
  в одиночку дал бы запрещённое «кнопка есть, действие падает». Прежде чем
  закрывать дыру на сервере — проверьте, закрыта ли она в интерфейсе
- `revoke execute … from anon` сам по себе НЕ РАБОТАЕТ: право приходит от PUBLIC
  (`=X/postgres` в ACL), а `anon` его наследует. Отзывать нужно
  `from public, anon` и следом явно `grant … to authenticated` — иначе отберёте
  доступ у самих политик. После отзыва проверьте `set local role authenticated`
- Страж разрешает ровно то, что разрешает интерфейс. Строже клиента — «кнопка есть,
  а действие падает», и виноватым выглядит цех; мягче — дыра. Поэтому переход
  в `done` принимает `stage.progress` (факт добрал тираж и закрыл этап сам) и
  `stage.move_department` (перенос закрывает исходный этап), а не только `complete`
- Плановые даты этапа (`planned_*`) стражем НЕ охраняются: колонка «План» в карточке
  заказа правами не гейтится вовсе, и проверка на сервере отобрала бы у менеджера
  то, что он делает сегодня. Гейт нужен, но вместе с гейтом в интерфейсе
- ТЗ в PDF принадлежит ПОЗИЦИИ и автоматически видно всем цехам её маршрута
  (`itemTzDocument`: своё ТЗ позиции → общее ТЗ заказа). Назначать документ каждому
  цеху не нужно — этот шаг отменён 2026-08-03. Гейт (`utils/tz`) требует ТЗ только
  у производственных цехов и только при `tz_required === true` (fail-open: остановка
  цеха не должна случаться из-за отсутствующего поля). Заказ с ТЗ создаётся одной
  транзакцией: файлы в бакет → `erp_create_order` с секцией `tz`
- Ключ объекта в Storage — строго ASCII (`tzFilePath` транслитерирует кириллицу).
  Supabase проверяет ключ регуляркой S3-safe символов, где `\w` без флага `u`, и на
  русское имя файла отвечает `InvalidKey`. На этом ломалось создание ЛЮБОГО заказа
  с ТЗ; человекочитаемое имя живёт в `erp_tz_documents.file_name`
- Файл, который человек видит приложенным, обязан быть в бакете: загрузка идёт при
  выборе файла, у каждого своё состояние (загружается/загружено/ошибка), и submit
  заблокирован, пока есть незавершённые. Грузить в сабмите нельзя — интерфейс
  показывал приложенным то, чего в Storage нет

## Правила проверки прав на живой базе (21.08, после разбора)

Готовый каркас — `docs/erp/permission-check.sql`: берите файл целиком и меняйте
только блок «что проверяем». Правило, которое надо помнить, забывается; шаблон —
нет. Ниже — почему он устроен именно так.

- **Проверка прав без `set local role authenticated` не проверяет НИЧЕГО.**
  `set_config('request.jwt.claims', …)` подменяет только личность
  (`auth.uid()`), а RLS не применяется к владельцу таблицы вовсе — блок
  исполняется от `postgres`, и любое действие «проходит». Такая проверка
  ОПАСНЕЕ отсутствующей: она выдаёт зелёный результат на непроверенном месте.
  Порядок один: `set_config(claims)` → `set local role authenticated` →
  действие → `reset role`
- **Роль для проверки заводится, а не подбирается.** В `erp_employees` живут
  три человека (директор и два менеджера), и «проверить от лица кладовщика»
  на боевых данных нечем. `profiles` не связан с `auth.users` внешним ключом,
  поэтому временный сотрудник заводится прямо в транзакции с откатом —
  профиль плюс строка `erp_employees` с нужной ролью
- **Выборка из `erp_role_permissions` без `allowed` читается наоборот.**
  Таблица хранит строку на КАЖДУЮ пару «роль × право», в том числе со
  значением `false`: запрос без фильтра показывает у рабочего все шестнадцать
  прав. Один раз это уже заставило меня решить, что у `worker` есть
  `order.manage`
- **Право проверяется ПО ВСЕЙ ЦЕПОЧКЕ, а не в одной точке.** RLS журнала
  подряда расширили до `warehouse.manage`, и приёмка всё равно падала: строку
  журнала кладовщик вставлял, а триггер `erp_subcontract_moves_rollup` менял
  `qty_done` подрядного этапа, и `erp_stage_guard` отклонял транзакцию —
  у `storekeeper` нет НИ ОДНОГО права `stage.*`. Пропуск сделан меткой
  транзакции `erp.subcontract_rollup` (как `erp.moving` у переноса цеха):
  метку ставит и снимает сам rollup ВОКРУГ своего update, страж принимает её
  только для подрядного этапа и только у того, кто вправе писать журнал

## Правила ERP (документ 20.08, сессия 33 — сверка)

- **Половина требования выглядит как сделанное требование.** Построчная сверка
  документа с кодом нашла четыре пункта одного класса: поле пишется в базу,
  но нигде не читается (ответственный подряда, план передачи, комментарий);
  схема заведена, а точки ввода нет (`ТЗ / файлы` этапа); величина считается
  на доске, но не в карточке (статус материалов ЭКС). Тесты этого не ловят,
  когда проверяют НАЛИЧИЕ ИМЁН полей в тексте функции, а не путь от ввода
  до показа. Сторож обязан проверять механизм: «файл, выбранный в форме,
  оказался привязан к тому этапу»
- **Файл, привязанный к строке, которой ещё нет, адресуется ИНДЕКСОМ.**
  У листа закупки это `material_index`, у подрядного этапа — `stage_index`
  (номер этапа ВНУТРИ позиции; ключ составной, потому что `v_stage_ids`
  обнуляется на каждой позиции). Номер проставляет ТОТ ЖЕ код, который строит
  секцию `stages`, — иначе рядом заводится второй порядок этапов
- **`pg_get_functiondef` отдаёт ЗАГЛАВНЫЙ заголовок и `$function$`.**
  Скопированный дословно, он молча уводит сторожевые тесты на предыдущую
  миграцию (`latestDefining` ищет `create or replace function public.<имя>(`,
  `functionBody` разбирает тело между `$$`): сторож зелен и проверяет не ту
  функцию, которая работает. Приводить к виду миграций проекта обязательно
- **`erp_order_attachments.stage_id`** + вид `subcontract` — файлы подрядного
  этапа. Не `tech` у позиции (адресат другой, и подрядных этапов бывает
  несколько) и не `erp_tz_documents` (по ним считается гейт ТЗ, и файл
  подрядчику открыл бы цехам работу без техзадания)
- **«Подряд» больше не тип производства.** Плитка `outsource` убрана из формы
  создания: две точки ввода одного решения означают, что маршрут считается
  по частному правилу `material_source`, а не по исполнителю шага. Значение
  остаётся в схеме и подписях — его несут заведённые раньше заказы

- **Селект хранимого статуса рядом с величиной, которую ведёт журнал, — это

- **Состояние, выводимое из маршрута, не хранится.** «Запланировано»
  и «Готово к передаче — N шт» считает `utils/subcontractFlow` тем же
  `stageInputQty`, что и «принято в работу» у обычного цеха. Хранимая фаза
  двигается с ПЕРЕДАЧИ — до неё хранить нечего
- **Триггер, у которого есть легаси-ветка, проверяйте на ОСНОВНОМ сценарии.**

  рабочим: строки были, статусы менялись, а склад заказ не видел
- **Уникальность, разведённая на частичные индексы, отменяет `on conflict`
  ВЕЗДЕ** — и в триггерах, и в клиенте. Частичный индекс из голого
  `ON CONFLICT (col, col)` не выводится: 42P10 на каждом срабатывании.
  Порядок правки один: сначала снять `onConflict`, потом делать индекс частичным
- **Лист закупки задаёт МЕНЕДЖЕР ФАЙЛОМ, строки заводит ЗАКУПЩИК.** Файл

  edge-функция при пересборке УДАЛЯЕТ строку вложения со своим путём — файл
  менеджера снесло бы первой же пересборкой
- **«Закупка не требуется» — колонка `erp_orders.purchase_required`, а не
  пустой список материалов.** «Закупать нечего» и «до закупки ещё не дошли» —
  разные состояния, и второе не должно молча закрывать заказу путь. Отметка
  вырезает этап `supply` из маршрута (`needsPurchase` в `buildItemRoute`),
  и это же закрывает требование «убрать автоматическую связь Подряд → Закупка»
- **ПРИНИМАТЬ — НЕ ЗНАЧИТ ЗАПИСАТЬ.** `erp_route_apply` перечисляла все девять
  полей подрядного этапа, сторож был зелёным, а доезжали они только со ВТОРОГО
  сохранения: шаг payload функция искала по `stage_id`, которого у только что
  созданного этапа нет вовсе (клиент шлёт `null`). Связывать шаг с этапом надо
  ПО ПОЗИЦИИ в массиве (`v_ids[e.ord]`) — тем же приёмом, каким в этой же
  функции разрешаются `depends_on`. Сторож проверяет СПОСОБ связывания,

- **Этап разработки ВЫЧИСЛЯЕТСЯ, а не хранится** (`utils/experimentalBoard`).

- **Пустой шаг, ПОСЛЕ которого уже есть работа, считается пропущенным.**
  Наивное «колонка — первый шаг с незакрытой задачей» ломается дважды:

- **Нанесения ЭКС — ОТБОР этапов по `origin`, а не свой механизм.** Задача

## Правила ERP (подряд как этап маршрута, сессия 32)

- **Подряд — признак ЭТАПА (`erp_item_stages.executor`), а не тип производства.**
  `department_id` остаётся обязательным и означает ЧЕЙ ЭТО УЧАСТОК
  ОТВЕТСТВЕННОСТИ — какой наш цех делал бы работу и куда она вернётся.
  Псевдо-цех «Подряд» заводить нельзя: он потечёт во все поверхности, читающие
  цеха из данных, а уникальность `(item_id, department_id, cycle)` разрешит
  ровно один подрядный этап на позицию — при том, что документ требует несколько
- **Сравнение только с `'contractor'`, никогда с `!== 'internal'`.** Колонка
  новая, и у этапов из старых фикстур, урезанных выборок и кэша её нет вовсе:
  второй вариант отправил бы в подряд ВСЁ производство разом. Правило живёт
  в `utils/outsourcing.ts` (модуль-лист, как `utils/supply.ts`), и отсев есть
  в трёх потребителях — сторожит `contractorStageNotInQueue.test.ts`
- **Колонка, добавленная в `erp_item_stages`, попадает в `ORDER_LIST_SELECT`
  тем же коммитом.** Иначе `executor` приезжает `undefined`, отсев подряда молча
  перестаёт работать, и подрядные задания снова оказываются в очереди цеха —
  без единой ошибки
- **Конструктор маршрута работает над ГРУППАМИ, а не над этапами.** Документ
  описывает маршрут линейно, модель — граф с параллельными ветками нанесения;
  группа (шаг маршрута, внутри которого один или несколько этапов) — это и есть
  то, что `buildRoute` уже делает одинаковым `sortOrder`. `depends_on`
  пересчитывается механически: каждый шаг зависит от ВСЕХ этапов предыдущего
- **Инвариант тождества обязателен**: `linearize(draftFromRoute(buildItemRoute(x)))`
  ≡ `buildItemRoute(x)`. Без него открытие конструктора без единой правки молча
  переписывает производственный план заказа. Прогоняется по всем сочетаниям
- **`sort_order` остаётся `int` и перенумеровывается ЦЕЛИКОМ.** Numeric-шкала
  (как `queue_position`) здесь не работает принципиально: у параллельных этапов
  порядок ОДИНАКОВЫЙ, и «середины между 30 и 30» не существует
- **Этап с фактом из маршрута не выбрасывается.** Замок считает `isStepLocked`
  по факту (`qty_done`, `qty_rework`, `started_at`, статус), а не по одному
  статусу: этап, взятый в работу и возвращённый в очередь, тоже стирать нельзя.
  Это условие ДОСЛОВНО повторяют RLS-политика удаления и `erp_route_apply` —
  три места обязаны совпадать значением
- **Спутник подряда удаляется ЯВНО.** `erp_subcontracting.stage_id` объявлен
  `on delete set null`, и каскад оставил бы строку подряда без этапа — ровно
  то состояние, из-за которого раздел жил собственной жизнью
- **Частичный индекс уникальности идёт ПОСЛЕ удаления `onConflict` из клиента.**
  `subcontractingSlice` делал `upsert(onConflict: 'item_id,department_id,cycle')`,
  а PostgREST шлёт голый `ON CONFLICT` и частичный индекс по нему не выведет —
  42P10 на каждом возврате подряда. Порядок соблюдён: upsert заменён явной
  проверкой существования, и только следом индекс стал частичным
  (`where coalesce(executor,'internal') = 'internal'`). Сторожит `upsertConflict.test.ts`
- **`stage_id` у подряда не писал НИКТО** (проверено на проде: 2 строки, обе
  `null`), поэтому ветка rollup `erp_subcontract_moves_rollup`, обновляющая этап,
  не срабатывала ни разу. Прежде чем чинить поведение — проверьте, заполняется
  ли колонка, на которой оно построено. Теперь спутника заводят ОБА писателя
  этапов — `erp_route_apply` и `erp_create_order`, тем же оператором, что и этап;
  третьего писателя связи заводить нельзя
- **Журнал перемещений — не история, а МЕХАНИЗМ.** `addSubcontractMove` жил
  с волны 3.5 без единой точки вызова, и это был не косметический долг: приёмка
  в журнале — единственное, что приращает `qty_done` подрядного этапа
  (`erp_subcontract_moves_rollup`) и закрывает его. Без формы «вернулось
  от подрядчика» не открывало следующий этап, потому что предыдущий не
  закрывался никогда. Форма — `screens/subcontracting/MoveJournal`
- **Строка раздела «Подряд» — ЭТАП, а не запись реестра.** `erp_subcontracting`
  это карточка подрядчика ПРИ этапе: подрядчик, сроки, оплата, материалы,
  журнал. Экран, читающий соседние данные вместо этапов, выглядит рабочим
  и прячет заказ целиком — ровно так 12.08 сломалась закупка
- **«Вернулось ≠ заказ готов» не требует НИКАКОЙ специальной логики.** Следующий
  этап уже в маршруте и зависит от подрядного через `depends_on`; колонка
  «Следующий этап» его ПОКАЗЫВАЕТ, а не вычисляет переход. Это и есть главный
  аргумент за выбранную модель — раздел перестаёт быть тупиком по построению
- **Подряд заводится ТОЛЬКО конструктором маршрута.** Форма «добавить операцию»
  удалена: иначе рядом с маршрутом снова заведётся вторая сущность — та самая,
  ради устранения которой всё и переделывалось
- **Разметка конструктора ОДНА на карточку заказа и форму создания**
  (`components/RouteFields`). Маршрут задаётся дважды, но это одно решение —
  какие этапы, в каком порядке, чьими руками; две реализации разошлись бы
  в первую же правку, причём молча: обе «работают», просто предлагают разное
- **Правило «правка человека или расчёт» — `formItemRoute`, и ЦЕЛИКОМ, включая
  сборку аргументов `buildItemRoute`.** Читателей трое: превью ТЗ в форме, сам
  конструктор и `createOrder`. Разойтись они могут не только правилом, но и тем,
  что подставлено в расчёт: `materialSource`, взятый без проверки типа
  производства, вырезает из маршрута закупку — заказ создаётся не по тому
  маршруту, по которому считался гейт ТЗ. Пустой массив читается как «не
  трогали»: маршрут без единого этапа сделал бы заказ невидимым для всех цехов
- **Конструктор в карточке монтируется ТОЛЬКО открытым.** Черновик посеян
  из `item.stages`; оставленный смонтированным, он после сохранения показывает
  прежний состав этапов поверх перечитанного заказа, и следующая правка уходит
  на сервер от устаревшего состояния
- **Перечисление, расширенное в одной таблице, проверьте во ВСЕХ.** `mixed`
  завели у `erp_subcontracting`, а выбирает источник менеджер В ФОРМЕ ЗАКАЗА —
  значение пишется прежде всего в `erp_order_items`, где CHECK остался на двух.
  Заказ со смешанными материалами не создавался ВООБЩЕ: 23514 на вставке
  позиции, ещё до единого этапа. В клиенте перечисление ОДНО на оба поля,
  поэтому ни типы, ни тесты маршрута расхождения не видели. Сторож сверяет
  оба CHECK по имени констрейнта, а не по слову в файле
- **Legacy снимается ПОСЛЕ того, как опустеет блок совместимости** на экране
  «Подряд». Строки старого реестра без `stage_id` живут по старым правилам,
  и их ветка возврата (`return_dept` → этап) сохранена: маршрута у них нет,
  и снятие оставило бы такой заказ стоять после возврата. Обратный порядок
  уже ронял весь раздел «Производство» дропом `erp_experimental_ops`

## Правила ERP (волны A–F, остаток документа 16.08)

- **Ключ объекта Storage — `utils/storageKey`, один на весь проект.** Правило
  не про ТЗ, а про Storage: Supabase проверяет ключ регуляркой S3-safe символов,
  где `\w` без флага `u`, и на кириллицу отвечает `InvalidKey`. `tzFilePath` —
  тонкая обёртка над общим `safeFileName`; копия транслита рядом означала бы
  повтор истории, на которой не создавался НИ ОДИН заказ с ТЗ
- **Файл уходит в бакет ПРИ ВЫБОРЕ, а не в сабмите** — у каждого своё состояние,
  submit заблокирован, пока есть незавершённые (`useAttachmentUploads`). Иначе
  форма показывает приложенным то, чего в Storage нет
- **Файл ЗАКАЗА к позиции не подмешивается.** У ТЗ приём «своё → общее» верен —
  общий документ описывает весь заказ; у вложений нет: превью упаковки одной
  позиции к другой отношения не имеет, и чужая схема узла хуже никакой
- **Файл строки закупки привязан к СТРОКЕ** (`erp_order_attachments.material_id`).
  Строк на момент выбора файла ещё нет — в payload едет `material_index`,
  и считается он по ключам строк В ТОМ ЖЕ ПОРЯДКЕ, в каком они уедут в секцию
  `materials`: пустые строки отбрасываются, и счёт по положению в состоянии
  формы сдвинул бы привязку у всех, кто ниже
- **Брак и потери подряда НЕ хранятся, а считаются** (`subcontractShortfall`):
  журнал уже держит приращения, и «не вернулось» = передано − вернулось,
  «брак» = вернулось − принято. Вторая пара счётчиков рядом с журналом — два
  писателя одной величины, на чём уже ловились с `qty_received`
- **PDF листа закупки хранится ВЛОЖЕНИЕМ вида `purchase`, а не в
  `erp_tz_documents`.** Гейт ТЗ считает документы той таблицы: лист закупки
  стал бы для него техническим заданием и открыл цехам работу без ТЗ
- **Кириллица в PDF требует ВСТРОЕННОГО шрифта.** Четырнадцать стандартных
  шрифтов кодируют текст в WinAnsi и кириллицы не знают вообще — документ
  выходит пустым или мусорным МОЛЧА. Проверять надо русский текст в готовом
  файле, а не «функция ответила 200»
- **Сбой производной не отменяет основное действие.** PDF собирается сам после
  создания заказа, и его неудача не показывается ошибкой: заказ создан, лист
  в нём есть, а файл пересобирается кнопкой. Красная полоса читалась бы как
  «заказ не создался»
- **Разбор ошибки `functions.invoke` — один на все серверные функции**
  (`invokeFunction` в `store/adminUsers.ts`). На любой не-2xx туда приходит
  один и тот же текст, а причина лежит в теле; копия разбора во второй функции
  снова сделала бы отказ прав неотличимым от обрыва сети
- **NOT NULL снимается только после проверки RLS.** У `erp_materials` политики
  не ссылались на `order_id` вовсе, поэтому предварительная закупка видна
  автору. Ссылайся они на заказ — строка исчезла бы у того, кто её завёл.
  Проверять это надо ДО миграции
- **Привязка предварительной закупки — UPDATE существующей строки**, и пустой
  ответ считается отказом: RLS запрещает через `USING`, то есть отдаёт «0 строк»,
  а не ошибку, и зелёное «привязал» было бы неправдой

## Правила заведения сотрудников (приглашения, сессия 31)

- **Основной путь — приглашение ссылкой** (`erp_invites`): админ выбирает роль
  и цех, получает готовую ссылку `/join?code=…` и отдаёт её человеку САМ.
  Писем в этом пути нет вовсе — а прежний порядок вставал именно на них
  (встроенный SMTP Supabase: ~2 письма в час, у gmail спам). Самостоятельная
  регистрация осталась ЗАПАСНЫМ путём: заявка, роль `pending` без прав,
  одобрение админом
- **Код проверяет и гасит ТОЛЬКО сервер** — `handle_new_user`. Клиент кладёт код
  в `options.data.invite_code`, то есть присылает его сам и может прислать что
  угодно. Гашение — ОДИН `update … returning` по сроку, отзыву и адресу: двое,
  открывшие одну ссылку одновременно, не могут оба получить права, а отдельные
  SELECT и UPDATE такого не гарантируют
- **Нечитаемый код не имеет права ронять регистрацию.** Триггер исполняется
  внутри вставки в `auth.users`; необработанное исключение даёт «Database error
  saving new user» ВСЕМ, включая тех, кто про приглашения не знает. Отсюда
  `exception when invalid_text_representation`
- **Приглашение показывает функция `erp_invite_preview`, а не выборка.** Человек
  ещё не вошёл, а RLS не видит фильтр запроса: политика `for select to anon`
  открыла бы всю таблицу приглашений вместо одной строки
- **Право `staff.invite`, а не роль учётной записи.** Приглашение раздаёт права,
  и гейт обязан совпадать с сервером ЗНАЧЕНИЕМ: `isPrivileged` это
  admin + director + РОП, `is_admin()` — только admin, и на этом расхождении
  в проекте уже ловились
- **Роль `pending` — единственная без единого права** (у `hr` тоже ноль, но это
  должность, а не состояние). Её ставит триггер каждому, кто пришёл без
  приглашения. Без строки в `erp_employees` `erp_role_of_caller()` выводит роль
  из профиля и делает новичка МЕНЕДЖЕРОМ: правка любого заказа, ТЗ, перенос
  этапов — причём по всей фабрике, потому что ограничение по цеху на человека
  без цеха не действует (`canActInDept` там fail-open, и это осознанно)
- **Колонка `pending` в матрице прав не редактируется** (`LOCKED_ROLES` рядом
  с `director`): одна галочка раздала бы право всем неназначенным разом.
  Права выдаются назначением должности, а не правкой этой колонки
- **Приглашения требуют выключенного «Confirm email».** Иначе `signUp` не отдаёт
  сессию, и приглашённый упирается в экран подтверждения адреса — ровно
  в то, ради чего приглашения и заводились
- Отзыв — `revoked_at`, не DELETE: журнал «кто, кого и куда звал» и есть
  половина смысла таблицы. Отзыв идёт с `.select()` — RLS на UPDATE запрещает
  через `USING`, то есть отдаёт «0 строк», а не ошибку

## Правила регистрации и входа (сессия 31)

- **В проекте ДВА независимых гейта: подтверждение адреса почты (Supabase Auth,
  «Confirm email») и одобрение администратором (`profiles.approved`).**
  Интерфейс обязан различать их и называть тот, который держит человека сейчас.
  Стена говорила «ждите администратора» в обоих случаях — и когда админ уже
  одобрил, и когда дело было только в письме. На этом встали ДВЕ учётные записи
  (13.08 и 16.07), обе с `approved = true`, обе ни разу не вошедшие
- **`signUp` НЕ создаёт сессию при включённом подтверждении адреса.**
  Класть `user` в стор по факту успешного `signUp` нельзя: получается экран
  «вы вошли, но ждите», за которым нет ни сессии, ни способа что-либо
  перечитать. Пользователь появляется только из `fetchProfile`, то есть
  из настоящей сессии — тогда любая стена по определению говорит правду
- **Имя нового сотрудника уходит в `options.data.name`**, откуда его читает
  серверный триггер `handle_new_user`. Клиентский `profiles.upsert` при
  регистрации невозможен в принципе: RLS разрешает INSERT и UPDATE только
  `is_admin()`, а сессии в этот момент нет вовсе. Он там стоял, его ошибку
  игнорировали, и у всех, кто регистрировался сам, имя в базе равно почте
- **`emailRedirectTo` задаётся явно** (`window.location.origin`): иначе адрес
  берётся из Site URL проекта, а там легко оказывается чей-то `localhost`
- **Отказ `email_not_confirmed` — не ошибка формы.** Пароль верен, исправлять
  человеку нечего; ему нужно письмо. Такой отказ ведёт на экран подтверждения
  адреса с повторной отправкой, а не в красную строку под полем
- **Стена доступа обязана давать выход без F5.** Одобрение приходит из чужой
  вкладки, подписки на собственный профиль нет — поэтому «Проверить снова»
  (`refreshProfile`), а не молчаливое ожидание. Догадаться до перезагрузки
  человек должен не сам
- **`maybeSingle`, а не `single`, когда строки может не быть.** У `single`
  отсутствие строки — ошибка `PGRST116`, и «профиля ещё нет» становится
  неотличимо от «запрос не прошёл». `fetchProfile` смотрел только на `data`
  и обрыв связи при живой сессии показывал как форму входа
- **Класс в разметке — не стиль.** `#pendingScreen` и все `.pending-*` жили
  в `App.jsx` без единого объявления CSS (остались от html-прототипа): человек
  упирался в системный шрифт и нативную серую кнопку и читал это как поломку
  сайта. Заметно только глазами — ни один тест на разметку такого не видит

## Правила восстановления доступа (сессия 31, волна 2)

- **Пустой экран загрузки — только на ПЕРВИЧНУЮ проверку сессии
  (`initializing`), а не на общий `loading`.** `loading` поднимает каждый вход
  и каждая регистрация, и пока гейт App стоял на нём, форма на время запроса
  РАЗМОНТИРОВАЛАСЬ и возвращалась заново — с пустыми полями и обнулённым
  состоянием экрана. На приглашении из-за этого не показывалось объяснение
  «такой сотрудник уже заведён»: исход приходил в компонент, которого уже нет,
  и человек видел ту же пустую форму. На проде — девять попыток подряд.
  Кнопки при этом имеют собственные состояния («Вход…», «Создаём доступ…»)
  и показать их не могли: экрана в этот момент не существовало
- **Unit-тест экрана такого дефекта не видит по построению**: он монтирует
  компонент напрямую, минуя App, — а ломал экран именно App. Сторож живёт
  в `App.test.jsx` («вход не подменяет форму глобальным „Загрузка…“»),
  и проверять такие вещи нужно там, где собирается настоящее дерево
- **Флаг первичной загрузки снимается в `finally`.** У `init()` четыре выхода
  (нет сети, есть сессия, dev-автологин, обычный), и флаг, оставшийся поднятым
  на любом из них, — это белый экран навсегда, а не «чуть дольше грузится»
- **Приглашение на существующий адрес — ТУПИК, а не ошибка формы.** `signUp`
  второй учётной записи не создаёт, поэтому ссылка не сработает НИКОГДА,
  сколько её ни открывай: человеку нужен вход, а не ещё одна попытка. Экран
  `already_registered` называет адрес и ведёт ко входу; админку это же
  предупреждает ДО выписки — `InviteModal` сверяет введённый адрес с профилями
- **Восстановление пароля обязано существовать.** Его не было вовсе:
  «Забыли пароль?» отсутствовал, и единственным выходом из забытого пароля
  была регистрация заново, отвечающая «адрес уже заведён». Ссылка приходит
  событием `PASSWORD_RECOVERY`, и ветка формы нового пароля в App стоит ПЕРЕД
  проверкой пользователя: ссылка уже вошла человека в систему, и без неё он
  попал бы прямо в оболочку, так и не задав пароль

## Правила администрирования учётных записей (сессия 31, волна 3)

- **`service_role` в браузере не бывает.** Создание учётной записи, смена
  пароля и адреса, удаление — это Admin API GoTrue, а он требует ключ,
  обходящий RLS ЦЕЛИКОМ. Отсюда серверная функция `supabase/functions/admin-users`:
  ключ живёт у неё, клиент только зовёт и показывает ответ
- **Гейт функции — `is_admin()`, вызванная ОТ ЛИЦА ВЫЗЫВАЮЩЕГО**, а не своя
  проверка роли. Личность берётся из токена (`caller.auth.getUser()`), права —
  из той самой функции, на которой стоят политики `profiles`. Своя реализация
  разошлась бы с политикой в первую же её правку; в проекте на таком
  расхождении уже ловились (`isPrivileged` против `is_admin()`)
- **Роль новому сотруднику проставляет ТОТ ЖЕ путь, что приглашению.** Функция
  заводит одноразовый `erp_invites` и кладёт код в метаданные создаваемого
  пользователя — дальше работает триггер `handle_new_user`, единственное место,
  где роль, цех и одобрение вообще проставляются. Вариант «создать, потом
  дописать профиль» — вторая реализация тех же правил, и она разъедется
- **Созданному админом адресу подтверждение не нужно** (`email_confirm: true`):
  пароль задан вручную, а письма шлёт встроенный SMTP — ровно то, от чего
  проект ушёл, заведя приглашения
- **Удаление — не замена «Отключить».** Мягкое отключение остаётся обычным
  путём: история сохраняется, человека можно вернуть. Удаление живёт для одного
  случая — запись заведена по ошибке, и три вещи его сторожат: себя удалить
  нельзя, заказы (`created_by` объявлен `no action`) отказывают ДО первой
  записи, а подтверждение требует впечатать адрес
- **`profiles` не связан с `auth.users` внешним ключом ВООБЩЕ** (проверено на
  боевой схеме). Строку профиля убирает сама функция; забыть — значит оставить
  в списке человека, которого больше нет, и «Отключить» на нём не сделает ничего
- **У `functions.invoke` своя механика ошибок**: на любой не-2xx он кладёт
  в `error` единственный текст «Edge Function returned a non-2xx status code».
  Причина лежит в теле (`error.context`), и достаёт её `erp/store/adminUsers.ts` —
  один раз, а не в каждом действии. Иначе отказ прав, занятый адрес и заказы,
  держащие удаление, выглядели бы одинаково
- Проверка серверной половины — `erp/utils/adminUsers.test.ts`: он читает

- **Журнал хранит приращения, агрегат — итог, пишутся ОДНОЙ транзакцией.**

  (`qty_received`) и `erp_subcontract_moves` (количества подряда). Журнал без
  агрегата — цифры, которых не видит производство; агрегат без журнала — число
  без объяснения
- **Колонку, которую ведёт триггер, клиент только ЧИТАЕТ.** `qty_received`
  стала суммой журнала, и прямая запись из карточки приёмки убрана: два
  писателя одной колонки затирают друг друга молча, потому что оба пути
  «работают». Поле в интерфейсе становится текстом в том же коммите
- **Схема отчёта участка — в данных** (`erp_departments.result_fields`), как
  и материальный гейт. Пусто = отчёт не требуется (fail-open): цех не должен
  остаться без способа сдать работу из-за незаполненной настройки
- «Принято в работу» считает КЛИЕНТ (`utils/stageInput`) и остаётся
  единственным источником: несколько предшественников дают МИНИМУМ, а не сумму —
  параллельные ветки нанесения обрабатывают одни и те же единицы, и сумма дала
  бы 200 при тираже 100. В журнал число уходит снимком: это аудит, а не расчёт
- **`phase` подряда — не второй статус,** а детализация внутри `in_progress`
  этапа. Единый статус — `erp_item_stages.status`. `payment_status` не участвует
  ни в одном производственном переходе: неоплаченный подряд не останавливает цех
- **Сравнение со строковым значением, которое переехало, не падает — оно молча
  становится всегда истинным.** Гейт упаковки сравнивал `sc.status <>
  'received_at_pinhead'`; после переезда в `phase` он пустил бы упаковку до
  приёмки подряда, и заметили бы это на отгрузке непринятого. Переписан
  на `phase`, сторожит `warehouseGate.test.ts`
- **Новый тип складской задачи — двенадцать точек касания**, и опаснее всех
  терминальный статус: пропуск в `TERMINAL` не роняет ничего, он даёт ВЕЧНЫЙ
  бейдж на пункте меню. Сторожит `warehouseTaskTypes.test.ts`
- **`origin` этапа (образец/серия) в маршрутную логику НЕ входит** — только
  бейдж и фильтр. Иначе цех работал бы с образцом по особым правилам, а он
  проходит те же гейты и переходы
- **Колонка, которой нет в `ORDER_LIST_SELECT`, молча приезжает `undefined`.**
  Список перечисляет колонки поимённо; добавили колонку, которую читает
  очередь или канбан, — впишите её туда же
- `substring(x from '…')` в Postgres возвращает ПЕРВУЮ ГРУППУ, а не совпадение.
  Необязательная группа не совпала — вернулся NULL. Группы в таких шаблонах
  только не захватывающие (`(?:…)`)
- **Шрифты — только токенами, и только загруженные.** `Space Grotesk` и
  `Roboto Condensed` жили в CSS, но отсутствовали в `index.html`: браузер молча
  падал на следующий, правила существовали, эффекта не давали. Сторожит
  `styles/fonts.test.ts`
- Эхо даты под полем НЕ УБИРАТЬ: нативный `type="date"` печатает дату в формате
  локали браузера, и в en-US «08/14» читается двояко. Пресеты убраны, эхо
  оставлено — решение записано в SESSION-STATE, чтобы его можно было оспорить

## Правила ERP (правки заказчика 10.08, волна 2)

- **Мощность производства считается в ИЗДЕЛИЯХ, а не в этапах.** Одна футболка
  проходит закрой → нанесение → швейку → ВТО, и сумма «штук по этапам» даёт
  вчетверо больше единиц, чем фабрика выпускает. `utils/capacity` сравнивает
  10 000 ед./мес с объёмом активных заказов по сроку сдачи; поцеховая сетка
  `/load` — другая величина, и складывать их нельзя. Обе подписаны на экране
  прямым текстом именно поэтому
- **Дневная мощность НЕ хранится.** Документ прямо запрещает фиксированное
  значение на день: оно считается из числа рабочих дней месяца, поэтому
  в феврале и марте при одной месячной мощности дневная разная. Праздничного
  календаря нет намеренно — погрешность в день-два меньше погрешности плана
- `percentUncapped` рядом с `percentOf`: потолок в 100 % прячет перегрузку —
  ровно тот случай, ради которого показатель заводили. Правило про ноль
  в знаменателе общее, живёт в одном месте
- **Очередь «Не запланировано» смотрит на ГОРИЗОНТ, а не на видимую неделю.**
  Слоты грузятся за неделю, а «запланировано ли вообще» границы не имеет:
  считать по загруженной неделе значит предлагать запланировать заново то, что
  разложено на следующую. Отсюда отдельный узкий запрос `plannedStageIds`
  и пересчёт после снятия задачи — у этапа могут быть задачи и на другие дни
- Просрочка ЗАКАЗА и просрочка ЭТАПА — разные решения (отвечать перед клиентом
  или разбираться в цехе), и фильтр их различает вместе с четвёртым видом
  «этап без плановой даты». Этап без `planned_end` просроченным не считается
  и считаться не должен — но и молчать о нём нельзя: он выпадает из контроля
  сроков целиком (на проде 305 открытых из 311)
- **Стор разделён на ЯДРО и доменную часть.** В ядре — `bootstrap`, `orders`,
  `permissions`, `bypass`, `realtime` (то, чем пользуется оболочка); остальные
  11 слайсов приезжают отдельным чанком вместе с первым экраном через
  `erp/lazyScreen`. Экран ERP заводится ТОЛЬКО этой обёрткой — правило по
  ЭКРАНАМ, а не по файлу-оболочке: админка смонтирована и в Order Studio, мимо
  `ErpApp`, и сторож, привязанный к одной точке входа, её не увидел
- **Данные доменных слайсов живут в ядре** (`store/domainState.ts`), приезжают
  только действия: `loadBootstrap` наполняет часть этих полей ещё до открытия
  экрана, и подключение слайса с собственными значениями затирало бы загруженное
- **Файлы `src/store/**`, `main.jsx` и `App.jsx` НЕ импортируют `erp/store/*`
  статически.** Одна такая строка (`resetErpStore` в `useAuthStore`) тянула весь
  ERP-стор во входной чанк — 26 кБ gzip у каждого, кто открыл только Order
  Studio. Сбросы регистрируются через `store/appReset`; строку сторожит тест,
  потому что бюджет бандла скажет «стало больше», но не скажет, из-за чего
- Сторожевой тест читает миграцию по ИМЕНИ ФУНКЦИИ (`latestDefining`
  в `utils/migrations.testutil`), а не по имени файла. Копия этого правила
  в каждом тесте уже один раз разошлась: `permissionsCoverage` сверялся
  с текстом стража, который база переписала дважды
- **Проверочный блок на живой базе обязан заканчиваться `raise exception`.**
  `execute_sql` коммитит: функция `set local role` + `update` без исключения
  в конце переписала боевую настройку мощности. Значение восстановлено, но
  правило теперь записано — откат делает исключение, а не намерение

## Правила ERP (security-разбор 10.08)

- **Право, до экрана которого не дойти, — то же декоративное право, только
  этажом выше.** Разделы «Операции» были закрыты ролью УЧЁТНОЙ ЗАПИСИ, двумя
  независимыми списками (маршрут и меню). Выданные права оказались недостижимы:
  кладовщик с `warehouse.manage` не видел пункта «Склад». Список теперь ОДИН —
  `utils/screenAccess`, и он же используется в обоих местах. Правило: раздел
  видит тот, кто может там работать, плюс менеджер заказа (на чтение)
- **Пропуск, выданный «на всякий случай», однажды выдаётся не тому.** `v_move`
  в страже этапов стоял OR-ом не только там, где меняется цех, но и в проверке
  принадлежности цеху и в четырёх ветках статуса — на допущении «право переноса
  есть только у ролей со сквозным доступом». Допущение сломалось в тот день,
  когда перенос выдали менеджеру. Пропуск теперь действует ТОЛЬКО внутри самого
  переноса (метка транзакции `erp.moving`), а право RPC проверяет явно
- **Политика, которая «и так не работает», однажды заработает.** `erp_att_update`
  стояла на «любой участник», но была неисполнима без SELECT-политики у бакета.
  Миграция, добавившая чтение ради ТЗ, разблокировала запись всем сразу.
  Проверяя политику, смотрите не только на её предикат, но и на то, что мешает
  ей исполняться сегодня
- **Выход обязан завершать сессию даже без сети.** `signOut()` при сбое
  возвращает ошибку ДО удаления сессии: токен остаётся, экран показывает форму
  входа, а на общем планшете следующий человек получает доступ предыдущего.
  При неудаче — `signOut({ scope: 'local' })`, чистка и снятие флага в `finally`
- Колонка, добавленная в `erp_item_stages`, попадает в `v_guarded` ТЕМ ЖЕ
  коммитом: ранний выход стража стоит выше проверки прав и проверки цеха,
  поэтому не вписанная колонка не проверяется вообще ничем

## Правила ERP (решения заказчика по матрице, сессия 29)

- **Складские задачи — под `warehouse.manage`** (директор, РП, кладовщик,
  закупщик). `material.receive` для этого не годился: маркировка и упаковка —
  не приёмка, и расширение права означало бы, что название перестало совпадать
  со смыслом. Диспетчеру не даётся: он распоряжается очередью цехов, а не
  физическим движением товара
- **INSERT складской задачи гейтится ДВУМЯ правами** (`warehouse.manage` ИЛИ
  `order.manage`). Строку можно вставить сразу в терминальном статусе — тогда
  гейт на UPDATE обходится вставкой, поэтому INSERT тоже под правом. Вторая
  ветка обязательна: подряд «под ключ» заводит упаковку из клиента (этапов нет,
  триггер не сработает никогда), а делает это менеджер заказа
- `stage.move_department` есть и у менеджера (решение заказчика). Перенос меняет
  загрузку производства — менеджер влияет на неё без ведома диспетчера; это
  названо вслух и снимается галочкой
- **`DEFAULT_PERMISSIONS` приводятся К БАЗЕ, а не наоборот**, когда расхождение
  подтверждено как осознанная правка админа: база — источник правды, а запасные
  значения нужны ровно для случая «матрица не загрузилась», и отбирать в нём
  работающий доступ хуже, чем сохранить
- Блок «только просмотр» — общий примитив `components/ReadOnlyFieldset`, а не
  копия в каждом экране: нативный `fieldset[disabled]` гасит всё вложенное разом
- **Сторож, который слабее своего названия, опаснее его отсутствия.** Тест
  «дефолты не выдают прав, которых не даёт seed» проверял ровно одну строку
  (`hr` пуст) и правку `catalog.edit` у РП не заметил бы. Решения заказчика
  по матрице закреплены поимённо в `permissionsCoverage.test.ts`

## Правила ERP (даты, сессия 29)

- **Календарная дата берётся только из `src/utils/date`** (`localToday`,
  `isoDate`, `addDays`, `mondayOfWeek`, `weekdayIndex`). `toISOString()` даёт
  дату в UTC: в Москве полночь 10.08 — это 09.08 21:00Z, и «слайс от ISO»
  отдаёт девятое. `toISOString()` годится для МОМЕНТА (`created_at`, `fact_at`,
  `shipped_at`), не для календарного дня. Сторожит `utils/date.test.ts`,
  проверяя сам оборот в исходниках
- **На доске плана ошибка удваивалась**: понедельник считался через
  `toISOString` (−1), и от него тем же способом отсчитывались дни (ещё −1).
  10.08.2026, настоящий понедельник, выходил «средой», а неделя начиналась
  с субботы 08.08. Дефект дожил до прода при зелёном CI, потому что
  **в UTC-контейнере он не воспроизводится вовсе** — сдвиг равен нулю.
  Поэтому тесты дат идут в поясе заказчика: `process.env.TZ = 'Europe/Moscow'`
  в unit, `test.use({ timezoneId })` в e2e
- **День недели считается ИЗ ДАТЫ** (`erp/utils/format.weekdayName`), а не по
  номеру колонки. Подпись по индексу («первая колонка — понедельник») с датой
  не спорит: когда расчёт недели уехал, подписи уехали вместе с ним вместо того,
  чтобы выдать расхождение

## Правила ERP (хвосты документа 10.08, сессия 29)

- **Сторож на колонку-гейт не сторожит ничего, если её никто не двигает.**

- Заглавные начертания ERP объявлены ОДНИМ групповым правилом (`.labelCaps`

- **Uppercase Order Studio не трогать.** Это его документированный язык, и из

## Правила ERP (правки заказчика 10.08, волна 0)

- **Dev-автологин включается ЯВНО** (`VITE_DEV_AUTOLOGIN=1`) и только когда настоящей
  сессии нет. Прежний `import.meta.env.DEV` включал его у каждого, кто запустил
  `npm run dev`, — в том числе против боевой базы: интерфейс показывал полный доступ
  админа, запросы уходили ролью `anon`, чтение возвращало пусто, запись отвечала
  «new row violates row-level security policy». Человек, ни разу не увидевший формы
  входа, не мог понять, что он не вошёл. `playwright.config.ts` ставит флаг сам
- **Сессия отслеживается всё время работы** (`watchAuthState` → `onAuthStateChange`),
  а не проверяется один раз в `init()`. Потеря сессии — это `sessionLost()`: сброс
  сторов и внятное «Сессия истекла, войдите заново». Dev-пользователь исключён:
  сессии у него не было, и терять ему нечего
- **Любой сетевой вызов идёт через `erpQuery`** (`store/shared.ts`). Он превращает
  бросок supabase-js в такой же `{ data: null, error }`, какой пришёл бы от сервера,
  и дальше работает уже написанная ветка `if (error) …`. Без него ветка не
  выполняется вовсе: busy-флаг не снимается, откат не делается, а отклонение промиса
  всплывает сырым `Load failed` из WebKit
- **У `loadAll` НЕТ guard'а «уже грузим — выходим», и это проверено.** Обе формы
  экономии (ранний выход и дедупликация общим промисом) ломают очередь цеха —
  10 e2e из 24: экраны зовут `loadAll()` как загрузку своих данных и читают стор
  сразу после, а отобранная загрузка даёт «Выберите свой цех выше» там, где задания
  есть. Лишний запрос дешевле пустого экрана
- **Одинаковые тосты не копятся**: повтор поднимает счётчик у висящей полосы. Один
  системный сбой доходит до человека десятью экранами сразу, потому что флаги
  загрузки общие. Id тоста — счётчик, а не `Date.now()`: два сообщения в одну
  миллисекунду получали общий id, и закрытие одного гасило оба
- **Гейт ТЗ на сервере — то же право, что в интерфейсе** (`erp_has_permission('tz.manage')`),
  а не отдельная функция по `profiles.role`. Прежняя `erp_can_manage_tz()` не знала
  про `erp_employees.role`, и диспетчер получал «кнопка есть, действие падает»
- **У бакета обязана быть SELECT-политика**, даже когда он публичный: публичная
  раздача идёт мимо RLS, а клиентские `upsert`, `remove` и `list` — через неё

## Правила ERP (код-ревью 05.08)

- Счётчики этапа (`qty_done`, `qty_rework`) пишутся ТОЛЬКО приращением, на сервере
  (`erp_stage_report_progress`, `erp_stage_apply_defect`). Абсолют с клиента —
  потерянное обновление: два планшета в одном цехе читают своё значение и
  затирают запись друг друга. Для цеха с несколькими исполнителями это обычный
  день, а не редкая гонка
- Действие из нескольких записей — ОДНА транзакция (RPC), а не `Promise.all`.
  Пачка независимых UPDATE с общим откатом интерфейса откатывает поверх уже
  закоммиченных: возврат брака оставлял позицию в состоянии, которого никто
  не выбирал. У переноса этапа это же правило раньше решалось компенсирующей
  записью — с транзакцией она не нужна
- Логику маршрута (какие этапы затронуты) считает КЛИЕНТ и остаётся её
  единственным источником. Сервер отвечает за атомарность и арифметику: вторая
  реализация обхода `depends_on` на SQL — та самая рассинхронизация, из-за
  которой текст подтверждения когда-то разошёлся с фактом
- Перенос между цехами переводит на целевой этап ВСЕХ, кто зависел от исходного.
  Без этого финальный ОТК открывался раньше перенесённой работы: исходный этап
  закрыт, ОТК видит зависимость выполненной, а новый цех ещё не начинал
- Страж этапов проверяет и ПРИНАДЛЕЖНОСТЬ ЦЕХУ (`erp_can_act_in_dept`, зеркало
  `canActInDept`) — интерфейс гейтит дважды, право И цех, и матрица второго
  не отменяет. Право `stage.move_department` проверку снимает: целевая строка
  по определению в чужом цехе, а перенос интерфейс гейтит по цеху-ИСТОЧНИКУ
- Плановые даты этапа — под `order.manage`, НО взятие задания в работу пишет
  `planned_end` под `stage.take`: форма «Взять в работу» просит план завершения
  и пишет его тем же действием. Без исключения каждый рабочий получал 42501
  на каждом взятии, а вместе с датой терялся расчёт просрочки
- Сторожевой тест, читающий миграцию ПО ИМЕНИ, сторожит файл, а не базу: функции
  пересоздаются целиком, и прежняя миграция остаётся со СТАРЫМИ правилами. Брать
  последнюю миграцию, определяющую функцию (`latestDefining` в
  `serverPermissions.test.ts`)
- Каждый `supabase.rpc(...)` сверяется с сигнатурой в миграциях
  (`rpcContract.test.ts`): опечатка в имени функции или параметра не ломает
  ни сборку, ни один тест — она отвечает PGRST202 в проде, на том действии,
  которое никто не прокликал
- Постраничная выборка обязана иметь УНИКАЛЬНЫЙ доводчик сортировки, а смещение
  вести своим счётчиком, а не считать из стора: `due_date` не уникален, а в стор
  архивные заказы попадают мимо пагинации (диплинк, realtime) и сдвигают
  смещение. Дубль гасит дедуп по id — пропуск не видно ничем
- `started_at` ставится ОДИН раз, при первом входе в работу. Снятие блокировки,
  переоткрытие после брака и открытие этапа при переносе её не сдвигают: от неё
  считается бейдж «ТЗ обновлено», и сдвиг прятал предупреждение, ради которого
  бейдж и сделан
- Файл, загруженный в бакет и не привязанный к строке БД, убирается за собой
  (`removeOrphanUpload`, политика `erp_att_delete_own` — автор удаляет СВОЙ
  объект). Прежде в трёх местах стоял комментарий «удалять политика не даёт»,
  и сироты копились навсегда
- Ошибки Supabase во ВСЕХ слайсах идут через `erpError` — он называет причину
  (офлайн, отказ прав, конфликт). Плоский `toast.error('Не удалось …')` делает
  42501 от стража неотличимым от обрыва сети
