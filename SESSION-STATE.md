## Состояние на 2026-10-01 (сессия 77) — правки ERP 01.10: шесть пунктов одним PR

Ветка `claude/new-edits-01-10-hcg3zo`, PR #195. Документ владельца «правки ерп» (01.10):
шесть пунктов. Владелец: запрос о просрочке пишет системный автор «ERP»; сначала два PR,
затем — «добавь пп. 4–5 в PR 1».

### Что сделано

- **П. 1, ткань без рулонов.** Причина — данные: у 4 тканей на бою пустая единица
  (форма закупки писала `''`), их приняли без рулонов, закрой встал. Ткань без единицы
  учитывается рулонами (`materialTracksRolls` ↔ `erp_material_tracks_rolls`); закупка ткани
  без единицы пишет «кг»; `erp_material_rolls_add` добавляет рулоны к ПРИНЯТОЙ ткани без
  нового прихода (сумма весов = принятому, ключ попытки `add_key`). Закрой говорит
  «Ткань принята без разбивки по рулонам»; «Материал поступил» рулонную ткань не принимает.
- **П. 2, подсветка.** `:hover`/указатель только у `a`/`button`; заголовки склада и закупки
  ведут в заказ. Сторож в `styles.test.ts`.
- **П. 3.** «Новый заказ» и формы ввода не закрываются по затемнению и Escape
  (`Modal`: `closeOnOverlay`/`closeOnEscape`).
- **П. 6.** Файлы заказа правятся в форме правки (`EditOrderFiles`): удалить/заменить/
  загрузить сразу. DELETE-политика вложений открыта `order.manage` для файлов формы;
  `erp_tz_document_remove` снимает ТЗ (`is_current = false` у группы, история остаётся).
  Кнопки — по зеркалу политики `utils/attachmentRights.ts`. `currentVersion` больше не
  подставляет старшую версию, если текущей нет (иначе снятое ТЗ воскресало).
- **П. 4, уведомления.** Уведомление гаснет, когда сообщение показано в чате
  (`erp_chat_mark_seen` ставит `read_at`), а не по клику; открытие ленты не двигает водяную
  отметку; упоминание и ответ приходят и в режиме «Без уведомлений» (отмена решения 20.09);
  колокол — «Сообщения» (счётчик с сервера) и «Сроки»; переход догружает ленту до
  сообщения; переподключение перечитывает уведомления без дублей, звук — одна вкладка;
  настройки — `erp_user_settings` (звук по умолчанию ВКЛ).
- **П. 5, просрочка.** `erp_overdue_requests_run()` + `pg_cron` 06:00 UTC: системное
  сообщение (пустой `author_id` = «ERP») «@Иванова Марийка, заказ №… просрочен…»,
  упоминание и `chat_mention`; один раз на срок (`erp_overdue_requests`, ключ заказ × срок).
  Правка/удаление сверяют автора `is distinct from` (с `<>` пустой автор пропускал всех).

### Миграции

Применены все пять: `20261001185238_erp_fabric_rolls_add`, `20261001185758_erp_order_files_edit`
(через `alter policy`), `20261001190924_erp_chat_notify_read`, `20261001194514_erp_overdue_chat_request`,
`20261001194849_erp_chat_system_guard_revoke`. Инструмент применения миграций держит на ручном
подтверждении текст, где рядом удаление и `erp_order_attachments` (а также `drop policy`), —
подтверждение в сессии не показывается, вызов падает по таймауту. Поэтому `erp_chat_edit`/
`erp_chat_delete` НЕ переписаны: их `<>` с пустым автором закрывает страж
`erp_chat_system_guard` (BEFORE UPDATE на `erp_chat_messages`: у сообщения без автора
вошедший не меняет `body`/`deleted_at`/`edited_at`). Проба на бою: удаление и правка
системного сообщения админом — 42501. Проба п. 5 с откатом — 7 запросов, повтор 0,
перенос срока 1.
