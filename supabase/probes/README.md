# SQL-пробы прав (`supabase/probes/`)

Пробы — сценарии «кто что может» против **живой** базы: менеджер, МС, начальник
цеха, руководитель, отключённая учётная запись пробуют читать и писать, и каждая
попытка сверяется с ожидаемым ответом. Миграций в файлах проб нет — они идут
против уже применённой схемы.

### Остаточный путь подделки (находка безопасности №1 закрыта ЧАСТИЧНО)

J закрывает подделку связи с ERP объектами самого продавца, пустым заказом ERP (`fake_*`), копией ТЗ,
которая уже привязана к другому заказу ERP (`oldcopy_*`, раунд 2 ревью), и давней копией того же МС
(`agedcopy_*`, финальное ревью). Хелпер `order_v4_erp_authentic` сверяет **владельца** объекта Storage
с `launch_by`, требует, чтобы путь документа ТЗ не встречался у другого заказа ERP, и **окно по возрасту**:
`o.created_at >= launch_started_at - interval '30 minutes'` (метка — у заказа v4 `orders.id =
erp_orders.tz_order_id`; метки нет — не подлинный). Запас 30 минут нужен: шаг recheck продлевает метку уже
ПОСЛЕ загрузки копий на шаге files (условие `>= launch_started_at` без запаса сломало бы настоящий запуск —
`agedfresh_*`, копия за 20 минут до метки, проходит). Остаток неудачной попытки давнего запуска другого
заказа (на бою — часы и дни назад) подлинности больше не даёт.

Не закрыт путь через копию МС, которая **ни к какому заказу ERP не привязана и создана за последние
30 минут до метки** (`resid_*`):

1. МС ставит метку (`launch_check`) на этом заказе.
2. Продавец с правом ERP `tz.manage` берёт из списка бакета (публичный, ключи видны любому члену ERP:
   `erp_att_read = erp_is_member()`) непривязанную копию ТЗ этого МС `tz/v4-…`, созданную не раньше чем за
   30 минут до метки: копию текущей попытки (шаг files, после которого `erp_create_order` упал) или копию
   неудачной попытки запуска другого заказа этим же МС в том же окне.
3. Продавец вставляет свой `erp_orders` с `tz_order_id`/`tz_number` (оба ему известны), `erp_order_items`
   и `erp_tz_documents` со ссылкой на эту копию. Хелпер отвечает `true`, `launch_check` — `already`
   с поддельным `erp_order_id`, `transition(production)` проходит.

Окно сузить дальше внутри J нельзя: путь `tz/v4-<attemptId>/…` с заказом v4 не связан, а метку продлевает
recheck после files. Нужна свежая (≤ 30 минут) непривязанная копия того же МС — то есть почти одновременная
неудачная попытка запуска.

Посылка плана «у продавца нет `tz.manage`» на бою **не выполняется**: у всех 10 активных одобренных профилей
с ролью `manager` (будущие продавцы с `is_sales`) должность ERP — `production_head` (SELECT 18.10), то есть
`tz.manage` и `order.manage` есть. Пробы `resid_*` фиксируют путь как OK (известный факт, как К13 для Storage);
`resid_worker_doc` показывает, что при должности `worker` вставка документа ТЗ — 42501.

Внутри J без правки ERP путь не закрыть: `erp_orders.created_by` и `erp_tz_documents.uploaded_by`
без умолчания (автора вставки не узнать), аудит ERP пишет только UPDATE. **Решение — за владельцем**, варианты:
- (а) снять у продавцов должность ERP `production_head` (данные, без миграции) — путь закрывается пробой
  `resid_worker_doc`;
- (б) принять риск (подделку видно: заказ ERP без этапов от `erp_create_order`, вручную);
- (в) ослабить заморозку ERP (умолчание `created_by = auth.uid()` или страж вставки `erp_tz_documents`) — затем
  хелпер сверяет и автора заказа ERP.

### Разделение обязанностей при запуске (находка безопасности №2, раунд 2)

Проверки «свой заказ запускает другой» и «без оплаты разрешили вы — запускает другой» стоят и в `launch_check`,
и в ветке `ready_to_launch → production` перехода: переход зовут напрямую (`race_*`). `set_payment` при свежей
метке запуска (10 минут) и при созданном заказе ERP оплату не меняет никто — P0001; при старой метке смена оплаты
снимает `launch_started_at`/`launch_by`, и запуск снова идёт через `launch_check` (`toctou_*`).

### Мутации миграции J (`mutations/make-mutations.mjs`)

`node supabase/probes/mutations/make-mutations.mjs <каталог>` пишет по файлу на мутацию:
`1m-<n>-<имя>-mutation-J.sql` = `begin`, предусловие (H и I в журнале, md5 тел B/F), J с одной правкой,
пробы `order_v4_launch.sql`, `PROBE_RESULT`. Ожидание каждой — `fails>0` (какая проба краснеет — в шапке файла
и в поле `kills`); №16 `no-is-member` — эквивалентная (на бою `erp_has_permission` истинна только у активного
и одобренного профиля, то есть влечёт `erp_is_member()`): ожидание `fails=0`, предикат оставлен защитой.
Сторож `pinhead-react/src/orderstudio/orderV4Launch.test.ts` держит, что каждая правка находится ровно один
раз и «убиваемая» проба есть в файле.

## Как запускать

1. Supabase → SQL Editor проекта `pinhead-os-v2`.
2. Вставить файл **целиком** и выполнить.
3. Результат — **ошибка** с текстом `PROBE_RESULT fails=0 total=N {…}`.
   `fails=0` и `total`, равный числу из шапки файла, — всё в порядке. Иначе
   в карте ответов ищите ключи `FAIL имя` (`got` — что ответила база,
   `want` — ожидаемое начало ответа).

Ошибка — это и есть откат: файл сам открывает транзакцию (`begin`, `set local
lock_timeout = '3s'`, `statement_timeout = '30s'`), а последний блок бросает
исключение. **В базе ничего не остаётся**: заказы `PROBE-…`, смена роли
сотрудника, строки журнала — всё откатывается. Номера заказов
(`order_number_seq`) не расходуются: тестовые заказы вставляются с явным
`order_number = 'PROBE-…'`.

MCP `execute_sql` для проб не годится, пока он ждёт ручного подтверждения
на `delete`/`drop` (висит до таймаута) — запускает владелец через SQL Editor.

## Когда запускать

- После каждой правки прав, стражей, RPC или миграций Order v4 — и до, и после
  применения (до — сухим прогоном вместе с новой миграцией в одной транзакции).
- В **тихое время**: пробы берут блокировки строк `orders`, `erp_employees`
  и `storage.objects` на время прогона (секунды), а `order_artworks.sql` создаёт
  временную политику на `storage.objects` (до отката она видна только этой транзакции,
  но DDL берёт блокировку таблицы).

## Правила файла (сторож `pinhead-react/src/orderstudio/probesFiles.test.ts`)

Для каждого `supabase/probes/*.sql`:
- первые операторы — `begin; set local lock_timeout = …; set local statement_timeout = …;`;
- нет `insert into (public.)orders` без явного `order_number`;
- в конце — `raise exception 'PROBE_RESULT …'` (после него — только конец блока
  и необязательный `rollback;`);
- нет `commit`;
- в шапке — ожидание `fails=0 total=N`, и N равно числу проб `pg_temp.p(…)`;
- файл упомянут в этом README.

Пробы ссылаются на реальные профили боя (uuid в шапке файла). Сменилась роль
или `active` у такого профиля — пробы покажут `FAIL`; правьте данные пробы,
а не ожидания.
