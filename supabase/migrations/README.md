# Миграции: репозиторий и боевая база

## Зачем здесь `APPLIED.json`

Снимок журнала `supabase_migrations.schema_migrations` боевой базы
(`pinhead-os-v2`). Его сверяет
`pinhead-react/src/erp/utils/migrationJournal.test.ts` — часть CI.

Он поставлен после того, как отказ «применили к проду, файл в репозитории
не завели» случился **дважды**: 18.08 (три миграции — крой→каталог, DTG,
связь заказа с ТЗ) и 13.08 (`erp_stage_guard_ready`,
`erp_catalog_edit_policies`, `erp_guards_and_grants`). Оба раза заметили
задним числом.

Прод от такой потери не ломается — ломается репозиторий, и ломается молча:

1. **Реплей на чистое окружение** (превью-ветка, staging, восстановление
   из бэкапа) воспроизводит НЕ ту систему, что в проде. У потери 13.08 цена
   была прямая: в репозитории `erp_warehouse_ops_insert` и
   `erp_item_prints_*` стояли `with check (true)` — любой вошедший пишет
   складские операции и нанесения.
2. **Сторожевые тесты засыпают.** `latestDefining`
   (`src/erp/utils/migrations.testutil.ts`) читает последнюю миграцию
   в РЕПОЗИТОРИИ. Пока файла нет, тест сверяется с устаревшим текстом
   и остаётся зелёным — то есть подтверждает отсутствие гейта как норму.
3. **Правило «бери подлинный текст прежней миграции» перестаёт работать**:
   подлинный текст — это тот, что в БАЗЕ, а не тот, что в файле.

## Порядок после каждой выкладки

1. Применили миграции к проду — **сразу** заведите файлы в этой папке.
   Имя: `<YYYYMMDDHHMMSS>_<слаг>.sql`, слаг совпадает с именем в журнале.
2. Обновите снимок:

   ```sql
   select string_agg(version || ' ' || name, E'\n' order by version)
   from supabase_migrations.schema_migrations;
   ```

   Допишите новые записи в `migrations` массива `APPLIED.json`, сохраняя
   порядок по `version`.
3. Прогоните сторожа:

   ```bash
   cd pinhead-react && npx vitest run src/erp/utils/migrationJournal.test.ts
   ```

4. **Сверьте снимок с живой базой** — шаг обязательный, и вот почему он
   появился. Сторож проверяет снимок сам с собой и с файлами репозитория;
   живую базу из CI не прочитать (`supabase_migrations` не выставлена наружу
   PostgREST). Предполагалось, что «применили и не обновили снимок» видно
   в диффе выкладки. Сверка 31.08 показала, что не видно: снимок отстал
   на пять записей, и шесть дней все сторожа прав сверялись с определениями
   функций, которых в базе нет.

   ```bash
   cd pinhead-react && npm run migrations:verify
   ```

   Скрипт печатает отпечаток снимка (число записей + md5 списка версий)
   и запрос, дающий те же величины из прода. Сравнили — либо глазами, либо
   так, чтобы код возврата отвечал за вас:

   ```bash
   npm run migrations:verify -- --expect <md5 из прода>
   ```

   Сравниваются два числа, а не 192 строки: сверку списками не делают именно
   потому, что её не сделать.

## Поля записи снимка

| Поле | Смысл |
|---|---|
| `version`, `name` | как в журнале базы |
| `files` | файлы репозитория, несущие это изменение. Обычно один; больше — когда применили одной версией, а разложили на несколько |
| `noFile: true` | файла нет и не должно быть: перенос данных, бэкфилл, отменённое изменение |
| `fileLost: true` | файл ДОЛЖЕН был быть и его нет: применили к проду, в репозиторий не завели, подлинный текст восстановить нечем. Не смешивать с `noFile` — тот про решение, этот про потерю. Число таких записей держит ратчет в сторожe: новая потеря роняет CI |
| `note` | **обязательно**, когда соответствие не выводится из совпадения имени. Через месяц «разложили на два файла осознанно» и «привязал к первому попавшемуся, чтобы позеленело» неразличимы без записанной причины |

`preJournalFiles` — базовая схема Order Studio, применённая до того, как
завели журнал (его первая запись — `20260415202746`). Файлы есть, записей
в журнале нет и не будет.

## Чего сторож НЕ ловит

Он читает снимок, а не живую базу: в CI доступа к ней нет. Значит, он ловит
«применили и не завели файл», но не поймает «применили и не обновили
снимок». Второе, в отличие от первого, видно в диффе выкладки — там, где
о нём есть кому спросить.

Раз в несколько выкладок стоит сверять по-настоящему — сравнить
`pg_get_functiondef` каждой функции схемы с последним её определением
в репозитории. Сверка 22.08 прошла: 47 из 47 функций совпали, ни одной
незагейченной политики записи в живой базе нет.

## Локального CLI нет

`supabase/config.toml` в репозитории отсутствует, CLI не инициализирован —
`db push` и `db reset` локально недоступны. Миграции применяются через MCP,
и именно поэтому дисциплина «применил → завёл файл → обновил снимок»
держится только на этом сторожe.
