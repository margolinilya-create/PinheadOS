## Ревизия клиента: `SALES_CLIENT_REV` — всегда пара «клиент + миграция»

- `order_v4_save` пишет позицию ЦЕЛИКОМ: ключа нет — поле становится пустым. Вкладка,
  открытая до выкладки, не знает новых полей и первым автосохранением сотрёт их. Поэтому
  клиент шлёт `client_rev`, а сервер (обе функции — `order_v4_save_full` и
  `order_v4_save`, вторая открыта `authenticated` и зовётся в обход обёртки) отказывает
  меньшей ревизии: `P0001` «Вышло обновление — обновите страницу, правка не сохранена».
- **Повышение `SALES_CLIENT_REV` — всегда ПАРА:** константа в `api/salesOrders.ts` и новая
  миграция с тем же порогом в обеих функциях. Одно без другого — либо порог не защищает,
  либо новый клиент получает отказ. Сторож `orderstudio/orderV4Rights.test.ts` сверяет
  порог в тексте миграции с константой.
- Поднимать, когда payload получает поле, которое старый клиент затёр бы. Лишний ключ
  старый сервер игнорирует — поэтому порядок выкатки такой:
  1. мердж и **выкладка фронта** (новый клиент шлёт новую ревизию, старый сервер её не смотрит);
  2. **затем миграция** (сухой прогон проб → применение в SQL Editor → `APPLIED.json`).
  Миграция раньше фронта — все открытые вкладки получают «Вышло обновление» и не
  сохраняют ничего до выкладки.
- **Откат фронта — сначала откат миграции** (вернуть прежний порог новой миграцией),
  потом откат фронта. Иначе откатанный клиент шлёт старую ревизию и сервер отказывает
  каждому сохранению.
- Ревизия — защита совместимости, а не права: подделка даёт только порчу своего
  черновика, права держат RLS и стражи.

## Конкурентная правка: `expected_updated_at`

- Клиент хранит `updated_at` заказа (чтение и каждое сохранение) и шлёт его как
  `expected_updated_at`. `order_v4_save_full` берёт строку `for update` и при расхождении
  отвечает `P0001` «Заказ изменён в другой вкладке — обновите страницу».
- Заказ НЕ в `draft` сверку пропускает: переход статуса двигает `updated_at`, и вкладка
  над отправленным заказом должна услышать стража (42501 «Заказ отправлен в работу —
  правка закрыта»), а не «изменён в другой вкладке».
- **Любое будущее RPC, меняющее заказ** (переход статуса, оплата — веха 6), обязано
  вернуть новый `updated_at`, а клиент — положить его в `current.updated_at`. Иначе
  следующее автосохранение получит ложный `conflict`.

## Состояния сохранения

- `SaveState`: `clean | dirty | saving | error | locked | outdated | conflict`. Три
  последних — **конечные**: автосохранение останавливается, повторов и потока RPC нет,
  поля закрываются, `SaveIndicator` объясняет, что делать («Обновить страницу»).
- `other` (сеть, истекшая сессия) — `error` с повтором; тост — один раз до успеха.
- `conflict` перечитывает заказ один раз (`open(id, {force:true})`): уже не `draft` —
  становится `locked`.
- Правка — только в `draft` (`model/editable.isEditable`); заказ в другом статусе
  открывается только для чтения, автосохранение не включается.
- Выход из учётной записи сбрасывает заказ, отложенное сохранение и буфер позиции
  (`registerAppReset`) — следующий пользователь в той же вкладке не увидит и не сохранит
  чужое.

## Буфер позиции

- `useStore` визарда — **буфер ОДНОЙ позиции** рабочего места. Панели визарда
  (`SkuList`, `FabricGrid`, `ColorPicker`, `SizeTable`, `ExtrasAccordion`) пишут в него,
  а `orderstudio/workplace/itemBuffer.ts` переводит правку в позицию:
  `loadItemIntoBuffer` → `bindBuffer` (подписка) → `garmentPatch(prev, next, base)` →
  `useSalesStore.edit` по ключу позиции.
- Пишется только РАЗНИЦА: поле позиции меняется, только если сменился его источник
  (модель, ткань, цвет, размеры, обработки). Загрузка позиции и перезагрузка каталогов
  ничего не пишут; модель/ткань/цвет не из каталога и ручной `main_fabric` /
  `color_supplier` переживают правку размеров.
- Смена позиции — отписка → загрузка следующей → новая подписка (`ItemTab` ключуется по
  `item.key`). Отложенная правка прежней позиции до неё не доходит.
- Позиция с несколькими цветами в буфер не грузится: плашка и «Разнести по цветам»
  (один цвет = одна позиция).
- Нанесения и бирки буфер не трогает — их правят строки `PrintRow`/`LabelRow` по ключу.
- Открытие заказа ничего не пишет; позиция появляется только по «+ Изделие»;
  «Новый заказ» открывает свой пустой черновик, если он есть.
- `SkuList reorderable={false}` (иначе перетаскивание пишет `app_config`),
  `SizeTable showPrice={false}` (цена одна — `priceOrder`). Сторож
  `workplace/workplaceSource.test.ts`: нет `app_config` и `useStore()` без селектора.

## Продавец — явный признак

- `profiles.is_sales` ставит только admin/director через RPC `sales_set_staff` (страж
  `profiles_sales_guard`), экран `/sales-staff`. `sales_is_seller()` = активный,
  одобренный, `is_sales`; роль профиля `manager` продавцом больше не делает.
- Клиентский гейт `canUseSales` (`orderstudio/layout/orderNav.ts`) — зеркало
  `sales_is_seller() or sales_is_lead()`; без него раздел ТЗ сразу уводит в
  «Производство» (`LeaveToProduction`, без петли).

## Бюджет оболочки ERP держится на разбиении чанков

- Order импортирует ERP-примитивы (`EmptyState`, `ScreenSkeleton`, `TableSkeleton`) из
  `ErpStates`/`ErpSkeletons`. Один лишний импорт заставлял Rollup вынести `ErpSkeletons`
  или `ErpStates` отдельным чанком: JS оболочки ERP рос на ~270 Б, CSS — до 16309 > 16000.
  На 17.10 запас JS — 889 Б (194111 из 195000).
- **Любой новый импорт ERP-примитива в Order — сверять с `npm run build` +
  `npm run bundle:budget`** до коммита; комментарии у импортов в `SalesList.jsx` и
  `OrderWorkplace.jsx`.
