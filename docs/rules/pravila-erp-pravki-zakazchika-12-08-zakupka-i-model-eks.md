# Правила ERP (правки заказчика 12.08: закупка и модель ЭКС)


- **Непроизводственный цех виден ТОЛЬКО на своём экране.** Все общие поверхности
  (сайдбар, канбан, вкладки очереди, план, дашборд) фильтруют цеха по
  `is_production`. Миграция `20260727210000` написала это словами
  («живут своими экранами»), и никто не проверил: раздел «Закупка» был реестром
  строк `erp_materials` и об этапах не знал вовсе, поэтому заказ с открытым
  этапом `supply` и без материалов не показывался НИГДЕ — 33 заказа стояли.
  Сторожит `routeReachable.test.ts`: цех из маршрута обязан иметь поверхность
  с его ОТКРЫТЫМИ ЭТАПАМИ, и экран непроизводственного цеха обязан читать
  этапы, а не соседние данные. Проверка «экран есть» такого дефекта не ловит —
  экран был, назывался правильно и выглядел рабочим
- Правило «закупка по заказу» живёт в `erp/utils/supply.ts` и только там:
  им пользуются бейдж оболочки, экран закупки и автозакрытие. Вторая копия
  (`maybeCloseSupply` считал открытые этапы по-своему, а экран не считал вовсе)
  и была тем, чем дефект держался
- Строка списка закупки — ЗАКАЗ, а не этап: `supply` заводится на каждую
  позицию, а материалы принадлежат заказу целиком. Закрытие закрывает все
  открытые этапы разом — так же, как автозакрытие
- Закупка закрывается и ЯВНЫМ действием, досрочно — с обязательной причиной.
  Побочный эффект внутри правки материала остался, но перестал быть
  единственным путём: у заказа без материалов он не срабатывал никогда
- **Фазы разработки не хранятся.** Верхние вкладки экрана ЭКС —
  вычисляемые состояния (`utils/experimentalTasks.devState`), хранится только
  ИСХОД (`erp_experimental.outcome`). Два источника правды («хранимый статус»
  плюс «состояние задач») разъехались бы в первую же неделю
- Задачи разработки — отдельная таблица, а не `erp_item_stages`: там
  `department_id` NOT NULL (у «лекал» и «примерки» цеха нет), `erp_stage_guard`
  требует прав `stage.*`, а `erp_warehouse_task_derive` заморозил бы отгрузку
  заказа по условию «нет этапов вне done/skipped»
- Возврат задачи из цеха — ТРИГГЕР `erp_experimental_task_sync`. Правило
  «маршрут считает клиент» не нарушено: зеркалится статус ОДНОЙ строки в ОДНУ,
  обхода `depends_on` нет. Задачу со `stage_id` клиент только ЧИТАЕТ — слайс
  снимает `status`/`blocked_reason`/`done_on` перед записью, а доска не рисует
  кнопки статуса. Сторож едет вместе с писателем: без клиентского кода он
  проверял бы пустоту
- Цикл доработки — НОВАЯ строка задачи, а не счётчик: у каждого круга свои
  ответственный, срок, комментарий и результат. Номер круга считает сервер
  по ТИПУ задачи
- Гейт отгрузки и приёмка ГП по этапам образца НЕ ослабляются: открытый этап
  означает незакрытую работу, а ослабленный гейт отпустил бы образец
  недоделанным. Заброшенный цикл закрывается «Пропустить этап». А вот из
  ПРОГРЕССА (`itemProgress`) этапы образца убраны — иначе маршрут из четырёх
  этапов с одним заходом образца показывал бы 80 % при закрытой работе
- Старая модель убирается ОТДЕЛЬНЫМ коммитом ПОСЛЕ выкладки нового экрана:
  порядок «миграция → прод → фронтенд» означает окно, в котором старый бандл
  ещё читает `phase` и `erp_experimental_ops`
- **Удаляя объект БД, ищите его в ТЕЛАХ ФУНКЦИЙ, а не только в коде.** Дроп
  `erp_experimental_ops` прошёл проверку `grep` по исходникам — слайс, тип
  и подписка realtime были убраны, всё выглядело чистым. Но таблицу подтягивала
  `erp_bootstrap()`, а её последнее определение лежит в миграции от 03.08:
  в изменённых файлах упоминания не было вовсе. Пакет оболочки собирается при
  КАЖДОЙ загрузке, поэтому весь раздел «Производство» ответил 42P01 — ни меню,
  ни прав, ни справочников. Ловится одним запросом (`pg_get_functiondef` по всем
  функциям схемы) и сторожем `droppedObjects.test.ts`, который берёт ПОСЛЕДНЕЕ
  определение каждой функции и сверяет с тем, что дропнуто позже
- **Вид справочника живёт в ЧЕТЫРЁХ местах** — CHECK базы, `DictionaryKind`,
  подпись с подсказкой и `KINDS` в `DictionariesTab`. Пропуск последнего
  ничего не роняет: он даёт молчаливо отсутствующую вкладку. Так справочник
  единиц измерения не редактировался из админки ВООБЩЕ, хотя выглядел сделанным.
  Сторожит `dictionaryKinds.test.ts`
- **RLS на UPDATE запрещает через `USING`, то есть «обновлено 0 строк»,
  а не 42501.** Исключение бросает только `WITH CHECK`. Проверка гейта,
  ожидающая ошибку, даёт ложную тревогу — сверять надо `row_count`
  и значение в базе
- **RLS на DELETE запрещает через `USING` — это «удалено 0 строк», а не 42501**
  (то же правило, что для UPDATE). Клиент, проверяющий только `error`, показывал
  зелёное «Заказ удалён» и убирал заказ из списка, а тот возвращался при
  следующей загрузке. Удаление идёт с `.select()`, и пустой ответ — отказ
- **Файлы удаляются вместе со строкой, которая на них ссылается.** Пути
  собираются ДО удаления (`erp_tz_documents` и `erp_order_attachments` уедут
  каскадом), файлы убираются ПОСЛЕ: обратный порядок оставил бы живой заказ
  без ТЗ, если DELETE не прошёл. Без этого бакет копит платные файлы, которые
  никому не принадлежат и, пока он публичный, доступны по ссылке
- **Гейт кнопки сверяется с политикой ЗНАЧЕНИЕМ, а не на слух.** `isPrivileged`
  это `FULL_ACCESS_PROFILE_ROLES` = admin + director + РОП, а `is_admin()` —
  только admin; между ними и жило расхождение, подписанное комментарием «ровно
  как на сервере». Для admin-only гейтов есть `access.isAdmin` — дословное
  зеркало. Сторож, проверяющий подстроку, которая встречается в файле дважды
  (`access.isPrivileged && (` — и фильтр списка, и пометка «тестовый»),
  зелёный независимо от того, что чинит: привязывайтесь к полному выражению
- **Перечисление по именам не переживает следующего имени.** Триггерные функции
  закрывались для REST списком из двенадцати штук (`20260803250000`), и
  тринадцатая — `erp_experimental_task_sync` — осталась единственной вызываемой
  через `/rest/v1/rpc/…`. Дыры не было (Postgres сам отклоняет прямой вызов
  триггерной функции), но постоянно висящее предупреждение адвизора — это шум,
  за которым теряется настоящее. Отзыв переписан ОБХОДОМ по `prorettype =
  'trigger'`, и он же объясняет, почему предикаты RLS не задеты: они возвращают
  `boolean`. Сторожит `triggerFunctionsRevoked.test.ts` — обход закрывает то,
  что есть СЕЙЧАС, а у функции, заведённой позже, обязан быть свой `revoke`
- `constructor` как имя колонки сталкивается с `Object.prototype.constructor`:
  TypeScript не принимает объектный литерал ни в `Partial`, ни в `Omit`
  с обратным добавлением. Поле приходит под именем `constructorName`,
  слайс перекладывает его в колонку
