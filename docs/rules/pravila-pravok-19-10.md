# Правила правок 19.10 (план A — производство)

Документ владельца «правки 19.10» (снимок — `docs/erp/2026-10-19-pravki-19-10.md`), план
`docs/superpowers/plans/2026-10-19-erp-edits-19-10-a-production.md` (решения Р1–Р11). Здесь — правила,
которые из них следуют и которые легко нарушить следующей правкой. Выкатка и откаты —
`supabase/rollout/r1910a/README.md`.

## Вышивка — одна задача, две фазы (E1 `20261019100000`)

- **Строка вышивки одна; фаза — `result_kind`.** `'embroidery_program'` — «Разработка программы
  вышивки», `null` — «Вышивка». Вторую строку маршрут больше не заводит (`routes.ts`, поле `standalone`
  удалено). Переход фазы — ТОЛЬКО две RPC: `erp_embroidery_program_finish` («Программа готова»: строка
  `in_progress`, право `stage.progress` и цех, файл программы в `erp_order_attachments` этого заказа И объект
  в бакете) и `erp_embroidery_program_skip` («Без программы», `order.manage`, причина обязательна).
  Прямую смену `result_kind` страж этапов пропускает только с `order.manage`; метка `erp.program_finish`
  пропускает ровно переход фазы (снимок исключений, `qty_done = 0`, `waiting`).
- **Фаза есть только у одиночной строки** (Р1): у позиции нет другой строки цеха `embroidery`
  с `result_kind is null`; закрытая программа — наследие. Зеркала: сервер `erp_embroidery_is_phased`,
  клиент `utils/embroideryPhase.isProgramPhase(stage, siblings)` — siblings обязательны. Старые пары
  «программа + вышивка» живут по `erp_stage_program_block` / `embroideryProgramBlock`; удалить их —
  когда запрос «наследия» из README выкатки вернёт 0.
- **Фаза программы не ждёт ни маршрута, ни материалов и непрозрачна** (Р2, Р3): количество дальше не
  пропускает (`erp_stage_passthrough`), в выпуск не идёт (`erp_item_produced_qty`; иначе при вышивке
  последним этапом склад примет тираж до вышивки), `done`/`skipped`/штуки запрещены — и под
  `erp.force_complete` (триггер `erp_item_stages_dep_gate`, гейт `erp_stage_completion_block`,
  клиент `stageGates.programPhaseBlock`). Фаза вышивки ждёт существующие `depends_on`.
- Приёмка от подрядчика (`erp.subcontract_rollup`) превращает строку в фазе программы в «Вышивку»
  без события этапа — так задумано (находка ревизии A1, Minor).
- Плановые даты строки — даты вышивки; факт фазы программы — из `erp_stage_events` (Р4).
- Тексты и id для экранов (`PROGRAM_PHASE_BLOCK`, `stageHeadingId`) — `utils/embroideryPhaseText.ts`, НЕ
  в `embroideryPhase.ts`: тот читают `routes` и `outsourcing`, и всё в нём попадает в оболочку ERP
  (`bundle:budget`).

## Закрой — выпуск один раз, расход по рулонам (C1 `20261019110000`)

- **Выпуск вводится один раз** («Результат кроя», `CutResultTable`) — строки `erp_stage_report_sizes`
  с `report_roll_id = null`; **расход** («Расход ткани», `CutUsageSection`) — `erp_stage_report_rolls` без
  размеров: «Не использован» / «Полностью» / «Частично» (остаток «пригоден» или «малый, не учитывать»).
  Два материала позиции выпуск не умножают. Модель — чистые функции `utils/cutUsage.ts`
  (примеры документа — `cutUsage.examples.ts`, общие с пробой).
- **Старые отчёты не переписываются**: формат «размеры на рулоне» сервер читает по-старому.
- **Средний расход — по материалу** (Р6): знаменатель — годные строки сдачи того же цвета (без регистра,
  пробелов, «ё/е» — `erp_color_key`), нет совпадений — все годные позиции («по всей позиции»); по заказу —
  Σ метров / Σ годных, не среднее средних. Риск задвоения у позиции с двумя основными материалами
  без совпадения цвета — известен (ревизия A5).
- **Брак, переделка и плюс без рулонов** — поле за полем: строки `p_sizes` несут ключ → сумма строк,
  иначе скаляр `p_qty_*` (зеркало `reportTotals.fromSizes`).
- Рулон блокируется `for update`, повтор `roll_id` → `22023`, `material_id` берётся из рулона.
  **У `erp_material_rolls` есть страж** (`erp_material_roll_guard`, Р11): метраж и статус — только под
  `erp.roll_adjust`, `erp.cut_submit` или с `warehouse.manage`.
- Сдача с выпуском без отмеченного рулона — подтверждение «Сдать без списания ткани?», не блок (Р7);
  позиция без рулонов вовсе — без блока. Рулон без метража блокирует «Полностью» (`METRES_MISSING_TEXT`).
- Откат C1 — только `erp_stage_submit_report`; читатели и страж остаются новыми.

## Вложения 30 МБ и техпаспорт (S1 `20261019090000`)

- **30 МБ = `31457280` одной величиной**: бакет `erp-attachments`, `ATTACH_MAX_BYTES`, `TZ_MAX_BYTES`
  и писатели Order (`erpFiles.ts`, `sendChecklist.ts`, `launchFiles.ts`, мок бакета e2e) — сторож
  `attachmentLimits.test.ts` («писатели Order не мягче бакета»). Подпись у загрузки — ровно «До 30 МБ на
  один файл» (`utils/fileLimitText.ts`). Глобальный лимит Storage проекта — предусловие выкатки.
- «Готово к серии» не требует технического паспорта (страж `erp_dev_package_guard` — фото и лекала);
  в интерфейсе — «Технический паспорт · необязательно».

## ТЗ пачкой, закупка

- ТЗ в форме создания и в карточке грузится **пачкой**: строка на файл, один сводный `role="status"`,
  большой файл — строка с причиной без повтора, сбой — «Загрузить заново: <имя>» только у него;
  замена файла — одиночная (`EditableFiles`, `useTzDocs.addTzDocs(files, itemIndex)`).
- **Приёмка — только на складе** (Р8): «Принять поставку» / «Открыть приёмку» из закупки убраны вместе
  с возвратом «← К закупке» (`ReceiptButton`, `purchasingReturnHref`, `fromPurchasing` удалены).

## Интерфейс

- **Блок по условию в ERP — `Button ariaDisabledReason`**: `aria-disabled`, клик заглушён, причина видимым
  текстом и `aria-describedby`; `disabled` — только на время запроса (`loading`), без причины. Ручной
  `aria-disabled` у `Button` не писать (форма закроя переведена при сборке).
- `Button` лежит в оболочке ERP: любой рост примитива — рост бюджета оболочки (на 19.10 оболочка 195 057 Б gzip,
  потолок поднят до 196 000 решением Р6; запас ≤ 1 000 Б — под «Бизнес-задачи»).
