# Правила ERP (документ 20.08, сессия 33 — сверка)


- **Половина требования выглядит как сделанное требование.** Построчная сверка
  документа с кодом нашла четыре пункта одного класса: поле пишется в базу,
  но нигде не читается (ответственный подряда, план передачи, комментарий);
  схема заведена, а точки ввода нет (`ТЗ / файлы` этапа); величина считается
  на доске, но не в карточке (статус материалов ЭКС). Тесты этого не ловят,
  когда проверяют НАЛИЧИЕ ИМЁН полей в тексте функции, а не путь от ввода
  до показа. Сторож обязан проверять механизм: «файл, выбранный в форме,
  оказался привязан к тому этапу»
- **Файл, привязанный к строке, которой ещё нет, адресуется ИНДЕКСОМ.**
  У листа закупки это `material_index`, у подрядного этапа — `stage_index`
  (номер этапа ВНУТРИ позиции; ключ составной, потому что `v_stage_ids`
  обнуляется на каждой позиции). Номер проставляет ТОТ ЖЕ код, который строит
  секцию `stages`, — иначе рядом заводится второй порядок этапов
- **`pg_get_functiondef` отдаёт ЗАГЛАВНЫЙ заголовок и `$function$`.**
  Скопированный дословно, он молча уводит сторожевые тесты на предыдущую
  миграцию (`latestDefining` ищет `create or replace function public.<имя>(`,
  `functionBody` разбирает тело между `$$`): сторож зелен и проверяет не ту
  функцию, которая работает. Приводить к виду миграций проекта обязательно
- **`erp_order_attachments.stage_id`** + вид `subcontract` — файлы подрядного
  этапа. Не `tech` у позиции (адресат другой, и подрядных этапов бывает
  несколько) и не `erp_tz_documents` (по ним считается гейт ТЗ, и файл
  подрядчику открыл бы цехам работу без техзадания)
- **«Подряд» больше не тип производства.** Плитка `outsource` убрана из формы
  создания: две точки ввода одного решения означают, что маршрут считается
  по частному правилу `material_source`, а не по исполнителю шага. Значение
  остаётся в схеме и подписях — его несут заведённые раньше заказы
