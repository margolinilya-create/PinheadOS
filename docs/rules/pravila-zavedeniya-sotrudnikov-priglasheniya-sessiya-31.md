# Правила заведения сотрудников (приглашения, сессия 31)


- **Основной путь — приглашение ссылкой** (`erp_invites`): админ выбирает роль
  и цех, получает готовую ссылку `/join?code=…` и отдаёт её человеку САМ.
  Писем в этом пути нет вовсе — а прежний порядок вставал именно на них
  (встроенный SMTP Supabase: ~2 письма в час, у gmail спам). Самостоятельная
  регистрация осталась ЗАПАСНЫМ путём: заявка, роль `pending` без прав,
  одобрение админом
- **Код проверяет и гасит ТОЛЬКО сервер** — `handle_new_user`. Клиент кладёт код
  в `options.data.invite_code`, то есть присылает его сам и может прислать что
  угодно. Гашение — ОДИН `update … returning` по сроку, отзыву и адресу: двое,
  открывшие одну ссылку одновременно, не могут оба получить права, а отдельные
  SELECT и UPDATE такого не гарантируют
- **Нечитаемый код не имеет права ронять регистрацию.** Триггер исполняется
  внутри вставки в `auth.users`; необработанное исключение даёт «Database error
  saving new user» ВСЕМ, включая тех, кто про приглашения не знает. Отсюда
  `exception when invalid_text_representation`
- **Приглашение показывает функция `erp_invite_preview`, а не выборка.** Человек
  ещё не вошёл, а RLS не видит фильтр запроса: политика `for select to anon`
  открыла бы всю таблицу приглашений вместо одной строки
- **Право `staff.invite`, а не роль учётной записи.** Приглашение раздаёт права,
  и гейт обязан совпадать с сервером ЗНАЧЕНИЕМ: `isPrivileged` это
  admin + director + РОП, `is_admin()` — только admin, и на этом расхождении
  в проекте уже ловились
- **Роль `pending` — единственная без единого права** (у `hr` тоже ноль, но это
  должность, а не состояние). Её ставит триггер каждому, кто пришёл без
  приглашения. Без строки в `erp_employees` `erp_role_of_caller()` выводит роль
  из профиля и делает новичка МЕНЕДЖЕРОМ: правка любого заказа, ТЗ, перенос
  этапов — причём по всей фабрике, потому что ограничение по цеху на человека
  без цеха не действует (`canActInDept` там fail-open, и это осознанно)
- **Колонка `pending` в матрице прав не редактируется** (`LOCKED_ROLES` рядом
  с `director`): одна галочка раздала бы право всем неназначенным разом.
  Права выдаются назначением должности, а не правкой этой колонки
- **Приглашения требуют выключенного «Confirm email».** Иначе `signUp` не отдаёт
  сессию, и приглашённый упирается в экран подтверждения адреса — ровно
  в то, ради чего приглашения и заводились
- Отзыв — `revoked_at`, не DELETE: журнал «кто, кого и куда звал» и есть
  половина смысла таблицы. Отзыв идёт с `.select()` — RLS на UPDATE запрещает
  через `USING`, то есть отдаёт «0 строк», а не ошибку
