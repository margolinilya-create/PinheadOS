# Правила обзора проекта 24.09 (сессия 67)

Обзор всего репозитория по просьбе владельца; отчёт —
`docs/2026-09-24-project-review.md`. Здесь — правила, которые из него следуют.

---

## Носители ключа в бакете выводятся из схемы, а не перечисляются

`storage-gc` удаляет объект, чей ключ не встречается ни в одном носителе,
и список носителей у него рукописный. 15.09 появился третий —
`erp_sku_card_files.file_path`, снимок ключа вложения разработки, — а в список
он не попал: комментарий «состав закрыт проверкой 13.09» был верен на дату
и молча устарел. Девять дней техпакет модели считался ничьим.

Это тот же класс дыры, что поимённый список колонок в `erp_order_guard`
(сессия 66): перечисление отстаёт от схемы без единого красного теста.
Поэтому сторож `erp/utils/storageGc.test.ts` читает миграции и требует, чтобы
КАЖДАЯ таблица с колонкой `file_path` стояла в `REFERENCES`. Сторож, проверяющий
известные имена, здесь бесполезен: он зелен ровно до появления неизвестного.

## Удаление объекта на клиенте спрашивает второго носителя

Три места убирают объект бакета по пути — удаление заказа, файла разработки
и вложения заказа. Каждое идёт через `freeOfSkuCards` (`store/shared.ts`):
строка карточки переживает удаление вложения (`attachment_id … on delete
set null`), и объект обязан пережить его тоже.

**Ошибка проверки = не удалять.** Удаление необратимо, сирота стоит копейки
и убирается уборщиком, который те же носители знает сам. Неверный ответ
опаснее отсутствия ответа — поэтому при ошибке чтения `freeOfSkuCards`
возвращает пустой список, а не «всё можно».

**Проверка держится на RLS `sku.view`.** Роль без этого права получила бы
пустой ответ и удалила бы объект как ничей. Сторож в том же тесте требует:
всякая роль с `files.manage` или `experimental.manage` в `DEFAULT_PERMISSIONS`
имеет `sku.view`. Матрица правится в админке — сторожатся дефолты как зеркало seed.

## Документ-память — не источник истины о базе

Три утверждения разведки не прошли сверку с живым источником, и все три
повторяли записи из `SESSION-STATE.md`: «миграции 24.09 не применены»
(журнал прода: применены), «бэкап падал 5 из 5» (Actions: 57 из 57),
«Supabase Preview красный на `main`» (PR #176 прошёл зелёным). Правило то же,
что записано днём раньше: перед выводом о системе — живой источник, а не
прошлая формулировка. Добавление: запись в памяти, описывающая состояние
«до», обязана быть исправлена в момент «после» — иначе она становится
инструкцией сделать то, что уже сделано.

## Надстройка над Claude Code оценивается по факту использования

claude-flow / ruflo стоял в проекте с сессии 15: MCP-сервер, 44 vendored-файла,
хуки на каждое событие, самообновление с коммитами ±3502 строк. Применён
один раз. MCP не поднимался ни в 53-й, ни в 67-й сессии, а роутер отвечал
«Agent: coder, confidence 30%» на каждый запрос. Снят из `.mcp.json`
и `settings.json`; файлы удаляет владелец.

Правило: инструмент, который не поднялся две сессии подряд и не был
применён по назначению, — не «на всякий случай», а стоимость на каждом
запросе. У сильной модели главный рычаг — чистый контекст и точные правила.

## `settings.json` не разрешает запись в бой заранее

Прежний allow-list содержал `apply_migration`, `execute_sql`,
`deploy_edge_function` — запись в боевую базу без подтверждения — рядом
с путями чужой машины и разовыми `git commit -m '…'`. Переписан: чтение
Supabase и GitHub разрешено, запись спрашивает каждый раз. Правило проекта
«миграции применяются до мержа» не отменяется — но каждое применение
остаётся явным решением.
