# Правила проверки прав на живой базе (21.08, после разбора)


Готовый каркас — `docs/erp/permission-check.sql`: берите файл целиком и меняйте
только блок «что проверяем». Правило, которое надо помнить, забывается; шаблон —
нет. Ниже — почему он устроен именно так.

- **Проверка прав без `set local role authenticated` не проверяет НИЧЕГО.**
  `set_config('request.jwt.claims', …)` подменяет только личность
  (`auth.uid()`), а RLS не применяется к владельцу таблицы вовсе — блок
  исполняется от `postgres`, и любое действие «проходит». Такая проверка
  ОПАСНЕЕ отсутствующей: она выдаёт зелёный результат на непроверенном месте.
  Порядок один: `set_config(claims)` → `set local role authenticated` →
  действие → `reset role`
- **Роль для проверки заводится, а не подбирается.** В `erp_employees` живут
  три человека (директор и два менеджера), и «проверить от лица кладовщика»
  на боевых данных нечем. `profiles` не связан с `auth.users` внешним ключом,
  поэтому временный сотрудник заводится прямо в транзакции с откатом —
  профиль плюс строка `erp_employees` с нужной ролью
- **Выборка из `erp_role_permissions` без `allowed` читается наоборот.**
  Таблица хранит строку на КАЖДУЮ пару «роль × право», в том числе со
  значением `false`: запрос без фильтра показывает у рабочего все шестнадцать
  прав. Один раз это уже заставило меня решить, что у `worker` есть
  `order.manage`
- **Право проверяется ПО ВСЕЙ ЦЕПОЧКЕ, а не в одной точке.** RLS журнала
  подряда расширили до `warehouse.manage`, и приёмка всё равно падала: строку
  журнала кладовщик вставлял, а триггер `erp_subcontract_moves_rollup` менял
  `qty_done` подрядного этапа, и `erp_stage_guard` отклонял транзакцию —
  у `storekeeper` нет НИ ОДНОГО права `stage.*`. Пропуск сделан меткой
  транзакции `erp.subcontract_rollup` (как `erp.moving` у переноса цеха):
  метку ставит и снимает сам rollup ВОКРУГ своего update, страж принимает её
  только для подрядного этапа и только у того, кто вправе писать журнал
