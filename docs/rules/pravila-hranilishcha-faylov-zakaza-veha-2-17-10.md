# Правила хранилища файлов заказа v4 (веха 2, 17.10)

Закрытый бакет `order-artworks` (миграция `20261017070826_order_artworks_bucket`,
применена на бою 17.10: сухой прогон проб `fails=0 total=67`; пробы — `supabase/probes/order_artworks.sql`)
и клиент `pinhead-react/src/orderstudio/api/artworks.ts`. Здесь — правила,
которые обязаны соблюдать экраны вехи 3 (загрузка и показ макетов, ТЗ в PDF,
бирок, стикеров) и любая будущая миграция Storage.

---

## SVG: показ — только `<img>`, новая вкладка — только скачивание

Бакет принимает `image/svg+xml`, а SVG — это документ, который может нести
`<script>`. Подписанная ссылка ведёт на домен Supabase Storage; открытая
НАПРЯМУЮ (новая вкладка, `<a href target="_blank">`, `<iframe>`, `<object>`,
`<embed>`) она отрисует SVG как документ, и скрипт выполнится в origin
Storage — это stored XSS на домене, где лежат ВСЕ наши файлы.

- **Превью** — только `<img src={await artworkSignedUrl(path)}>`. В `<img>`
  браузер скрипты SVG не исполняет.
- **«Открыть в новой вкладке» / «Скачать»** — только `artworkDownloadUrl(path)`:
  `createSignedUrl(path, 600, { download: true })`, supabase-js дописывает
  к ссылке `&download=`, Storage отвечает `Content-Disposition: attachment`,
  и браузер файл сохраняет, а не рисует. Касается ЛЮБОГО типа, не только SVG:
  экрану незачем помнить, какой формат опасен.
- `<iframe>`, `<object>`, `<embed>` и `innerHTML` со ссылкой бакета —
  запрещены.

## Формат определяет расширение, а не браузер

supabase-js грузит File через FormData, и Storage берёт тип из части формы,
то есть из `File.type`; опцию `contentType` для File он не смотрит. У .ai,
.eps, .ps, .psd, .tif тип браузера зависит от ОС и бывает пустым, а пустой
уходит как `application/octet-stream`, которого бакет не принимает (и не
должен: иначе он принимает что угодно). Поэтому `artworkContentType` берёт
тип по расширению и пересобирает Blob. Новый формат добавляется в ТРИ места
сразу: `allowed_mime_types` бакета (новой миграцией, если C уже на бою),
`ARTWORK_MIME_TYPES` + `TYPE_BY_EXT` клиента и `ARTWORK_FORMATS_HINT` тоста.
Сторож `orderArtworksBucket.test.ts` держит равенство списков бакета и клиента.
Состав на 17.10 (решение владельца): PNG, JPG/JPEG, WEBP, SVG, PDF, AI, EPS,
PS, PSD, TIF/TIFF. Подсказка тоста — ровно эти расширения (тест в обе стороны). CorelDRAW (.cdr) — не принят, вопрос открыт.

## Удаление: «уже нет» решает вызывающий

На `remove` объекта, которого нет, и объекта, который RLS не дал удалить,
Storage отвечает одинаково: пустым списком без ошибки. По ответу их не
различить. По умолчанию `removeArtwork(path)` считает пустой ответ отказом
(тост, `null`). Экран, который всё равно убирает путь из заказа (удалили
позицию, заменили файл), зовёт `removeArtwork(path, { missingOk: true })`
и получает `'missing'` без тоста. Отказ RLS при этом не теряется: у
сохранения заказа то же условие (черновик, автор или руководство).

## UPDATE в `order-artworks` запрещён всем — restrictive-политикой

Политики `storage.objects` permissive складываются через OR — и по USING
(какую строку можно взять), и по WITH CHECK (какой она станет). Сухой
прогон проб на бою 17.10 показал: с permissive `order_artworks_update`
автор переносил (`move` = `update … set bucket_id, name`) СВОЙ файл
черновика в `erp-attachments` и в ПУБЛИЧНЫЙ `sku-photos`: USING нашей
политики брал старую строку, WITH CHECK `erp_att_update` / `sku_photos_update`
(`owner = uid`) пропускал новую. Это новая возможность, а не «скачать и
загрузить»: перенос идёт мимо лимитов типа и размера бакета-получателя
(SVG или PDF — в публичный бакет картинок).

Поэтому:
- permissive-политики UPDATE на `order-artworks` нет и не заводится;
- `order_artworks_no_update` — `as restrictive for update to authenticated
  using (bucket_id <> 'order-artworks') with check (bucket_id <> 'order-artworks')`.
  Restrictive складывается через AND с КАЖДОЙ permissive: строку бакета не
  взять на UPDATE (перезапись, вынос) и не сделать ею строку другого бакета
  (внос) — никому, включая владельца и руководство, и против любой будущей
  широкой permissive (локальная проба с `update … using (true)`);
- клиенту UPDATE не нужен: загрузка `upsert: false` (INSERT), новый файл —
  новый ключ, замена — новая загрузка и удаление старого; `move` не зовём.
- Политики ERP не трогаются (заморожены).

`copy` — это INSERT. Внутрь `order-artworks` его судит наша политика записи
(путь заказа, черновик, автор или руководство). Наружу — политика
бакета-получателя: МС, которому виден отправленный заказ, как член ERP
может скопировать файл в публичный `erp-attachments` (`erp_att_upload`).
Это «прочитал — опубликовал», которое у читающего есть и так (скачать
и загрузить), а лимитов `erp-attachments` не обходит — их там нет. Записано
и проверено пробой (`ms_copy_out`), не закрывается.

**Блокировка строки под ролью пользователя = «не найдено».** `SELECT …
FOR UPDATE` под ролью пользователя применяет USING политик UPDATE, и строк
`order-artworks` он не видит (проба `s_for_update` → 0). Так было бы и без
restrictive: permissive update у бакета нет. Значит, если какой-то путь
storage-api блокирует строку под ролью пользователя, он ответит «не найдено».

**Дымовой прогон на бою после применения C — обязателен** (отложен до вехи 3:
экрана загрузки до неё нет, прогон — вместе с первым экраном, задача владельца). Менеджер на своём
черновике: upload → подписанная ссылка (`artworkSignedUrl`) и ссылка на
скачивание (`artworkDownloadUrl`) → remove. Параллельно смотреть логи storage
и postgres. Откат — `drop policy "order_artworks_no_update" on storage.objects`:
он безопасен (restrictive только сужает). Но если не работает remove, причина
в отсутствии permissive update (см. абзац выше), а не в restrictive, — тогда
это решается отдельно, откат restrictive не поможет.

**Копия ВНУТРЬ своего черновика из `erp-attachments` обходит MIME и размер
бакета** — известно и отложено, риск Low: бакет приватный, SVG открывается
только скачиванием, у Storage отдельный origin. Вариант закрытия на потом —
restrictive INSERT по `metadata->>'mimetype'` и размеру, с пропуском
`metadata is null` для пробной вставки. До этого на бою надо проверить
порядок вставки storage-api (когда заполняется `metadata`).

Локальная заглушка Storage для проб обязана нести ВСЕ живые политики
`storage.objects` (читать из `pg_policies` боя): без `erp_att_update`
локальный прогон не увидел того, что увидел бой.

## Любая политика `storage.objects` — с фильтром по бакету

Политика `storage.objects` без `bucket_id = '<литерал>'` первым конъюнктом
действует на ВСЕ бакеты, включая закрытый `order-artworks`. Сторож
`orderArtworksBucket.test.ts` находит каждую `create policy … on storage.objects`
во всех миграциях свободной регуляркой (имя в кавычках с пробелами,
`"storage"."objects"` — тоже; её сверяет грубый независимый счётчик) и требует, чтобы строгий разборщик
распознал каждую (иначе непривычно написанная политика прошла бы мимо),
а каждое тело USING и WITH CHECK permissive-политики было ограничено одним
бакетом (restrictive только сужает, ей фильтр не обязателен): первый
конъюнкт — `bucket_id = '…'`, на верхнем уровне нет `or`. `alter policy`
по `storage.objects` запрещён — его тело мимо проверки. Исключение для
старой политики — только в `BUCKET_EXCEPTIONS` с причиной.
