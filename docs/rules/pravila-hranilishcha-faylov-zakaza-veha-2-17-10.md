# Правила хранилища файлов заказа v4 (веха 2, 17.10)

Закрытый бакет `order-artworks` (миграция `20261017070826_order_artworks_bucket`)
и клиент `pinhead-react/src/orderstudio/api/artworks.ts`. Здесь — правила,
которые обязаны соблюдать экраны вехи 3 (загрузка и показ макетов, ТЗ в PDF,
бирок, стикеров) и любая будущая миграция Storage.

---

## SVG: показ — только `<img>`, новая вкладка — только скачивание

Бакет принимает `image/svg+xml`, а SVG — это документ, который может нести
`<script>`. Подписанная ссылка ведёт на домен Supabase Storage; открытая
НАПРЯМУЮ (новая вкладка, `<a href target="_blank">`, `<iframe>`, `<object>`,
`<embed>`) она отрисует SVG как документ, и скрипт выполнится в origin
Storage — это stored XSS на домене, где лежат ВСЕ наши файлы.

- **Превью** — только `<img src={await artworkSignedUrl(path)}>`. В `<img>`
  браузер скрипты SVG не исполняет.
- **«Открыть в новой вкладке» / «Скачать»** — только `artworkDownloadUrl(path)`:
  `createSignedUrl(path, 600, { download: true })`, supabase-js дописывает
  к ссылке `&download=`, Storage отвечает `Content-Disposition: attachment`,
  и браузер файл сохраняет, а не рисует. Касается ЛЮБОГО типа, не только SVG:
  экрану незачем помнить, какой формат опасен.
- `<iframe>`, `<object>`, `<embed>` и `innerHTML` со ссылкой бакета —
  запрещены.

## Формат определяет расширение, а не браузер

supabase-js грузит File через FormData, и Storage берёт тип из части формы,
то есть из `File.type`; опцию `contentType` для File он не смотрит. У .ai,
.eps, .ps, .psd, .tif тип браузера зависит от ОС и бывает пустым, а пустой
уходит как `application/octet-stream`, которого бакет не принимает (и не
должен: иначе он принимает что угодно). Поэтому `artworkContentType` берёт
тип по расширению и пересобирает Blob. Новый формат добавляется в ТРИ места
сразу: `allowed_mime_types` бакета (новой миграцией, если C уже на бою),
`ARTWORK_MIME_TYPES` + `TYPE_BY_EXT` клиента и `ARTWORK_FORMATS_HINT` тоста.
Сторож `orderArtworksBucket.test.ts` держит равенство списков бакета и клиента.
Состав на 17.10 (решение владельца): PNG, JPG, WEBP, SVG, PDF, AI, EPS, PS,
PSD, TIFF. CorelDRAW (.cdr) — не принят, вопрос открыт.

## Удаление: «уже нет» решает вызывающий

На `remove` объекта, которого нет, и объекта, который RLS не дал удалить,
Storage отвечает одинаково: пустым списком без ошибки. По ответу их не
различить. По умолчанию `removeArtwork(path)` считает пустой ответ отказом
(тост, `null`). Экран, который всё равно убирает путь из заказа (удалили
позицию, заменили файл), зовёт `removeArtwork(path, { missingOk: true })`
и получает `'missing'` без тоста. Отказ RLS при этом не теряется: у
сохранения заказа то же условие (черновик, автор или руководство).

## Любая политика `storage.objects` — с фильтром по бакету

Политика `storage.objects` без `bucket_id = '<литерал>'` первым конъюнктом
действует на ВСЕ бакеты, включая закрытый `order-artworks`. Сторож
`orderArtworksBucket.test.ts` находит каждую `create policy … on storage.objects`
во всех миграциях свободной регуляркой и требует, чтобы строгий разборщик
распознал каждую (иначе непривычно написанная политика прошла бы мимо),
а каждое тело USING и WITH CHECK было ограничено одним бакетом: первый
конъюнкт — `bucket_id = '…'`, на верхнем уровне нет `or`. `alter policy`
по `storage.objects` запрещён — его тело мимо проверки. Исключение для
старой политики — только в `BUCKET_EXCEPTIONS` с причиной.
