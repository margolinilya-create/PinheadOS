## Номер заказа: одна последовательность, один формат

`generate_order_number` читает `order_number_seq`, ту же, что и умолчание
колонки `orders.order_number` из базовой схемы. Вторая последовательность
завела бы два независимых счётчика одного номера: путь через RPC и путь
через умолчание раздали бы одинаковые `PH-0019`.

**`lpad` обрезает.** `lpad(x, 4, '0')` режет строку длиннее четырёх знаков:
10000-й заказ получил бы `PH-1000`, а 12345-й и 123456-й — оба `PH-1234`.
Так было в умолчании колонки с самого начала, и никто не видел:
последовательность на 24.09 дошла только до 18.
Ширина обязана расти с числом: `lpad(n::text, greatest(4, length(n::text)), '0')`.

Формат живёт в ОДНОМ месте: умолчание колонки зовёт функцию, а не держит
свою копию выражения. Две копии уже разошлись однажды — обрезкой.
Сторож — `src/store/orderNumber.test.ts`, проверен мутацией (обрезка,
вторая последовательность, умолчание без функции, неотозванный anon).

## Проверка RPC на бою без расхода последовательности

Функцию, которая зовёт `nextval`, нельзя «попробовать» в откатываемой
транзакции: последовательность не откатывается, и номер сгорит. Проверка
без побочного эффекта — вызов через REST ПОД `anon`, у которого исполнения нет:

- `42501 permission denied for function …` — функция в кэше схемы PostgREST,
  и анонимный вызов номер не тратит (право проверяется до исполнения);
- `PGRST202 … not found in the schema cache` — функции для REST нет.

Остальное — `has_function_privilege`, `has_sequence_privilege`, `prosecdef`,
умолчание колонки — читается из каталога, тоже без вызова.

## Классификация веток требует ПОЛНОЙ истории

Облачная сессия клонирует репозиторий на глубину 50 коммитов.
В таком клоне `git merge-base --is-ancestor` отвечает «не предок» почти
на всё: `main` обрывается 08.09, и старые ветки не находят с ним общего
предка. Первая сверка этой сессии насчитала 39 «несмерженных» веток там,
где их по полной истории 23. Перед любой классификацией —
`git rev-parse --is-shallow-repository` и `git fetch --unshallow`.

Сквош-мерж оставляет ветку «несмерженной» и в полной истории. Такую ветку
подтверждает не предок, а PR: голова ветки обязана совпасть с головой
последнего смерженного PR этой ветки. Коммит после мержа — это работа,
которой в `main` нет.

**Числа отчёта сверяются суммой.** В отчёте 67 стояло «смержены — 63»,
а список на удаление держал 67 веток: 21 под тег + 4 с открытым PR + 42
смерженных. Три слагаемых, не дающих итога, — признак, что одно из них
посчитано по другому снимку.

## Git-прокси сессии и GitHub-интеграция — границы, а не помехи

- Пуш тегов и удаление чужих веток отвечают **403 политикой организации**
  (`recentRelayFailures` пуст — это не обрыв). Не обходить: ни токеном
  из окружения, ни REST в обход прокси. Уборка веток — локально у владельца,
  команда в отчёте 67.
- Если теги не легли, удаление НЕ начинается: теги — страховка ровно тех
  21 ветки, у которых нет PR.
- `actions_run_trigger` → **403 Resource not accessible by integration**:
  у интеграции нет `actions: write`. Ручной прогон workflow делает владелец
  (Actions → Run workflow) или ночной cron.

## Выгрузка данных в CI — только после проверки видимости репозитория

Репозиторий `PinheadOS` ПУБЛИЧНЫЙ (`private: false`, сверка 24.09), а логи
и артефакты прогонов публичного репозитория видны всем: артефакт скачивает
любой вошедший на GitHub. `storage-backup.yml` писался в предположении
приватности: он печатает в лог путь каждого объекта (а бакеты `public` —
путь и есть ссылка на файл) и кладёт архив ВСЕХ файлов в артефакты на
30 дней. 57 прогонов падали на проверке секретов и ничего не выдавали;
первый зелёный (#58, 24.09) выдал бы всё.

Правило: прежде чем запускать или чинить workflow, который выгружает
данные, — `private` репозитория. Для публичного — шифрованный архив
(ключ в секретах) без печати путей, либо приватное хранилище.
«Секреты заданы» не значит «бэкап можно включать».

Второе следствие — про память: обзор 67 записал отсутствие секретов
единственной бедой бэкапа («бэкапа нет ни дня»). На деле то же отсутствие
секретов и удерживало файлы от публикации: починка «по записи» открыла бы
утечку.

## Секреты окружения проверяются по форме, а не по значению

`SUPABASE_ACCESS_TOKEN` в окружении сессии лежал в угловых скобках
(`<sbp_…>`): вставлен вместе с плейсхолдером. Проверять регуляркой
(`^sbp_[0-9a-f]{40}$` после снятия скобок), печатая только «да/нет», —
не префиксом и не длиной.

Ответ `GET /v1/projects/{ref}/config/auth` несёт секреты (SMTP, внешние
провайдеры). Печатать из него только нужные поля через `jq`, файл
ответа удалять сразу.

## Leaked password protection

Включается одним полем Management API — `password_hibp_enabled: true`
(`PATCH /v1/projects/{ref}/config/auth`), кода не требует. После — advisor
`auth_leaked_password_protection` должен исчезнуть из `get_advisors security`;
проверено 24.09.

## Копия Storage — серверная, инкрементальная и внутри проекта

Бэкап файлов больше не архив в артефактах GitHub: он копирует объекты
серверным `copy` (`destinationBucket`) в приватный бакет `storage-backup`,
только то, чего в копии ещё нет. За ночь уходит прирост (~20–30 МБ), а не весь
бакет (398 МБ), в GitHub не остаётся ничего, в лог — только счётчики.

- Из копии ничего не удаляется — ради этого она и заведена.
- Тот же ключ с другим размером: прежняя копия переименовывается
  в `<ключ>~<время>`, новая ложится на её место. Ключи по правилу неизменны,
  так что это страховка.
- Список источников сторож ВЫВОДИТ из миграций (`insert into storage.buckets`):
  бакет, заведённый позже, иначе остался бы без копии при зелёном стороже.
- Предел: копия лежит в том же проекте. От ошибки приложения и уборщика она
  защищает, от потери проекта — нет.

Как уменьшали объём (разбор 24.09): инкремент — главный рычаг; дедупликация
по содержимому (-85 МБ, 21%) и пропуск листов закупки (-32 МБ) отвергнуты:
восстановление обязано класть файл по тому же ключу, а экономия на тарифе
Pro копеечная. Ничьи файлы (-20 МБ) копия не фильтрует сознательно — для этого
понадобился бы третий список носителей, а их и двух хватило, чтобы разойтись.

## Две реализации одного списка — сторож читает обе

Уборщиков два: edge-функция `storage-gc` и npm-скрипт `storage:gc`, и оба
удаляют по своему списку носителей. Сессия 67 дописала третий носитель
в функцию, а сторож читал только её — скрипт остался с двумя, и его `--apply`
удалил бы техпакет модели. Правило: если у списка две копии, сторож проверяет
каждую, и проверка «разбор не пуст» стоит рядом — иначе сломанная регулярка
выглядит как «носителей нет».

## Стражи на исключениях — семь из девяти, и почему не остальные два

`erp_stage_guard`, `erp_calendar_guard`, `erp_attachment_guard`,
`erp_notification_guard` сравнивают снимки строки (`to_jsonb(new) - …` против
`to_jsonb(old) - …`), как `erp_order_guard` с 24.09. Сверка поимённых списков
с живой схемой нашла открытыми `message_id` у вложений (держатель
`files.manage` сносил чужой файл через `erp_chat_delete`), `id`/`created_at`
у этапов (любой участник ERP; смена `id` рвала граф `depends_on`) и у плана.

- **Текст функции — с живой базы**, и разница с ней сверяется построчно
  на стороне базы (`regexp_split_to_table(prosrc)` против нового тела) —
  так видно, что изменилось ровно задуманное.
- **Проверка на бою — двумя знаками.** Запрет: подставной `request.jwt.claims`
  без прав, правка под `postgres` (RLS в стороне, страж работает). Законная
  дорога: временные QA-менеджер и QA-рабочий в той же транзакции; строки
  `erp_employees` заводит триггер профиля — их ОБНОВЛЯЮТ, а не вставляют
  (уникальность `profile_id`).
- **Сторож проверяет вычитаемый набор**, а не имена колонок: общий
  `snapshotExclusions` (`migrations.testutil`) понимает `- 'x'`,
  `- array[…]` и константу `v_x constant text[]`, и бросает, если у `new`
  и `old` вычитается разное — такое сравнение ложно всегда.
- `erp_material_guard` — **не тот класс.** Его таблица открыта участникам
  решением 10.08 («ведение закупки не гейтится»), страж охраняет узкое
  подмножество приёмки. Исключения здесь означали бы «закупщик не может
  править закупку» — это решение владельца, а не починка стража.
- `erp_sku_card_guard` переведён следом (`20260924235701`). Открыты были
  `id`, `experimental_id`, `source_item_id`, `created_by`, `created_at`:
  держатель `sku.edit` перепривязывал карточку к чужой разработке.
  **`experimental_id` — под `sku.publish`, а не неизменный для всех:**
  `erp_sku_from_dev` меняет его у существующей карточки через
  `on conflict (code) do update`, и это UPDATE. Прежде чем запирать колонку,
  найдите всех её писателей, в том числе серверные функции, а не только форму.
  Сторож `skuCardGuard.test.ts` требует, чтобы у КАЖДОГО исключения была своя
  проверка: поле, вычтенное из снимка без проверки, открыто всем, кого
  пускает UPDATE-политика.
- `erp_dev_package_guard` — тоже не тот класс: это гейт полноты финального
  пакета при переходе разработки в `ready_for_serial` (`check_violation`),
  а не разбор прав по колонкам. Правку строки целиком гейтит RLS
  (`experimental.manage`).

## Ссылка `on delete set null` у таблицы со стражем — ветка «родитель удалён»

Удаляя родителя, Postgres обнуляет ссылку UPDATE-ом дочерней строки. Этот
UPDATE проходит через BEFORE UPDATE-страж, и `auth.uid()` в нём — того, кто
удалял: для стража обнуление неотличимо от правки руками. Страж, который
держит такую колонку неизменной или под правом, которого у удаляющего нет,
запирает УДАЛЕНИЕ РОДИТЕЛЯ. Ошибка при этом приходит про чужую таблицу:
«позиция-источник карточки не меняется» в ответ на удаление позиции заказа.

Проверено на бою 24.09 контрольной пробой: без отдельной ветки удаление
позиции, из которой завели модель, падало 42501 даже у админа (роль
`director`, все права). Проходил только service_role.

- **Ветка узнаёт обнуление по факту:** ссылка ушла в NULL, а строки,
  на которую она указывала, больше нет (`not exists` по родителю). Внутри
  каскада удалённая строка уже не видна, а с клиента ветку не открыть:
  пока родитель жив, обнулить ссылку нельзя, а после удаления её уже
  обнулила сама база. Глубина триггеров (`pg_trigger_depth()`) — хуже:
  она пропускает любую правку из любого триггера.
- **Ловушка тихая:** удаление падает только у родителя, на которого
  ссылаются, то есть редко и не на тестовых данных. Поэтому сторож общий
  (`guardSetNull.test.ts`) для всех девяти стражей. Таблицу стража он берёт
  из миграций (`create trigger … before update on … execute function
  …_guard()`), ссылки `set null` — из `FK_SNAPSHOT.md`. Новая ссылка
  попадёт под проверку сама, когда обновят эталон.
- **Исключение одно, с причиной:** `erp_orders.tz_order_id` → `orders`.
  Колонка меняется под `order.manage`, а заказ ТЗ удаляют admin, director,
  rop и менеджер-автор; их роли по умолчанию (director, dispatcher, manager)
  это право имеют. Связанных заказов сегодня 0. Пересмотреть на мосте
  «ТЗ → производство»: rop или менеджер с цеховой должностью без
  `order.manage` связанный заказ ТЗ удалить не сможет.

## Ратчет размера файлов — только вниз

`fileSizeRatchet.test.ts`: новый модуль ≤ 500 строк; 25 крупных записаны
со своими размерами на 24.09. Рост — красный CI: место ищется выносом соседнего
куска в свой модуль, а не подъёмом числа. Похудание — тоже красный, пока
потолок не опущен: иначе файл отрастёт обратно до старой отметки незаметно.
Считаются строки как у `wc -l`, вместе с комментариями — объяснения живут
в коде, и выносить их ради счётчика никто не станет.

## Красный Supabase Preview на новом PR — сначала последняя проверка и журнал превью

На PR #180 `Supabase Preview` упал на миграции 23.08, которую сессия не трогала:
`policy "erp_item_labels_read" … already exists (42710)`. Миграция не виновата.
Два пуша с разницей около 30 секунд пришли, пока превью-ветка ещё создавалась,
и два прогона миграций пошли по одной базе одновременно: `create table if not
exists` второго прогона дождался первого и прошёл, а голый `create policy` упал.
Последняя проверка того же коммита уже была зелёной. Журнал превью-базы полный:
264 записи из 264 файлов, включая новую миграцию PR.

Порядок разбора:
1. Посмотреть ПОСЛЕДНЮЮ проверку `Supabase Preview` на текущем коммите.
   Список проверок PR показывает последнюю под каждым именем, а письмо
   об ошибке приходит по любой, в том числе по устаревшей.
2. Сверить журнал превью-базы:
   `select count(*), max(version) from supabase_migrations.schema_migrations`
   на `project_ref` превью (`list_branches`) против числа файлов в
   `supabase/migrations/`. Поле `status` ветки на это не ответит:
   его `updated_at` равен `created_at`, поле отстаёт.
3. Совпало — это гонка прогонов, а не дефект миграции. Переписывать
   применённую миграцию под `if not exists` нельзя (правило журнала:
   применённую правят новой), а новая миграция здесь ничего не чинит.
4. Не совпало, или упавшая миграция падает и на свежем прогоне, — это дефект.
   Разбирать по тексту миграции.

Чтобы не ловить гонку: первый пуш новой ветки делать, когда коммиты уже готовы,
а не догонять его вторым через полминуты.
