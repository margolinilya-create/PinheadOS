## Номер заказа: одна последовательность, один формат

`generate_order_number` читает `order_number_seq`, ту же, что и умолчание
колонки `orders.order_number` из базовой схемы. Вторая последовательность
завела бы два независимых счётчика одного номера: путь через RPC и путь
через умолчание раздали бы одинаковые `PH-0019`.

**`lpad` обрезает.** `lpad(x, 4, '0')` режет строку длиннее четырёх знаков:
10000-й заказ получил бы `PH-1000`, а 12345-й и 123456-й — оба `PH-1234`.
Так было в умолчании колонки с самого начала, и никто не видел:
последовательность на 24.09 дошла только до 18.
Ширина обязана расти с числом: `lpad(n::text, greatest(4, length(n::text)), '0')`.

Формат живёт в ОДНОМ месте: умолчание колонки зовёт функцию, а не держит
свою копию выражения. Две копии уже разошлись однажды — обрезкой.
Сторож — `src/store/orderNumber.test.ts`, проверен мутацией (обрезка,
вторая последовательность, умолчание без функции, неотозванный anon).

## Проверка RPC на бою без расхода последовательности

Функцию, которая зовёт `nextval`, нельзя «попробовать» в откатываемой
транзакции: последовательность не откатывается, и номер сгорит. Проверка
без побочного эффекта — вызов через REST ПОД `anon`, у которого исполнения нет:

- `42501 permission denied for function …` — функция в кэше схемы PostgREST,
  и анонимный вызов номер не тратит (право проверяется до исполнения);
- `PGRST202 … not found in the schema cache` — функции для REST нет.

Остальное — `has_function_privilege`, `has_sequence_privilege`, `prosecdef`,
умолчание колонки — читается из каталога, тоже без вызова.

## Классификация веток требует ПОЛНОЙ истории

Облачная сессия клонирует репозиторий на глубину 50 коммитов.
В таком клоне `git merge-base --is-ancestor` отвечает «не предок» почти
на всё: `main` обрывается 08.09, и старые ветки не находят с ним общего
предка. Первая сверка этой сессии насчитала 39 «несмерженных» веток там,
где их по полной истории 23. Перед любой классификацией —
`git rev-parse --is-shallow-repository` и `git fetch --unshallow`.

Сквош-мерж оставляет ветку «несмерженной» и в полной истории. Такую ветку
подтверждает не предок, а PR: голова ветки обязана совпасть с головой
последнего смерженного PR этой ветки. Коммит после мержа — это работа,
которой в `main` нет.

**Числа отчёта сверяются суммой.** В отчёте 67 стояло «смержены — 63»,
а список на удаление держал 67 веток: 21 под тег + 4 с открытым PR + 42
смерженных. Три слагаемых, не дающих итога, — признак, что одно из них
посчитано по другому снимку.

## Git-прокси сессии и GitHub-интеграция — границы, а не помехи

- Пуш тегов и удаление чужих веток отвечают **403 политикой организации**
  (`recentRelayFailures` пуст — это не обрыв). Не обходить: ни токеном
  из окружения, ни REST в обход прокси. Уборка веток — локально у владельца,
  команда в отчёте 67.
- Если теги не легли, удаление НЕ начинается: теги — страховка ровно тех
  21 ветки, у которых нет PR.
- `actions_run_trigger` → **403 Resource not accessible by integration**:
  у интеграции нет `actions: write`. Ручной прогон workflow делает владелец
  (Actions → Run workflow) или ночной cron.

## Секреты окружения проверяются по форме, а не по значению

`SUPABASE_ACCESS_TOKEN` в окружении сессии лежал в угловых скобках
(`<sbp_…>`): вставлен вместе с плейсхолдером. Проверять регуляркой
(`^sbp_[0-9a-f]{40}$` после снятия скобок), печатая только «да/нет», —
не префиксом и не длиной.

Ответ `GET /v1/projects/{ref}/config/auth` несёт секреты (SMTP, внешние
провайдеры). Печатать из него только нужные поля через `jq`, файл
ответа удалять сразу.

Включается одним полем Management API — `password_hibp_enabled: true`
(`PATCH /v1/projects/{ref}/config/auth`), кода не требует. После — advisor
`auth_leaked_password_protection` должен исчезнуть из `get_advisors security`;
проверено 24.09.
