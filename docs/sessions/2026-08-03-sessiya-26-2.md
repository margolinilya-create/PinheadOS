## Состояние на 2026-08-03 (сессия 26) — Правки менеджера, волна 1: ТЗ и вёрстка

**Пакет менеджера** — пять пунктов, поставка тремя волнами (решение заказчика):
волна 1 — блокирующая ошибка ТЗ + единое ТЗ на позицию + вёрстка строки (эта сессия);
волна 2 — группа «Ожидают материалы» в канбане; волна 3 — недельное и ежедневное
планирование производства.

**Главная находка.** ТЗ в PDF не загружалось **ни разу с момента внедрения**: в бакете
ноль объектов с префиксом `tz/`, в `erp_tz_documents` и `erp_tz_assignments` ноль строк.
`tzFilePath` намеренно сохранял кириллицу в ключе объекта Storage, а Supabase проверяет
ключ регуляркой S3-safe символов, где `\w` объявлен без флага `u`, и отвечает
`InvalidKey`. Это закреплял тест, прямо ожидавший кириллицу в ключе. Урок тот же, что
с порядком операций ТЗ в прошлую сессию: тест фиксирует намерение автора, а не поведение
внешней системы, — инварианты чужого API проверять нечем, кроме реального вызова.

**Что сделано:**
- **Ключ Storage строго ASCII** (`translitAscii` + `sanitizeKeyPart`), расширение
  отделяется заранее — имя целиком из непереводимых символов больше не съедает `.pdf`.
- **Честный статус загрузки**: файл уходит в бакет при выборе, а не в сабмите; на каждый
  файл — `uploading`/`uploaded`/`error` с причиной (через `translateSupabaseError`) и
  кнопкой «Загрузить заново»; «Создать заказ» заблокирована, пока есть незавершённые.
  Повтор пишет тот же путь (`upsert: true`), мусор в бакете не копится.
- **Единое ТЗ на позицию**: резолюция `itemTzDocument` (своё ТЗ позиции → общее ТЗ
  заказа), `stageMissingTz` больше не принимает id цеха, `validateTzAssignments` заменена
  на `validateTzDocs`. Выпадающие списки на каждый цех убраны и в форме, и в карточке
  заказа — вместо них справка «ТЗ увидят: Закрой · Швейка · ВТО · ОТК».
- **Наложение в строке очереди**: `grid` не обрезает содержимое ячейки — всё, что не
  влезло в трек, рисуется поверх соседней колонки. `min-width: 0` роздан всем ячейкам,
  дата и просрочка разведены по строкам, `align-items: start`.

**Решения:**
- **`erp_tz_assignments` не удаляем**: миграция на удаление необратима, строк там ноль,
  хранение бесплатно. Код перестал её читать и писать, тип и ветка RPC помечены
  `@deprecated` с датой. Realtime-подписка на таблицу снята — событий по ней не будет.
- **Гейт «заказ без ТЗ не создаётся» сохранён**, но считает один файл на позицию вместо
  N назначений. Это снимает жалобу «блокирует создание, если хоть одному цеху не
  назначено», не отменяя прежнего решения заказчика.
- **Наследование ТЗ при переносе этапа между цехами удалено** — оно существовало только
  потому, что у нового этапа не было назначения; теперь ТЗ у позиции и наследовать нечего.

**Важно для следующей сессии:**
- Проверить исправление **на живом проде**: создать заказ с ТЗ, имя файла кириллицей.
  Критерий — появившийся объект `tz/` в бакете и строка в `erp_tz_documents` (сейчас 0).
- Волна 2 («Ожидают материалы») требует **миграции**: `erp_departments.gate_material_kinds`
  (карта «вид материала → цех» сейчас захардкожена в `routes.ts` и противоречит правилу
  «признак цеха — из данных») и `erp_materials.responsible` (ответственного за получение
  материала в схеме нет). Плюс новое право `material.receive`.
- Волна 3 (планирование) переиспользует **`erp_calendar_slots`** — таблица заведена
  первой миграцией и не используется ни одной строкой кода. Роль «Руководитель
  производства» (`production_head`) и права `plan.manage`/`plan.fact` — новые.
