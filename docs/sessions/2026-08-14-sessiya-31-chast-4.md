## Состояние на 2026-08-14 (сессия 31, часть 4) — администрирование учёток

Заказчик: «сделаем полное администрирование юзеров — смена пароля, добавление,
удаление и редактирование на странице пользователей». До этого в таблице
правились только роль, цех и цеховая роль — то, что живёт под RLS. Имя, адрес
входа и пароль лежат в `auth.users`, и починить их можно было ИСКЛЮЧИТЕЛЬНО
в дашборде Supabase. Ровно на этом встал предыдущий разбор.

### Серверная функция `admin-users`

Всё перечисленное умеет только Admin API GoTrue, а он требует `service_role` —
ключ, обходящий RLS целиком, и в браузере его не бывает. Функция держит ключ
у себя и сама проверяет вызывающего:

- личность — из токена (`caller.auth.getUser()`), не из тела запроса;
- права — `is_admin()`, вызванная от лица вызывающего: та самая функция,
  на которой стоят политики `profiles`;
- роль новому сотруднику проставляет ТОТ ЖЕ путь, что приглашению — функция
  заводит одноразовый `erp_invites` и отдаёт код триггеру `handle_new_user`.

Четыре действия: `create` · `set_password` · `set_email` · `delete`.

### Что теперь есть на странице «Пользователи»

| Действие | Где | Гейт |
|---|---|---|
| Пригласить ссылкой | кнопка «Пригласить» | право `staff.invite` |
| Завести с паролем | кнопка «Добавить» | `is_admin()` |
| Переименовать | карточка (✎ в строке) | `is_admin()` |
| Сменить email (логин) | карточка | `is_admin()` |
| Задать пароль | карточка | `is_admin()` |
| Удалить навсегда | карточка, красная зона | `is_admin()` + впечатать адрес |
| Роль · цех · цеховая роль | инлайн в таблице | как было |
| Подтвердить · Отключить · Вернуть | инлайн в таблице | как было |

Каждое поле уходит своим действием, а не общей кнопкой «Сохранить»: роль и цех
правит PostgREST под RLS, пароль и адрес — Admin API. Одна кнопка на пять
разных запросов означала бы «сохранено» там, где прошла половина.

### Удаление: три сторожа

Мягкое отключение остаётся обычным путём. Удаление живёт для записи, заведённой
по ошибке: себя удалить нельзя, заказы (`created_by` — `no action`) отказывают
ДО первой записи, подтверждение требует впечатать адрес. `profiles` не связан
с `auth.users` внешним ключом вовсе, поэтому строку профиля функция убирает явно.

### Проверено на боевом проекте

Заведён временный админ, получен настоящий токен, прогнаны все ветки и всё
убрано за собой (в базе снова 6 профилей):

| проверка | результат |
|---|---|
| без токена / только anon | 401 |
| не админ (заведённый сотрудник) | 403 «Доступ только у администратора» |
| заведение | роль `production`, цеховая `worker`, одобрен, адрес подтверждён, имя из метаданных, приглашение погашено |
| вход заданным паролем | вошёл |
| адрес уже занят | 409 с объяснением |
| смена пароля | старый — `invalid_credentials`, новый — вошёл |
| смена адреса | старый адрес не пускает, новый пускает |
| себя удалить | 409 |
| автор заказа | 409 с числом заказов, строки профиля и сотрудника НЕ тронуты |
| удаление без заказов | нет ни в `auth.users`, ни в `profiles`, ни в `erp_employees` |
