Заказчик прислал документ с пакетом правок (P0–P3 + отдельная страница про загрузку,
склад и подряд). Решения по развилкам: делаем ВЕСЬ документ волнами; роли —
переименовать существующие и добавить недостающие; ОТК убрать из интерфейса и из
маршрута новых заказов; загрузку производства ввести общей мощностью 10 000 ед./мес,
блок «Загрузка цехов» переименовать в «Задачи по цехам». План — в
`/root/.claude/plans/wise-cooking-forest.md` (волны 0–4).

Эта сессия закрывает **волну 0 — P0**: «не грузится PDF-ТЗ» и системные `Load failed`.

### Причина найдена, и она одна на оба симптома

**Dev-режим подделывал вход.** `useAuthStore.init()` брал `DEV_MODE` из
`import.meta.env.DEV`, то есть режим включался у ЛЮБОГО, кто запустил `npm run dev` —
в том числе против боевой базы. Дальше он подставлял `{ id: 'dev', role: 'admin' }`
и выходил, не проверив, есть ли настоящая сессия. Интерфейс выглядел рабочим
и админским (в довершение `canActInDept` для `'dev'` разрешает любой цех), а каждый
запрос уходил в Supabase ролью `anon`: чтение — пусто («Не удалось загрузить
производственный план / историю заказа / заказ»), запись — отказ RLS.

Проверено на проде, не по догадке: под `authenticated` с JWT пользователя вставка
в `storage.objects` проходит, под `anon` — `42501: new row violates row-level
security policy for table "objects"`, и Storage отдаёт это как HTTP 400. Ровно эти
400 и лежат в логах Storage за 10.08 06:09–06:20 (три попытки, ключ ASCII-валиден,
MIME разрешён, лимит не превышен). Рядом в auth-логах — пять входов по паролю за час
и `Invalid Refresh Token: Refresh Token Not Found`: человек пытался войти, потому что
система не говорила ему, что он не вошёл.

**Что сделано:** автологин включается только явным `VITE_DEV_AUTOLOGIN=1` и только
когда настоящей сессии нет (`playwright.config.ts` ставит его сам — e2e гоняются
против мока, где сессии не бывает); появилась подписка `watchAuthState()` на
`onAuthStateChange` — до неё сессия проверялась ровно один раз за загрузку страницы;
опции клиента (`persistSession`, `autoRefreshToken`, `detectSessionInUrl`) заданы явно.

### Второй дефект ТЗ — расхождение гейтов (нашёлся попутно)

Файл в бакет пускал `erp_is_member()`, строку в `erp_tz_documents` —
`erp_can_manage_tz()` (только `profiles.role`, про `erp_employees.role` не знает),
а кнопку в интерфейсе — право `tz.manage` из матрицы, где оно есть и у диспетчера.
Диспетчер видел кнопку, файл улетал в бакет, строка падала с 42501, код убирал файл
за собой. Политики переведены на `erp_has_permission('tz.manage')` — тот же механизм,
что у плана и этапов. Никого из прежних это не отсекает: admin/director → `director`,
rop → `dispatcher`, manager → `manager`.

Заодно добавлена SELECT-политика на `storage.objects` для `erp-attachments` — её
не было НИ ОДНОЙ. Публичная раздача идёт мимо RLS, поэтому не замечали, но
клиентские `upsert`, `remove` и `list` ходят через RLS: отсюда и старый комментарий
«удалять его клиенту политика не даёт», из-за которого копились сироты.

### Сбой без ответа сервера закрыт по всему стору

Правило «supabase-js возвращает `error` на ответ и БРОСАЕТ, когда ответа не было»
соблюдалось в трёх функциях из шестидесяти. Введена обёртка `erpQuery` в
`store/shared.ts`: она приводит бросок к такому же `{ data: null, error }`, какой
пришёл бы от сервера, и дальше работает уже написанная ветка `if (error) …` — со
снятием флагов, откатом и `erpError`. Проведена по всем слайсам ERP (58 мест).

Тосты перестали копиться: одинаковое сообщение в пределах жизни полосы поднимает
счётчик вместо новой полосы (прямая жалоба документа про «россыпь одинаковых красных
ошибок»). Заодно починен id тоста — он брался из `Date.now()`, и два сообщения в одну
миллисекунду получали общий id, а закрытие одного гасило оба. Глобальный
`unhandledrejection` больше не показывает сырое `Load failed` из WebKit.

### Что выяснилось экспериментом и стоит помнить

**У `loadAll` НЕ должно быть guard'а «уже грузим — выходим».** Он напрашивается
(`ErpLayout` и экран зовут её одновременно), но ломает очередь цеха — 10 e2e из 24.
Обе формы экономии одинаково плохи: и ранний выход, и дедупликация общим промисом.
Экраны вызывают `loadAll()` как загрузку СВОИХ данных и читают стор сразу после;
отобрав у них загрузку, получаем «Выберите свой цех выше» на экране, где задания
есть. Лишний запрос дешевле, чем пустой экран, который рабочий читает как «работы нет».
