## Состояние на 2026-07-27 (сессия 23, часть 4) — Волна 4 «ТЗ в PDF»

**Замысел:** закрыть последний блок сводного списка — технические задания в PDF
для производственных цехов. До сих пор ТЗ существовало только как структурные поля
(`TzBlock`: сетка, нанесения, упаковка); файлов ТЗ не было вовсе, `accept` всех загрузок
был `image/*`, вложения вешались только на заказ.

**Схема БД (миграция `20260727190000_erp_tz_documents.sql`, применена на прод):**
- `erp_tz_documents(order_id, item_id nullable, group_id, version, is_current, file_path,
  file_name, mime_type, size_bytes, note, uploaded_by)`, `unique(group_id, version)`,
  партиальный `unique(group_id) where is_current`. `item_id = null` — общее ТЗ заказа.
- `erp_tz_assignments(order_id, item_id, department_id, group_id)`, `unique(item_id,
  department_id)` — одному этапу одно ТЗ.
- `erp_orders.tz_required boolean not null default true`, **бэкфилл `false` всем 147
  существующим заказам** — иначе гейт мгновенно застопорил бы живое производство.
- Право `tz.manage` (director/dispatcher/manager), функция `erp_can_manage_tz()`
  (admin/director/rop/manager) — своя, `erp_is_manager()` не трогали. RLS: читают все
  авторизованные (цех обязан открыть ТЗ), пишут — по `erp_can_manage_tz()`; у документов
  есть UPDATE-политика (снятие `is_current`), в отличие от `erp_order_attachments`.
- `erp_create_order` расширен секцией `tz`: документы и назначения вставляются той же
  транзакцией, что заказ, позиции и этапы.

**Ключевое решение — назначение ссылается на `group_id`, а не на версию.** Замена файла
создаёт версию N+1 и снимает `is_current` с прежней; все цеха, которым документ назначен,
видят новую версию сами. Переназначать ничего не нужно — ровно то, что просил заказчик.

**Гейт двухступенчатый (решение заказчика «жёстко на создании + гейт на этапе»):**
1. Форма создания: кнопка «Создать заказ» заблокирована **сразу**, не дожидаясь первой
   попытки, с конкретным текстом — «Невозможно создать заказ: для позиции «Футболка
   Regular» не назначено ТЗ: Швейка и ВТО».
2. Этап без ТЗ не становится «Готов к запуску» (`isStageReady`/`waitingReason` получили
   флаг `missingTz`, причина — «Не назначено ТЗ»). Страховка для заказов, заведённых
   раньше, и для этапов, добавленных переносом на канбане.

**Что вошло:**
- `utils/tz.ts` (37 тестов) — резолюция «этап → актуальная версия», история версий,
  `missingTzStages`/`missingTzMessage`, `validateTzAssignments` для формы,
  `tzUpdatedAfterStart`, обеззараживание имени файла в ключе объекта.
- `tzSlice` — загрузка (валидация `application/pdf` + 15 МБ, которых не было у превью),
  замена версии, назначение/снятие, `setTzRequired`. Замена пишет в `erp_stage_events`
  «ТЗ обновлено до версии N» каждому назначенному этапу — цех видит это в истории задания.
- `TzViewer` — встроенный просмотрщик браузера (`<iframe>`), полноэкранный режим с
  focus-trap, «Скачать» и «В новой вкладке» (запасной путь для мобильного Safari).
  Новых npm-зависимостей нет.
- Раздел «ТЗ и файлы» в форме создания: маршрут позиции считается **до** создания заказа
  общим `buildItemRoute`, файлы грузятся в `tz/new/<group_id>/` до RPC.
- Карточка заказа и её боковая версия: загрузка общего ТЗ и ТЗ позиции, назначение по
  цехам, замена файла, баннер «Заказ не запустится: …» и кнопка «Требовать ТЗ» для
  дедушкованных заказов. Вкладка «Файлы» перестала рисовать `<img>` для не-картинок.
- Очередь цеха: индикатор 📄 с именем и версией реального PDF (📋 остался для
  структурного ТЗ), задание цеха — «Открыть ТЗ» и бейдж «ТЗ обновлено».

**Решения:**
- **ТЗ требуют только производственные цеха** (`deptNeedsTz` = `isQueueDept`): закупке,
  логистике и складам PDF по образцу заказчика не адресуется — иначе гейт застрял бы
  на «Закупке» первым же этапом.
- **Гейт fail-open при отсутствии флага**: `tz_required` учитывается только при явном
  `true`. Отсутствие поля (старый кэш, урезанный select) не должно останавливать цех.
- **Файлы вперёд, заказ одной транзакцией.** Обратный порядок («заказ, потом файлы»,
  как грузится превью) нарушал бы требование при сбое дозагрузки: заказ есть, ТЗ нет.
  Цена — файлы-сироты в `tz/new/`, если RPC упал; удалить их клиент не может
  (delete в бакете — только admin), поэтому префикс намеренно отдельный.
- **Перенос между цехами наследует ТЗ**: этап, созданный `moveStageToDepartment`,
  берёт назначение исходного цеха (или общее ТЗ заказа) — иначе перетащенная карточка
  превращалась бы в намертво заблокированное задание.
- **Генерация ТЗ-PDF из полей заказа не делалась** — прежний замысел
  `docs/erp/tz-format-analysis.md` («PrintPreview как рендер ТЗ») заменён загрузкой
  готового файла. Структурный `TzBlock` остаётся рядом и никуда не девается.

**Проверка:** lint 0, **1172 unit** (+46), build ок, e2e — 17 сценариев ERP.
