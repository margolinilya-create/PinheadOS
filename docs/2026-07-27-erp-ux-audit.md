**Дата:** 2026-07-27 · **Область:** только 🏭 Производство (`src/erp/**`), Order Studio не трогали.

## P0 — ломает работу или портит данные

### 1. Перенос между цехами на канбане молча не срабатывает на ~90% площади колонки
`erp/components/ErpKanban.jsx:118-124` + `:234-238`

Дорожка ловит `drop` первой и синхронно зовёт `onLaneDrop` → `onDragEnd()` → `dragRef.current = null`.
Затем событие всплывает в `<section>` колонки, `onColumnDrop` читает уже `null` и тихо выходит (`:148-150`).
`stopPropagation` при этом не вызывается: для чужого цеха `droppable === false` и `dropAt === null`.

Перенос работает **только** если отпустить карточку ровно на шапке колонки (~40px) —
остальное занято тремя дорожками. Колонка при этом подсвечена как валидная зона приёма:
пользователь видит приглашение, бросает — и не происходит ничего, даже тоста.

**Фикс:** в `onDrop` дорожки выходить сразу, если `dragRef.current.stage.department_id !== deptId`
(отдать событие колонке). Плюс компонентный тест на порядок drop-событий — сейчас
`kanbanColumns.test.js` покрывает только чистую группировку.

### 2. Клик по чипу этапа на производственном плане закрывает этап без прав и без подтверждения
`erp/screens/ProductionBoard.jsx:53-69` и `:149-152`

```jsx
const onAdvance = async (stage, nextStatus, item) => {
  const extra = nextStatus === 'done' ? { qty_done: item.qty } : {};
  await setStageStatus(stage.id, nextStatus, extra);
};
```

`ProductionBoard.jsx` — единственный экран действий, который **не импортирует `useErpAccess`**.
Один промах мышью по 23-пиксельному чипу в плотной таблице: этап закрыт, `qty_done` затёрт
полным тиражом (сдали 300 из 500 → станет 500), зависимые этапы разблокированы.
Нарушены оба правила: «доступ только через `useErpAccess`» (CLAUDE.md) и «молча этап не закрывать».

**Фикс:** гейт `access.canDo(...)` на чипе + `confirm()` с последствиями; количество —
через `reportProgress`, а не подстановкой `qty_done: item.qty`.

### 3. «✓ Завершить этап» в очереди цеха записывает весь тираж без подтверждения
`erp/screens/queue/useStageActions.js:37-40`

```js
const onDone = useCallback(
  (entry) => setStageStatus(entry.stage.id, 'done', { qty_done: entry.item.qty }), …);
```

Один тап, без диалога. Записал 40 из 100, нажал «Завершить» — в БД уйдёт 100.
`useConfirmStore` в зоне очереди не используется ни разу.
DESIGN.md прямо требует подтверждения именно для «незакрытого количества».

**Фикс:** при `qty_done < item.qty` — `confirm()`: «Останется незакрытыми N шт, они запишутся
как выполненные; следующий этап (X) откроется на весь тираж».

### 4. Фильтры производственного плана в табличном виде ничего не фильтруют
`erp/screens/ProductionBoard.jsx:133-147`

`QueueFilters` рендерится для обоих видов, но `rows` использует из `filters` **только `filters.q`**.
«🟢 Готово к запуску», «⏰ Просрочено», «🚫 С проблемой», цех, статус, исполнитель, срок с-по,
сортировка — мертвы. При этом чип красится синим и появляется «Сбросить».

Диспетчер жмёт «Просрочено», видит те же 200 строк и делает вывод, что просрочено всё.
Фильтр, который врёт, хуже отсутствующего.

**Фикс:** строить строки из `applyStageFilters(buildQueueEntries(...))` либо (минимум)
скрывать неработающие контролы в табличном виде.

### 5. Матрица прав врёт про админа — снятая галочка в колонке «Директор» отключает доступ ему самому
`erp/screens/admin/PermissionsTab.jsx:43-47` vs `erp/store/useErpAccess.ts:53-56`

Подпись обещает: «Администратор и директор имеют полный доступ независимо от галочек».
Код: `resolveErpRole('admin')` → `'director'`, а `can = isDev || isAllowed(matrix, role, permission)` —
никакого обхода для руководства нет. Админ снимает галочку, доверяя подписи, и молча
теряет право сам, одновременно у себя и у директора. Отката в UI нет.

**Фикс:** либо реально `can = isPrivileged || isAllowed(...)`, либо убрать ложную подпись
и показать колонку «Директор» read-only с замком.

### 6. 7 из 10 прав в матрице ничего не выключают
`erp/types.ts:685-688` объявляет 10 прав, проверяются три:
`stage.move_department` и `stage.priority` (`ErpKanban.jsx:92,110`), `tz.manage` (`TzDocsSection.jsx:65`).

`stage.take`, `stage.progress`, `stage.complete`, `stage.block`, `stage.defect`, `order.manage`,
`catalog.edit` — нигде. В очереди гейт один: `canAct = access.canActIn(dept?.id)`
(`DepartmentQueue.jsx:145`). Хуже: `canActInDept` возвращает `true`, если привязки к цеху нет
(`utils/permissions.ts:87`) — значит менеджер без записи в `erp_employees` жмёт «Взять в работу»,
«Завершить», «Брак» в **любом** цехе.

Руководитель снимает «Оформлять брак», видит галочку снятой, считает вопрос закрытым — а кнопка
у рабочего осталась. Матрица создаёт ложное чувство контроля.

**Фикс:** провести `can('stage.take'|'stage.complete'|…)` в `StageActionsPanel`/`useStageActions`
и `catalog.edit` в админские вкладки — либо временно показывать только 3 работающих права.

### 7. Повторная попытка создать заказ после сбоя падает всегда — форма превращается в тупик
`erp/screens/orders/CreateOrderModal.jsx:304-315`

Путь ТЗ детерминированный (`tz/new/<groupId>/v1-<имя>`), `groupId` генерируется один раз
при добавлении файла (`:113`), `upsert: false`. Если RPC `erp_create_order` упал или сорвалась
загрузка 2-го файла из 3 — повторное нажатие грузит **все** файлы заново, первый уже лежит
по тому же пути → Duplicate → «Не удалось загрузить ТЗ … — заказ не создан». Сколько ни жми,
будет то же самое. Спасает только неочевидное «убрать и приложить PDF заново».

**Фикс:** новый `groupId` (или суффикс попытки) перед каждой загрузкой либо `upsert: true`;
в тексте ошибки назвать действие.

### 8. Ошибка загрузки = вечный скелетон или пустой экран на 6 экранах
Флаг `loadError` в сторе есть (`ordersSlice.ts:59`) и корректно обработан на трёх экранах
(`Warehouse.jsx:167-172`, `Subcontracting.jsx:230`, `FabricPurchasing.jsx:315`). Игнорируют его:

| Экран | Что видит пользователь |
|---|---|
| `DepartmentQueue.jsx:312` | «Выберите свой цех выше» навсегда |
| `ProductionTask.jsx:79` | скелетон крутится вечно |
| `ErpDashboard.jsx:160` | скелетон крутится вечно |
| `ProductionBoard.jsx:203` | «0 позиций» и пустота |
| `OrdersScreen.jsx:230` | заголовок и тулбар, больше ничего |
| `OrderCard.jsx:42` | скелетон крутится вечно |
| `Experimental.jsx:31` | пустой раздел |

Эффект `if (!loaded) loadAll()` повторно не сработает — зависимости не изменились.
Единственный выход — F5, и то не всякий догадается.

Отдельно: `QueueSkeleton` **недостижим в принципе** — условие `dept && loading && !loaded`
не выполнимо никогда, потому что `departments` и `loaded: true` пишутся одним `set()`
(`ordersSlice.ts:62-67`), а `dept` берётся из `departments`.

**Фикс:** один блок «Не удалось загрузить · Повторить» по образцу `Warehouse.jsx:167-172`
на все семь экранов; условие скелетона очереди — `!loaded && !loadError`.

### 9. Цветовой код статусов в светлой теме не читается: «ожидает» — 2.02:1
`erp/erp.module.css:454-462` — чипы красят текст тем же токеном, что и заливку:

## P1 — заметно мешает (31)

### Производство и права
1. **Смена статуса перетаскиванием в канбане не проверяет права** (`ErpKanban.jsx:139-143`).
   Соседние жесты гейтятся, этот — нет. Работник швейки закрывает этап ДТФ с доски.
2. **Возврат брака откатывает промежуточные этапы, а рабочий видит только целевой**
   (`StageActionsPanel.jsx:296-300` → `stagesSlice.ts:154-171`). В выпадашке «Вернуть: Швейка»,
   по факту переоткроются ещё ВТО и Печать со снятым `qty_done`.
3. **На планшете нельзя менять приоритет, но интерфейс обещает, что можно**:
   `DepartmentQueue` не вызывает `useTouchDndPolyfill` (он только в `ErpKanban.jsx:65`),
   а `QueueRow.jsx:52` показывает ручку и подсказку «Перетащите, чтобы изменить приоритет».
4. **Колонку канбана нельзя проскроллить во время перетаскивания** — автоскролл только
   горизонтальный (`ErpKanban.jsx:95-102`), при `touch-action: none` и `max-height` колонки.
   Поставить задание на приоритетное место ниже видимой части невозможно ни мышью, ни пальцем.
5. **Выбранный цех переживает выход из системы**: `erp_my_dept` пишется напрямую в
   `localStorage` (`DepartmentQueue.jsx:114`) и не входит в `APP_KEYS` (`lib/storage.ts:35-45`).
   На общем цеховом планшете следующий рабочий попадает в чужой цех — и, поскольку
   `canActInDept` без привязки возвращает `true`, с полным набором кнопок.
6. **Счётчик просрочек на вкладке цеха нечитаем**: инлайн-стиль меняет только фон,
   `color` остаётся `--text-mid` — серый на красном, контраст ≈2:1 при кегле 11px
   (`DepartmentQueue.jsx:290`, ср. корректный `.deptTabHot` в `erp.module.css:673-677`).
7. **Кнопка «← В очередь цеха» теряет фильтры и позицию прокрутки** — ссылка собирается
   без `search` (`ProductionTask.jsx:133`), а `useScrollRestore` ключуется по `pathname+search`.
8. **Обрезанные названия невозможно прочитать**: `title` у ссылки дублирует номер вместо
   полного названия, у подстроки `title` нет вовсе (`QueueRow.jsx:60-72`, `QueueCard.jsx:57`).

## Что сделано хорошо — не сломать при правках

- **Единый источник группировки и фильтров** (`buildQueueEntries` + `applyStageFilters`):
  очередь, канбан и план считают группы и причины ожидания одинаково, фильтры живут в URL.
- **Один набор действий на три поверхности** (`StageActionsPanel` + `useStageActions`) —
  строка очереди, мобильная карточка и страница задания не расходятся.
- **Серверная валидация количеств**: `reportProgress` клампит к тиражу и честно предупреждает,
  `reportDefect` не даёт браку превысить ни тираж, ни фактически сделанное.
- **Инлайн-валидация формы создания реализована целиком**: `aria-invalid` + `aria-describedby` +
  автоскролл к первому ошибочному с раскрытием секции + «Осталось заполнить: …».
- **Гейт ТЗ объясняет себя**: «для позиции «X» не назначено ТЗ: Раскрой, Швейка» вместо
  абстрактного «заполните обязательные поля».
- **Транзакционность создания заказа продумана и задокументирована**, включая честный
  комментарий про цену решения (файлы-сироты).
- **Опасные экраны объясняют правила словами**: почему участки не удаляются, почему значения
  справочника отключаются, что делает выбранный вариант поставщика.
- **Четыре различимых состояния зоны приёма в канбане** + маркер места вставки —
  заметно лучше среднего канбана.
- **Перетаскивание не возит страницу**: `overscroll-behavior`, `touch-action` только на время
  drag, автоскролл доски вместо окна, полифилл тач-DnD лениво и только на `pointer: coarse`.
- **Красный дисциплинирован**: точка дедлайна, полоса заблокированной карточки, чип срока —
  строка целиком не красится. `DueCell` корректно снимает «просрочен» с отгруженных.
- **`orderLinkClick`**: ЛКМ → Drawer, Ctrl/Cmd/Shift → нормальный диплинк, `stopPropagation`,
  чтобы клик по названию не раскрывал строку.
- **Optimistic + rollback + toast** во всех мутациях, без исключений.
- **KPI закупки — эталон**: кликабельны целиком, фильтруют список, сбрасываются повторным
  кликом, одна найденная позиция открывает карточку сразу.
- **`prefers-reduced-motion` уважается глобально и корректно** (`styles/utils.css:356-362`),
  единственное `!important` в проекте документировано ссылкой на WCAG 2.1 SC 2.3.3.
  В самом `erp.module.css` — ноль `!important`.
- **Инлайн-стили не содержат цветов**: из 114 объектов `style={{…}}` ноль захардкоженных
  `#hex`/`rgb()`, ноль `fontSize`. Тёмная тема от инлайнов не ломается нигде.
- **Тёмная тема — не пост-фактум**: полный второй набор из 30 токенов, подобранных вручную,
  и по контрасту он лучше светлого (chipWaiting 7.33:1 против 2.02:1).
- **Изображения и iframe размечены полностью**: все 8 `<img>` с осмысленным `alt`,
  оба `<iframe>` с `title`, заглушки битых превью — `aria-hidden`.
- **`useFocusTrap` — качественная реализация**: восстанавливает предыдущий фокус,
  пересчитывает список фокусируемых на каждый Tab, держит `onEscape` в ref.
- **Скелетоны объявлены как живые области** — `role="status"` + осмысленный `aria-label`.
- **Правило «мобильные модалки» доведено до конца**: `100dvh`, sticky-кнопки, чтобы
  отправка не уезжала за клавиатуру.
