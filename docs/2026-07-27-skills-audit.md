## P0 — чинить в первую очередь

### 1. Цеха стали редактируемыми, а код их не видит

Волна 2 дала админке создавать участки (`erp_departments`), но список
производственных цехов по-прежнему захардкожен константой:

```
erp/data/departments.ts:
export const QUEUE_DEPT_CODES = new Set([
  'cutting', 'silkscreen', 'dtf', 'embroidery', 'sewing', 'vto',
]);
```

`isQueueDept` используется в **8 местах**, определяющих всю видимость цеха:
меню сайдбара (`ErpLayout.jsx:98`), колонки канбана (`kanbanColumns.js:16`),
гейт ТЗ (`tz.ts:110`), загрузка на дашборде (`ErpDashboard.jsx:123`),
переключатель очередей (`DepartmentQueue.jsx:271`), форма создания заказа
(`CreateOrderModal.jsx:242`), подряд, `ProductionBoard.jsx:122`.

Следствие: участок, заведённый директором в админке, **не появится ни в меню,
ни в канбане, ни в маршруте, ни в требованиях ТЗ**. Он просто не существует для
приложения. Отдельно: заказчик в примере сообщения об ошибке ТЗ прямо назвал
**ОТК** («не назначено ТЗ швейному цеху и ОТК») — такого цеха в системе нет, и
завести его сейчас бесполезно.

**Решение.** Признак «производственный цех» переносится в данные. В
`erp_departments` уже есть колонка `type`; добавить `is_production boolean`
(бэкфилл `true` для шести текущих кодов), в админке — чекбокс, `isQueueDept(code)`
заменить на `deptIsProduction(dept)` по строке из БД. Хардкод остаётся только как
fallback для сида. Заодно завести ОТК как реальный участок.

Риск: `isQueueDept` вызывается по коду, а не по объекту — придётся протащить
`departments` в места, где сейчас есть только код (`utils/tz.deptNeedsTz`).

### 2. Функциональные e2e не защищают main

`.github/workflows/ci.yml` гоняет `npm run lint` и `npm run test`. Из Playwright
запускается **только `e2e/visual.spec.ts`**, и тот с `continue-on-error: true`.
Остальные 8 спеков (включая `erp-queue.spec.ts` с 17 сценариями ERP) не
запускаются никогда.

Хуже: `playwright.config.ts` объявляет два проекта — `desktop` и `mobile`, — а ни
один спек не имеет гарда по вьюпорту. На mobile (375px) сайдбар скрыт и строк
очереди нет, поэтому `npm run e2e` локально **красный** минимум на 4 сценариях
`erp-queue`. Это не регрессия — просто спеки писались под desktop, а конфиг
про это не знает.

**Решение.** Двумя шагами:
- разметить спеки по проектам: ERP/десктопные — `desktop`, а для mobile оставить
  адаптированные проверки (сайдбар в бургере, карточки вместо строк);
- добавить в CI job `e2e` (без `continue-on-error`) и `npm run build` — сейчас
  сломанный билд ловит только Vercel.

### 3. Отладочный `console.log` — понижен до P2 (исправлено)

**Поправка к первой редакции аудита.** Я записал этот пункт в P0 как «уходит в
прод» — это неверно. Строка была обёрнута в `if (import.meta.env.DEV)`, и Vite
вырезает такую ветку при сборке; проверено грепом по `dist/assets/*.js` — в
бандле её нет.

Что действительно было не так: в `SkuEditor.jsx` жила отладка по конкретному
артикулу (`s.code === 'T-001'`) — оставленные леса, шумящие в dev-консоли на
каждом сохранении каталога. Блок удалён.

(`useAuthStore.ts:56` — тоже `console.log` под `import.meta.env.DEV`, но он
осмысленный: сообщает о работе в dev-режиме без Supabase. Оставлен.)

### 4. RLS вариантов поставщиков открыта нараспашку

Advisor `rls_policy_always_true` (3 предупреждения на `erp_material_suppliers`):
INSERT / UPDATE / DELETE — `true` для роли `authenticated`.

Это моя недоработка волны 3: политики скопированы «по образцу материалов», но
таблица хранит **закупочные цены и условия поставщиков**. Сейчас любой сотрудник
цеха может подменить цену или удалить вариант.

**Решение.** Привести к модели закупки, как в
`20260720130000_erp_procurement_rls_roles.sql`: чтение — всем авторизованным
(выбранный поставщик виден складу и цеху), запись — `erp_is_manager()`.
Проверить, что экран закупки после этого работает под ролью закупщика — если нет,
завести отдельную функцию `erp_can_manage_procurement()`.

## P1 — заметная польза, риска мало

### 5. RLS перевычисляет `auth.uid()` на каждой строке

Advisor `auth_rls_initplan` — 13 политик, все в таблицах Order Studio: `profiles`,
`orders` (2), `order_comments` (2), `order_audit`, `catalog_config` (2),
`order_templates` (3), `app_config` (2). ERP-таблицы чистые.

**Решение.** Механическая замена `auth.uid()` → `(select auth.uid())` в теле
политик: Postgres выносит подзапрос в InitPlan и считает его один раз, а не на
строку. Одна миграция, поведение не меняется.

### 6. Дублирующие permissive-политики

Advisor `multiple_permissive_policies` — 40 предупреждений: `orders` (20),
`app_config` (5), `catalog_config` (5), `order_audit` (5), `profiles` (5).
Причина типовая: политика на `ALL` и политика на `SELECT` живут рядом, и на
каждый SELECT Postgres проверяет обе.

**Решение.** Разделить `FOR ALL` на явные `SELECT` / `INSERT` / `UPDATE` /
`DELETE`. Делать после п.5 одной миграцией по Order Studio — ERP уже так написан.

### 7. Внешние ключи без индексов

13 штук, из них рабочие на горячих путях: `erp_stage_events.stage_id`
(история этапа открывается в каждом задании), `erp_materials.item_id`,
`erp_procurement_tasks.source_stage_id` (гейт закупки), `order_audit.order_id`,
`erp_tz_assignments.department_id` (мой, волна 4).

**Решение.** Одна миграция с `create index if not exists` на все 13. Сейчас
таблицы маленькие (443 этапа, 130 событий) — но именно поэтому дёшево.

### 8. Загрузка ERP не масштабируется

`ordersSlice.loadAll` тянет **все** активные заказы (76) одним запросом с
`ORDER_SELECT` — 9 вложенных отношений. `loadArchive` тянет **весь** архив (71)
тем же запросом, без лимита. Плюс `tz_documents:erp_tz_documents (*)` забирает
все версии каждого ТЗ, хотя UI почти всегда показывает только `is_current`.

Сегодня это ~150 заказов и работает. Через год типографии это тысячи.

**Решение.**
- Архив — постранично (`.range()`), у `Pagination` уже есть компонент.
- В `ORDER_SELECT` для списка не тянуть `tz_documents` целиком: либо
  `.eq('tz_documents.is_current', true)`, либо вынести историю версий в
  отдельную загрузку по требованию (как `loadOrderEvents`).
- Мерить до и после — иначе это гадание, а не оптимизация.

### 9. `queueEntries.js` без тестов

`pinhead-react/CLAUDE.md` называет его единым источником группы и причины
ожидания, а `Не трогать без тестов` перечисляет соседей — но у самого
`queueEntries` тестов нет. Он же теперь считает и гейт ТЗ.

**Решение.** `queueEntries.test.js`: группы ready/in_progress/waiting/blocked,
причина ожидания по материалам, по закупке, по ТЗ; фильтр по цеху; пропуск
`skipped`. По правилу TDD-скила — тесты вперёд рефакторинга п.1, потому что п.1
как раз этот файл и заденет.

### 10. `CreateOrderModal.jsx` — 1247 строк

Самый большой файл проекта, вдвое больше следующего. Внутри: размерная сетка,
нанесения, подряд, превью, черновик, раздел ТЗ, валидация, сабмит с загрузкой
файлов. Скил `software-architecture` требует резать по доменам.

**Решение.** Вынести в `screens/orders/create/`: `SizeGridEditor`,
`ItemBlock` (позиция с нанесениями и подрядом), `TzSection`, `PreviewDropZone`,
хук `useCreateOrderForm` (стейт + черновик + валидация). Модалка остаётся
композицией. Строго без изменения поведения — e2e из п.2 это и подтвердит.

### 11. `window.prompt` в канбане

```
erp/components/ErpKanban.jsx:181
  comment = window.prompt('Причина переноса (попадёт в историю заказа):', '');
```

Проект уже имеет императивный `confirm` через `useConfirmStore` — и он
используется строкой выше. Нативный `prompt` ломает вид, не стилизуется, не
работает в части браузеров и не даёт валидировать ввод.

**Решение.** Расширить `useConfirmStore` полем ввода (`prompt({ title, label,
required })`) и заменить вызов. Заодно закрывается требование заказчика
«комментарий при возврате/пропуске» нормальной формой.

### 12. Скилы устарели и уводят не туда

Проектные скилы писались до перехода на TypeScript и до ERP:

- `systematic-debugging` шлёт в `useOrdersStore.js`, `useStore.js`,
  `utils/pricing.js`, `catalogSlice.js` — все давно `.ts`;
- `test-driven-development` и `finishing-a-development-branch` требуют «722+
  тестов» — сейчас 1172, критерий бессмысленный;
- `software-architecture` описывает только визард Order Studio; ERP —
  раздел по умолчанию — в скиле отсутствует целиком;
- `test-driven-development` в таблице «куда писать тест» не знает ни про
  `erp/utils/*`, ни про `erp/store/slices/*`.

**Решение.** Обновить пути на `.ts`, заменить абсолютные числа тестов на «не
меньше, чем было до изменений», добавить в `software-architecture` карту ERP
(слайсы, `useErpAccess`, `buildQueueEntries`, гейты маршрута), а в
`test-driven-development` — строки про `erp/utils` и `useErpStore.test.ts`.

### 16. `SECURITY DEFINER` функции вызываемы через REST — принять и записать

Advisor предупреждает про `is_admin()`, `erp_is_manager()`, `erp_is_member()`.
Отзывать `EXECUTE` **нельзя**: выражения RLS-политик исполняются от лица
вызывающего, и без права на функцию политики перестанут работать — то есть
«исправление» закроет доступ всем.

Утечки нет: функции без аргументов и возвращают только булево о самом
вызывающем. Правильное действие — зафиксировать это решение в `CLAUDE.md`,
чтобы следующий аудит не пытался «починить» и не уронил прод.

## Что осталось после прохода

**П.15 — включить leaked password protection.** Тумблер в дашборде Supabase
(Auth → Password security), кодом и миграцией не делается. Единственный пункт,
который я не могу закрыть сам.

**П.8 — «лёгкий» ORDER_SELECT.** Архив теперь грузится страницами по 50 с явной
кнопкой «Показать ещё» — тихого лимита нет. А вот убрать из списочного запроса
все версии ТЗ (оставив только `is_current`) с ходу нельзя: карточка заказа
рендерится из того же массива и показывает историю версий. Чтобы срезать
payload, карточку надо перевести на обязательный `loadOne` — это отдельная
правка со своей проверкой, и на сегодняшних объёмах (76 активных, 197 позиций,
443 этапа, 0 документов ТЗ) она ничего не ускорит.

**Мобильные экраны без e2e.** Спеки ERP и визарда исключены из mobile-проекта:
на 375px это другой интерфейс (карточки вместо строк, свой поток шагов), и
desktop-сценарии там проверяют разметку, которой нет. Пока покрытие держит
`visual.spec.ts`, снимающий те же экраны в мобильном вьюпорте. Отдельные
мобильные спеки — следующая работа.

**ОТК не в маршруте по умолчанию.** Участок заведён и виден везде, но в
`BASE_CHAIN` не добавлен: это меняет поток каждого нового заказа и должно быть
вашим решением, а не побочным эффектом технической правки. Пока попасть на ОТК
можно переносом карточки на канбане.

**Неиспользуемые индексы.** Advisor насчитал 24 — но 13 из них созданы этим же
проходом (по внешним ключам), а остальные лежат на таблицах, которые только
начали наполняться. Статистика по ним ничего не значит; перепроверить через
месяц реальной работы.
