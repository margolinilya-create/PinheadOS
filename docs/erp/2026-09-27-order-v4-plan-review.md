# Ревизия плана Order v4 + мост: узкие места и улучшенный план
**Дата:** 27.09.2026 · сверено с репозиторием `PinheadOS` (main, PR #183)
**Что ревизовалось:** `2026-09-26-tz-bridge-spec.md`, `2026-09-27-order-v4-structure.md` (182 решения), план этапов 0 → A → B → C → D → пилот.

---

## 1. Критические узкие места

### 1.1 Обратная связь придёт только через несколько месяцев
План: пилот **после** этапа D, то есть после модели данных, документов, дизайн-мейкера и моста. По темпу проекта (ERP с нуля до прода — 30 сессий за полтора месяца) это 35–45 сессий, 2–3 месяца без единого реального заказа в новом Order. За это время 182 решения, принятые на бумаге, не проверит никто. В апреле проект уже застревал ровно на «сделаем всё, потом покажем».

**Что делать:** менять принцип с «этапы по слоям» на **сквозные срезы**: каждый срез даёт что-то, чем владелец пользуется на реальных заказах. Первый срез — «КП за час» — не требует ни моста, ни дизайн-мейкера, ни ERP. Это не отменяет решение «менеджеры входят, когда готово всё»: до общего пилота в Order работает только владелец, как он и планировал, просто начинает раньше.

### 1.2 В PinheadOS нет движка PDF
Проверено по коду: ТЗ в PDF сегодня **загружается менеджером как готовый файл** (`CreateOrderModal`, `application/pdf`), а «Печать / PDF» в Order Studio — это HTML и `window.print`. КП, ТЗ и тех-лист из данных — три документа этапа B — упираются в решение, которого нет. В дизайн-мейкере движок есть: jsPDF + svg2pdf с кириллицей (LiberationSans), проверен на тех-листах.

**Что делать:** решить движок в этапе 0, до любой вёрстки документов. Рекомендация — **клиентский jsPDF + svg2pdf из дизайн-мейкера**: уже работает с кириллицей и векторами, не требует серверного Chromium, а перенос этого модуля всё равно запланирован. Минус — вёрстка сложных многостраничных ТЗ на jsPDF трудоёмка; для ТЗ допустим второй путь — HTML-шаблон → PDF в edge-функции. Спайк на 1 сессию: собрать ТЗ «Дзен Арктика» обоими путями и сравнить.

## 2. Серьёзные узкие места

### 2.1 Этап A перегружен
В A сейчас: новая модель данных (12 таблиц), RLS «только свои» с исключениями, карточка + визард, сетка, четыре типа продукции с анкетой разработки, варианты двух уровней, платежи, статусы, копии и шаблоны, задачи, чат, архив. Это 60 % всего объёма в одном этапе без промежуточной проверки. Каждая из этих вещей по отдельности — сессия-две.

**Что делать:** резать A на срезы (раздел 4). Первый срез — только пошив по SKU, одна ткань, сетка, ручные мм, цена, один шаблон КП. Бланки, давальческое, разработка, варианты, шаблоны — следующие срезы.

### 2.2 Дизайн-мейкер — самый рискованный кусок, а спайка нет
Перенос react-konva 18 → React 19, zustand 4 → 5, Next.js → Vite, zod-схемы → типы PinheadOS, свой Supabase → `erp_sku_cards`, флэты на размер, раскладка цвет × группа. Ни одна из этих связок не проверена. Если konva не дружит с React 19 или бандл холста ломает бюджет CI (206 КБ gzip оболочки), это узнается в середине этапа C.

**Что делать:** спайк на 1 сессию в этапе 0: пустой холст konva внутри PinheadOS под флагом, один флэт FreeFit, лениво, замер бандла. Если красный — план C меняется до того, как на него завязали B.

### 2.3 Люди: один дизайнер, один технолог, один владелец
- **Дизайнер один** — и на него ложатся раскладки, макеты и подготовка к печати всех 50+ расчётов в неделю. Очередь по времени создания без приоритета по дедлайну означает, что срочный заказ ждёт за несрочными.
- **Технолог** одновременно: проверяет ТЗ пошива и разработки, ведёт SKU, ткани и зоны, заводит флэты на размер для 35 моделей (с конструктором). Это месяцы контентной работы поверх основной.
- **Владелец** — единственный, кто принимает решения и единственный тестировщик до пилота.

**Что делать:** в очереди дизайнера всё же показывать дедлайн заказа и давать РОПу поднимать задачу (ты выбрал «по времени создания», но без ручного подъёма срочный заказ встанет). Флэты на размер — не условие пилота: система работает на базовом + градации. Тест-кейсы — эталонные заказы, чтобы проверка не лежала только на владельце.

### 2.4 Мост стоит четвёртым, а проверяет он первое
Приоритет владельца: сетка и поля → документы → дизайн-мейкер → мост. Но именно мост проверяет, что модель данных Order совпала с контрактом ERP. Если расхождение всплывёт после C, переделывать придётся A и B. При этом сам запуск дешёвый: форма ERP переиспользуется, пишется только предзаполнение.

**Что делать:** контракт (этап 0 моста) — сразу; **минимальный запуск** (кнопка → предзаполненная форма ERP) — во втором срезе, до дизайн-мейкера. Порядок ценности не меняется: сетка и поля всё равно первые.

## 4. Улучшенный план: сквозные срезы

Принцип: каждый срез заканчивается реальным заказом, прошедшим через новое.

| Срез | Содержание | Что проверяет владелец | Сессий (оценка) |
|---|---|---|---|
| **0. Фундамент** | Эталонные заказы → тесты · спайк PDF (jsPDF vs edge) · спайк konva в React 19 · контракт `tzToErpDraft` (читает ERP, не пишет) · `order_dictionaries` | Ничего в интерфейсе; три решения по спайкам. ERP не трогается (аксиома 28.09) | 3–4 |
| **1. КП за час** | `order_items` + сетка цвет × размер · карточка + визард только для пошива по SKU · ткань с поставщиком · нанесения с ручными мм и Pantone · бирки из библиотеки · упаковка · цена с наценкой по позиции, ручная цена и порог · один шаблон КП в PDF · автосохранение и офлайн · «только свои» | **Владелец считает реальные КП в новом Order** вместо Excel | 8–10 |
| **2. ТЗ и запуск** | Чек-лист полноты ТЗ · ТЗ PDF из данных · текст ТЗ · платежи · статусы `paid`/`tz_ready`/`ready_to_launch` · согласование цены в чате · чат сделки · кнопка запуска → форма ERP · `done` по складу ГП · ТЗ только для чтения | **Первый заказ уходит в производство без ручного ввода в ERP** | 8–10 |
| **3. Все типы и повторы** | Бланки, давальческое, разработка с анкетой · образцы и авто-тираж · варианты двух уровней · копии и шаблоны · задачи дизайнеру и технологу · проверка технолога · правила сроков и календарь · уведомления · переделки и отмена по запросу | Второй менеджер подключается к пилоту | 8–10 |
| **4. Дизайн-мейкер** | Перенос модуля · флэты в карточки (35 SKU, базовый размер) · раскладка цвет × группа · «Применить к ТЗ» · превью в КП · тех-лист · редактор лекал · старый мейкер выключается | Раскладка в реальных КП и ТЗ | 10–12 |
| **5. Зрелость** | Шаблоны КП (3), онлайн-ссылка с открытием, аналитика и экспорт, вход по роли, снятие флага, статус для клиента | Весь отдел | 5–6 |

Итого 43–53 сессии — столько же, сколько по слоям, но с проверкой после каждого среза вместо одной в конце.

### Что срез-план меняет в решениях владельца
- Пилот «когда готово всё» → владелец один начинает со среза 1, отдел — после среза 3. Отдел это решение не затрагивает.
- Мост поднимается со 4-го места на 2-е — только его кнопка; сетка и поля остаются первыми.
- Дизайн-мейкер уходит на 4-е место, потому что до него всё работает на ручных мм (ты сам разрешил).

2. Движок PDF — спайк обоими путями в срезе 0, выбор по результату.
3. Очередь дизайнера — по дедлайну заказа автоматически.
