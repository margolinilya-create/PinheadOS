# Спека: срез 0 — фундамент Order v4
**Статус:** согласовано владельцем 27.09; пересобрано 28.09 под аксиому «ERP не трогаем»
**Основание:** `docs/erp/2026-09-27-order-v4-structure.md` (разделы 5, 5.1, 8), `2026-09-27-order-v4-plan-review.md`, `2026-09-26-tz-bridge-spec.md` (этап 0)

---

## 0. Аксиома

ERP — рабочий продукт. В этом срезе **ни одной правки** в `src/erp/`, ни одной миграции в `erp_*`, ни одного нового вида в `erp_dictionaries`. Из ERP — только чтение (импорт типов и `DraftForm`, SELECT справочников). Всё, что ERP однажды должна будет принять от Order, — раздел 5.1 структуры, отдельными решениями владельца.

**Сторож аксиомы — первый PR среза:** тест, который падает, если ветка Order v4 меняет файлы под `src/erp/` или добавляет миграцию, трогающую `erp_*` (кроме `SELECT`/`grant select`).

---

## 1. Цель и пользователь

Снять технические неизвестные до срезов 1–4 и закрепить контракт данных Order → ERP тестами. Интерфейс не меняется. Пользователь — разработка и владелец, который принимает решения по спайкам.

**Готово, когда:** сторож аксиомы зелёный и проверен мутацией; эталонные тесты цены зелёные; контракт `tzToErpDraft` покрыт тестами со сторожем полноты; `order_dictionaries` в базе; два отчёта спайков с рекомендацией.

## 2. Работы

### 2.1 Сторож аксиомы (PR 1)
Чистая функция-классификатор `src/orderstudio/erpBoundary.ts`: по списку изменённых путей и тексту новых миграций отвечает, задевает ли изменение ERP. ERP — это `src/erp/**`, **все модули вне `src/erp/`, которые импортирует `src/erp/`** (список выводится обходом импортов, а не константой — иначе отстанет), и миграции с DDL по `erp_*`. Нарушение = одно изменение трогает и Order (`src/orderstudio/**`, модули только Order Studio, таблицы `order_*`), и ERP. Тест классификатора (node-среда) с мутациями: правка `src/erp/types.ts`, правка `components/Button.jsx`, миграция `alter table erp_orders` — каждая в паре с файлом Order → красный. Применение в CI — шаг в `ci.yml` для PR: `git fetch --depth=1 origin $GITHUB_BASE_REF` + `node scripts/order-erp-boundary.mjs` (checkout по умолчанию неглубокий, без fetch сторож был бы зелёным вслепую). ERP-only PR (пункты 5.1 после «да» владельца) проходят — они не трогают Order.

### 2.2 Эталонные заказы → тесты (PR 2, ждёт файлов владельца)
3–5 реальных заказов: PDF ТЗ + итоговая цена + сетка. Для каждого:
- фикстура `src/orderstudio/fixtures/<slug>.json` — заказ в модели v4;
- снапшот-тест `calcTotal`: та же цена с допуском округления до 5 ₽; ручная цена в оригинале помечается в фикстуре явно, формула не подгоняется;
- те же фикстуры питают контракт моста и спайк PDF.

### 2.3 Контракт моста — `tzToErpDraft` (PR 3)
`src/orderstudio/bridge/tzToErpDraft.ts` — чистая функция: заказ v4 → `DraftForm` из `erp/utils/orderForm.ts` (**только импорт типа**). Маппинг — данными (`bridge/mapping.ts`), не ветвлениями: методы нанесения, зоны, бирки, упаковка, типы продукции, источник изделия.
- DTG: пока ERP не принял пункт 5.1 «DTG как подряд», позиция с DTG мапится с `method = 'dtg'` и **явным предупреждением контракта** «в ERP нет участка DTG — этап не создастся»; тест это фиксирует.
- Цена продажи: пока ERP не принял пункт 5.1, контракт её **не передаёт**; поле отмечено в `NOT_TO_ERP` с причиной.
- **Сторож полноты:** каждое поле `DraftItem`/`DraftForm` либо имеет источник в маппинге, либо перечислено в `NOT_FROM_ORDER` с причиной (`launch_date`, поля закупщика). Новое поле ERP без решения роняет тест. Мутация: убрать строку маппинга → красный.
- Тесты — граничные случаи спеки моста (раздел 6) + эталонные фикстуры.

### 2.4 Справочники Order (PR 4)
Миграция: `order_dictionaries (id, kind, code, name, meta jsonb, active, sort, created_at)`, уникальность `(kind, code)`; виды `blank`, `print_zone`, `print_place`, `label_type`, `label_place`, `packaging_kind`, `packaging_insert`, `pantone`. RLS: чтение — вошедшим; запись — `admin`/`director` через `is_admin()` и `rop` по `profiles.role`; политики на команду, `(select …)`-обёртки (правила кода `CLAUDE.md`). Сиды — из констант Order Studio (`data/*.js`). Только аддитивно; `erp_*` не упоминается.

### 2.5 Спайк PDF (ветка без мержа)
ТЗ «Дзен Арктика» двумя путями: **A** — jsPDF + svg2pdf, кириллица LiberationSans (движок из `PNHD-design-maker/lib/export`); **B** — HTML-шаблон → edge-функция → PDF. Отчёт `docs/erp/2026-09-27-pdf-spike.md`: время, размер, кириллица и векторы, многостраничность, трудоёмкость, стоимость. Рекомендация одним предложением. Новые npm-зависимости — только в ветке спайка, в `main` — после решения владельца.

### 2.6 Спайк konva (ветка без мержа)
Под флагом `orderStudio`, в `src/orderstudio/`: холст react-konva, один флэт FreeFit, перекраска, ленивая загрузка. Проверить: react-konva + React 19 + Vite 7, zustand 5, бюджет бандла CI (оболочка ERP не растёт — отдельный чанк), тач. Отчёт `docs/erp/2026-09-27-konva-spike.md`: переносить как есть / с заменой / отказаться.

## 3. Граничные случаи
- Фикстура с ручной ценой — тест помечает, не подгоняет формулу.
- Два цвета одной модели — одна позиция, сетка из нескольких строк.
- DTG — контракт возвращает предупреждение, не падает.
- Аксессуар без ткани и без нанесений — `purchase[]` пуст, контракт не падает.
- Новое поле в `DraftItem` — сторож полноты красный.
- Правка в `src/erp/` в ветке Order — сторож аксиомы красный.

## 4. Не входит
Интерфейс Order (срез 1), перенос дизайн-мейкера (срез 4), **любые изменения ERP** (раздел 5.1 структуры), статусы `orders`, Bitrix.

## 5. Открытые вопросы
Нет. Решения по спайкам — владелец по отчётам. Пункты 5.1 — владелец отдельно, в своих срезах.
