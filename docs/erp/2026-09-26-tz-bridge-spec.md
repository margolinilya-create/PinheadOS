# Спека: мост «Заказ (Order) → Производство (ERP)»
**Статус:** согласовано владельцем 26.09, готово к этапу 0 · 26.09.2026

---

## 1. Цель и пользователь

**Цель.** Менеджер отдела продаж ведёт заказ целиком в Order: считает, подбирает продукцию и получает ТЗ почти автоматически, заполняя поля и выбирая значения из библиотек. После оплаты заказ запускается в производство, и ERP получает его без повторного ввода.

**Главный принцип.** Эталон — ERP. Форма создания производственного заказа (`erp/utils/orderForm.ts`, `DraftForm` / `DraftItem`) и RPC `erp_create_order` и есть контракт. Order обязан выдавать данные, которые ERP принимает без ручной доработки. ERP под Order не подстраивается.

**Пользователи**
| Кто | Что делает в мосте |
|---|---|
| Менеджер продаж | Считает заказ, собирает ТЗ, отмечает оплату |
| Менеджер сопровождения | Проверяет ТЗ и **запускает** заказ в производство (решение 26.09) |
| Диспетчер, руководитель производства | Получают заказ в ERP, ставят в план |
| Цех | Видит полное ТЗ в задании, как сейчас |

**Что это даёт бизнесу:** один ввод вместо двух (Excel/PDF → форма ERP), меньше ошибок ТЗ (Pantone, размер и место нанесения, ткань, фурнитура, упаковка — все значения из библиотек), быстрее путь от заявки до запуска.

---

## 2. Что уже есть

**Сервер (готово, миграция `20260818203459`):**
- `erp_orders.tz_order_id → orders.id` (`on delete set null`) + `tz_number` текстом: цех не видит `orders` по RLS;
- `orders.erp_order_id → erp_orders.id` — подсказка интерфейсу;
- уникальный индекс `erp_orders_tz_order_uniq`: из одного ТЗ нельзя создать два производственных заказа;
- `erp_create_order(payload)` принимает `order.tz_order_id`.

**Клиент:** ничего. Связанных заказов на бою — 0.

## 3. Разрыв: что ERP требует, а Order не собирает

| Поле ERP | Есть в Order? | Как закрыть |
|---|---|---|
| **Шапка:** `customer`, `manager`, `due_date`, `bitrix_id`, `title` | Да: клиент, дедлайн, сделка | Маппинг; `title` собирается из клиента и позиций |
| `launch_date` | Нет | Ставит тот, кто запускает |
| Упаковка заказа: `packaging`, размер в мм, `stickers`, `no_chestny_znak` | Частично: БОПП / ZIP / без | Добавить стикеры, «без Честного знака», размер пакета из библиотеки |
| `purchase_required` | Нет | Галочка, по умолчанию — да |
| **Позиция:** `production_type` | Нет | Выбор на шаге «Изделие»: пошив / готовое изделие / только нанесение / крой; значение по умолчанию — из категории SKU |
| `garment_source` (купим / давальческое / со склада ГП) | Нет | Показывается только для «готового изделия» |
| `sku_card_id` | Нет | Подставляется по `code` SKU, если карточка модели есть |
| `main_fabric`, `color_supplier`, `fit`, `trim_material` | Да | Маппинг |
| **Размерная сетка цвет × размер** | Один цвет на позицию + размеры | Позиция Order = одна строка сетки. Несколько цветов одной модели — несколько позиций. Сетку в Order не делаем в первой версии |
| **Нанесения** `prints[]`: метод, зона, ширина и высота в мм, отступ, Pantone, эффект, «на крое / на готовом» | Метод, зона, формат A4/A3, цвета, эффект | Добавить: мм (по умолчанию из формата, правится), место и отступ из библиотеки мест, Pantone по цвету, «на крое / на готовом» |
| **Бирки** `labels[]`: тип, место, размер | Конфигуратор: составник / основная / хэнгтег | Маппинг типов + выбор места притачивания из библиотеки |
| **Закупка** `purchase[]` | Нет, но есть расход ткани и отделки у SKU | Черновые строки: основная ткань (расход × тираж), отделка, фурнитура из обработок. Закупщик доводит в ERP |
| Заметки кроя, пошива, бирок | Нет | Необязательные текстовые поля у позиции |
| Файлы: превью, макеты, ТЗ-PDF | Путь к макету | Этап 3 плана |

**Методы нанесения:**
| Order | ERP |
|---|---|
| Шелкография | `silkscreen` |
| Вышивка | `embroidery` |
| DTF | `dtf` |
| Флекс | `heat_transfer` (цех ДТФ) |
| DTG | **Подряд** (решение 26.09): этап у подрядчика, операция «DTG-печать», передача и приёмка через склад |

## 4. Библиотеки: один источник значений

Всё, что ERP проверяет или по чему считает, Order читает из справочников ERP, а не из своих констант. Иначе значения разойдутся на второй неделе.

| Что выбирает менеджер | Источник |
|---|---|
| Модель, ткань, цена | `app_config` / `catalog_config` («сколько стоит») |
| Карточка модели | `erp_sku_cards` по `code` («как шьётся») |
| Тип изделия, крой, поставщик, единицы | `erp_dictionaries` |
| Место нанесения и отступ, место бирки, типы бирок, упаковка, стикеры | Новые виды `erp_dictionaries`, правятся в админке ERP |
| Формат → мм | Таблица в справочнике: A6 / A5 / A4 / A3 / A3+ → ширина и высота по умолчанию |

## 5. Статусы и запуск

Статусы Order получают бизнес-смысл, без новых значений в CHECK:

| Статус | Смысл | Кто ставит |
|---|---|---|
| `draft` | Расчёт, КП | Менеджер |
| `review` | ТЗ собрано, на проверке | Менеджер |
| `approved` | **Оплачен**, можно запускать | Менеджер отмечает оплату (позже — из Bitrix) |
| `production` | Производственный заказ создан | Система, в момент создания |
| `done` | Заказ в ERP завершён | Система, по статусу ERP |

**Запуск (версия 1).** На заказе в статусе `approved` есть кнопка «Запустить в производство». Она открывает форму создания заказа ERP, **заполненную из ТЗ**. Запускающий проверяет, ставит дату запуска и превью маршрута, жмёт «Создать». Уходит `erp_create_order` с `tz_order_id`, ТЗ переходит в `production`.

Почему форма, а не одна кнопка: ERP-форма уже валидирует, строит превью маршрута и загружает файлы. Одна кнопка повторила бы всё это второй реализацией. Когда предзаполнение месяц идёт без правок, можно добавить быстрый запуск.

## 6. Сценарии и граничные случаи

1. **Обычный.** Расчёт → ТЗ → оплата → запуск → заказ в очереди закупки или склада.
2. **Двойной клик / два человека запускают одновременно.** Второй получает отказ по уникальному индексу, и интерфейс показывает ссылку на уже созданный заказ.
3. **Правка ТЗ после запуска.** В `production` ТЗ в Order только для чтения. Изменения идут в карточке ERP и в чате сделки. Обратная синхронизация правок не делается.
4. **Производственный заказ удалён.** `tz_order_id` обнулится, ТЗ возвращается в `approved` при следующем открытии. Известная ловушка: удалить связанный заказ ТЗ без права `order.manage` нельзя (сессия 68) — проверить права ролей до выката.
5. **Запуск без оплаты** (постоянный клиент, срочно). Разрешён тем, у кого есть право обхода, с обязательной причиной; причина пишется в аудит.
6. **Старые заказы Order** без типа производства и мм — предзаполнение даёт пустые поля, форма ERP подсвечивает их как незаполненные. Не падать.
7. **Позиция без SKU** (старый формат `type`) — запуск разрешён, `sku_card_id` пуст.
8. **Аксессуары и носки** (без ткани / без нанесения) — ткань в закупку не попадает, нанесений ноль.
9. **Отмена в ERP** — ТЗ показывает «отменён в производстве», статус не меняется сам.

---

## 7. Не входит

- Покупательский портал (отдельная спека, стартует после моста).
- Интеграция Bitrix24: оплата отмечается вручную.
- Сетка «много цветов × размеры» внутри одной позиции Order.
- Обратная синхронизация правок ERP → ТЗ.
- Изменения маршрутной логики ERP, кроме одного: нанесение DTG строит этап подряда (раздел 8, решение 3).

---

## 8. Решения владельца (26.09)

1. **Запускает менеджер сопровождения.** Менеджер продаж отмечает оплату, менеджер сопровождения проверяет ТЗ и нажимает «Запустить в производство» (право ERP `order.manage`). Диспетчер и руководитель производства тоже могут — у них это право есть. Кнопка у менеджера продаж не показывается.
2. **Цена продажи передаётся в ERP** и видна в «Экономике позиции» по праву `economics.view`. Нужна колонка цены продажи у позиции `erp_order_items` (аддитивная миграция, страж позиции её охраняет по умолчанию — он на исключениях). В экономике появляется маржа: цена продажи − себестоимость.
3. **DTG остаётся в Order и уходит в ERP как подряд.** Сейчас `BRANDING_DEPT.dtg = null` — нанесение DTG этапа не создаёт. Правка маршрута: нанесение с методом `dtg` строит этап участка «Подряд» с операцией «DTG-печать» (`executor = contractor`), «на готовом» после базовой цепочки; передача и возврат идут складскими задачами, как у любого подряда. Подрядчик выбирается в ERP при запуске. Тесты `routes.test.ts` дополняются этим случаем.

4. **Вход по роли** (этап 4, после снятия флага). Роль учётной записи `manager`, `rop` → Order; `production`, `designer` → ERP; `admin`, `director` → ERP. Переключатель в шапке остаётся у всех, кому доступны оба раздела. Менеджер сопровождения попадает в Order — там его рабочая очередь: оплаченные заказы, ждущие запуска. Логика — одна чистая функция `landingSection(profile)` с тестами; флаг `orderStudio` удаляется вместе с ветками в коде.

Открытых вопросов нет.

## 9. План (каждый этап — отдельный PR)

**Этап 0 — контракт без интерфейса.**
Миграция: цена продажи у позиции. Правка маршрута: DTG → этап подряда. Чистая функция `tzToErpDraft(order, catalogs) → DraftForm` + таблица маппинга методов, зон, бирок, упаковки. Тесты на каждый граничный случай раздела 6. Сторож: поле, добавленное в `DraftItem`, без решения в маппинге роняет тест.

**Этап 1 — Order собирает то, что нужно ERP.**
Тип производства и источник изделия; нанесения в мм, место и отступ, Pantone, «на крое / на готовом»; места бирок; стикеры, «без ЧЗ», размер упаковки; заметки кроя и пошива; галочка закупки. Все значения — из справочников ERP. Новые виды справочников в админке ERP.

**Этап 2 — запуск.**
Смысл статусов, отметка оплаты, кнопка «Запустить в производство» → форма ERP с предзаполнением и `tz_order_id`. ТЗ только для чтения после запуска, ссылки в обе стороны, обход без оплаты с причиной. E2E: расчёт → оплата → запуск → заказ в очереди.

**Этап 3 — файлы и ТЗ-PDF.**
Загрузка макетов в Storage прямо в Order, генерация ТЗ-PDF в формате цеха → `erp_tz_documents` при запуске.

**Этап 4 — замыкание.**
Статус `done` по завершению в ERP, снятие флага, вход по роли.

**Критерий готовности моста:** менеджер оформляет реальный заказ от расчёта до запуска, и в ERP ничего не вводится руками, кроме даты запуска.
