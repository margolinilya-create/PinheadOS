## Решения контроллера (с выбором и отвергнутыми вариантами)

### К1. Где лежит PDF ТЗ в `order-artworks` — `artworkPath(orderId, 'tz', name)`, хэш содержимого в имени
- Путь: `orders/<id>/tz/<uuid>-<PH-XXXX>-g<groupHash8>-c<contentHash12>-<model-ascii>.pdf`. Его строит существующая `artworkPath`; он проходит `order_artwork_path_ok` и политику `order_artworks_insert`.
- **Хэши — в начале имени.** `artworkPath` пропускает имя через `asciiFileName`, а тот режет основу до 100 знаков. Длинное имя модели в конце обрежется, хэши останутся. `tzFileName` держит основу ≤ 100 знаков до расширения. `hashFromTzPath` ищет `-g<8hex>-c<12hex>-`, а не конец имени.
- `contentHash12` — первые 12 hex sha-256 канонического JSON модели `tzDocument` (см. К3) плюс версия раскладки `TZ_LAYOUT_V`.
- **В хэш не входят `header.issuedOn` и `footer.link`.** Их убирает `canonicalTzForHash` (явный список `TZ_HASH_EXCLUDE` с тестом), иначе хэш менялся бы от даты и адреса сборки.
- **Дайджест — зависимостью** `digest`, по умолчанию `globalThis.crypto?.subtle`. В jsdom 29 `crypto.subtle` нет, а в браузере он есть только в безопасном контексте. Нет дайджеста — отказ «Отправка недоступна: браузер не дал криптографию (откройте сайт по https)».
- Путь пишется в `tz_pdf_path` **каждой** позиции группы.
- UPDATE в бакете запрещён (`order_artworks_no_update`), поэтому новая версия получает новый ключ — это и есть неизменяемый снимок. Старые файлы остаются историей возвратов.

Отвергнуто:
- путь спеки `order-artworks/tz/<order>/<groupKey>.pdf` — не проходит `order_artwork_path_ok` и политику INSERT (нужен `orders/<uuid>/…`);
- `upsert` с постоянным именем — UPDATE запрещён restrictive-политикой, и снимок перестал бы быть неизменяемым;
- новая колонка «хэш ТЗ» у позиции — новая колонка `order_items`, правка `order_v4_save` и пара «клиент + миграция» с подъёмом `SALES_CLIENT_REV`. Хэш в имени даёт то же без DDL.

### К2. PDF собирается при «Отправить в работу», а не заранее
- Загрузка в бакет разрешена только черновику (живая политика). Поэтому PDF всегда собирается и грузится **внутри** цепочки отправки, пока заказ в `draft`.
- Если хэш модели группы совпал с `-c<hash>` в уже записанном `tz_pdf_path`, PDF не пересобирается и не грузится повторно. Повторная отправка после возврата без правок файлов не плодит — в любой день и с любого адреса (К1). Дата оформления в таком PDF — дата первой сборки этой версии (снимок, решение 21).
- Пункт спеки «PDF сформирован после последней правки» выполняется сам собой, отдельного пункта чек-листа нет.
- Кнопка «Предпросмотр ТЗ» собирает PDF в память и **ничего не грузит**. Браузеры (особенно Safari на iPad) блокируют `window.open` после `await`. Поэтому по готовности на месте кнопки появляется ссылка «Открыть ТЗ 1 из 3 (PDF, 1,2 МБ)» (`target=_blank`, человек жмёт сам) и «Скачать». Object URL отзывается при уходе со вкладки или при новой сборке, а не по таймеру (T5).

Отвергнуто:
- кнопка «Сформировать ТЗ» с загрузкой и пункт чек-листа «PDF устарел» — лишний шаг человеку и лишние сироты в бакете;
- проверка свежести по `updated_at` — сохранение `tz_pdf_path` само его сдвигает.

### К3. Группа ТЗ — `tzGroupKey(item)` с цветами деталей
- Ключ: модель (`sku_code`, иначе `client_pattern` в нормализованном виде) + ткань (`fabric_code` / `main_fabric`) + `part_colors` (канонически, по детали) + набор нанесений.
- Набор нанесений — отсортированный список `(zone, method, width_mm, height_mm, artwork_path)`. Цвет позиции **не входит**: «Копия в другом цвете» сохраняет группу (спека, 6.1).
- Позиции группы идут строками сетки ЦВ/РАЗМ. Разный `tz_comment` печатается по цветам: «Чёрный: …», «Белый: …». Одинаковый — один раз.
- Порядок групп и позиций — порядок `order.items`. Номер ТЗ «k из m» — по первой позиции группы.

Отвергнуто:
- ТЗ на заказ целиком — у образца 68180 три отдельных ТЗ;
- `tz_comment` в ключе — одна модель распалась бы на ТЗ по цветам из-за комментария;
- без `part_colors` — у колорблока разных цветов деталей в одном ТЗ печатался бы только первый.

### К4. Тексты в PDF — только текстовым API jsPDF; SVG — только мокапы сцены
- Шапка, таблицы, сетки, бирки, заметки, подвал — `pdf.text`, `pdf.rect`, `pdf.line` по прямоугольникам из чистой `layoutTz`.
- Мокапы нанесений — существующие `buildSceneSvg` → `sanitize` сцены → `svg2pdf(el, pdf, {x, y, width, height})` в прямоугольник ячейки.
- Фото (бирки, стикер, заметки, растровые макеты) — `pdf.addImage(JPEG|PNG)` после `sniffArtwork` сигнатуры (`design/assets/sniff.ts`). Растр ужимается до 200 dpi по ячейке на `canvas` (`toBlob('image/jpeg', 0.85)`). PNG с прозрачностью (макет на цвете ткани) остаётся PNG.
- Ссылки карточек — `pdf.textWithLink` только при `isSafeHttpUrl(url)`. Функции на HEAD нет, её создаёт T2 в `tz/model/safeUrl.ts`: разбор `new URL`, только `http:`/`https:`, без пробелов и управляющих знаков. Прочее печатается текстом без ссылки.
- Правило вехи 4 «тексты справочников в PDF — только текстовым API» соблюдено, XSS через SVG-строку исключён.

Отвергнуто:
- всё ТЗ одной SVG-сценой — тексты справочников попали бы в SVG-строку (против правила вехи 4), а мелкий текст и переносы пришлось бы считать в SVG;
- `pdf.html` — запрещён сторожем.

### К5. Общий движок — `design/export/pdfCore.ts`
- Из `exportPdf.ts` выносятся без изменения поведения: `loadPdfFonts`, `registerFonts`, `ensureMeasureFonts`, `sceneElement`, `pageMm`, `SCENE_IMAGES`, константы шрифтов.
- Новые функции:

- `pdfCore.ts` — **единственный** файл с импортами `jspdf` и `svg2pdf.js`.
- Статически его импортируют ровно два движка: `design/export/exportPdf.ts` и `tz/pdf/tzPdf.ts`. Движки грузятся только `import()` из своих загрузчиков: `design/ui/panel/maketExport.ts` и `tz/ui/tzExport.ts`.
- Сторож `pdfGuards.test.ts` переписывается под эту схему одним коммитом с выносом.

Отвергнуто:
- второй разрешённый файл с собственной копией шрифтов и регистрации — две копии кода, расходящиеся в мелочах (уже ловилось на `sourceFiles`);
- движок ТЗ внутри `exportPdf.ts` — смешал бы два документа и раздул чанк макета.

### К6. Мокап мелко — масштаб вывода в `buildSceneSvg`
- Новый необязательный параметр `SceneInput.outputScale` (мм листа ТЗ на мм сцены). По умолчанию 1 — макет 5а побайтно прежний, это сторожит существующий тест сцены.
- Размер шрифта подписей, толщина размерных линий и отступы легенды делятся на `outputScale`. В PDF они выходят не мельче 7 pt и 0,25 мм.
- Легенда в ячейке мокапа ТЗ не рисуется (`legend: []`): подписи нанесения и так в таблице страницы.

Отвергнуто: растр мокапа — у цеха пропали бы векторные мм, файл вырос бы.

### К7. Матрица «зона × техника» — строка из 5б, столбец `tzColumnOf`
- Строка:
  - нанесение на холсте — `tzRowOfArea(flatAtVersion(flat, layout.flat_version).area)`;
  - нанесение строкой — `tzRowOfZone(zonesCatalog по имени зоны)`;
  - зона без строки — `other` с текстом «Другое: <зона>».
- Столбец — новая чистая `tz/model/tzColumns.ts → tzColumnOf(method, contractor)`:
  - `silkscreen` → Ш, `embroidery` → В, `dtf`/`transfer`/`flex` → Т (по факту `METHOD_LABELS` — сверка в T2), `dtg` → DTG;
  - `other` или непустой `contractor` → П при **любой** технике (решение 23 плана 5б).
- Сторож: каждый ключ `METHOD_LABELS` имеет столбец (`Record<SalesPrintMethod, …>` — тип из `model/types.ts:41`, тест на полноту).
- `order_item_prints.zone_id` не заводим (бэклог вехи 8): имя зоны неизменно после сохранения (5б, решение 5), поиск по имени устойчив. План 5б (решение 5) относил `zone_id` к вехе 6 — перенос записан в «Решено за владельца» (п. 44): новая колонка `order_item_prints` требует правки `order_v4_save` и пары «клиент + миграция», а матрице ТЗ хватает имени.

### К8. Комментарий заказа (`orders.notes`) — не в 6+7
- У `SalesOrder` нет поля `notes`, `order_v4_save` его не пишет, у всех v4 он пуст (проверено).
- Первая страница печатает `tz_comment` позиций группы (К3).
- Поле «Комментарий к заказу» во вкладке «Клиент» и печать под комментарием позиции — бэклог вехи 8. Ключ `notes` пишется в `order_v4_save` только при наличии ключа (`p_order ? 'notes'`), поэтому ревизия клиента не поднимается.

Отвергнуто: правка `order_v4_save` в J — самая большая функция заказа и правило «пара клиент + миграция» ради пустого поля.

### К9. QR в подвале — нет; ссылка текстом
- Своего QR у jsPDF нет, нужна новая npm-зависимость, а владелец разрешил только уже добавленные.
- Подвал: `tzSettings.footerText` · `PH-XXXX · ТЗ k из m · стр. i/n` · `<APP_ORIGIN>/sales/<id>` текстом. `APP_ORIGIN` — константа из `VITE_APP_ORIGIN` (прод-адрес), а не `location.origin`: ТЗ, собранное на превью-деплое или на localhost, не напечатает чужой адрес.

### К11. Переполнение — `fitText`, страница «Продолжение»

### К12. Копии в ERP — при запуске клиентом МС, по копии на позицию ERP, случайные ключи попытки
- **Ключи без id заказа и номера.** Каждая попытка запуска берёт `attemptId = crypto.randomUUID()` (через `deps.randomId`).
  - ТЗ: `tz/v4-<attemptId>/<groupId>/v1-tz.pdf`.
  - Макеты: `att/v4-<attemptId>/<kind>/<uuid>.<ext>`. Здесь `uuid` — новый `crypto.randomUUID()` на файл, а не `print_key`.
  - Человеческое имя (`PH-XXXX-<модель>…`) — только в `file_name` строки.
  - Ключ не раскрывает uuid заказа v4 и номер и не угадывается заранее.
- **ТЗ.**
  - PDF группы скачивается `downloadArtwork` **один раз** и проверяется на сигнатуру `%PDF-`.
  - Из одного `Blob` грузится N копий — по копии на каждую позицию ERP группы. Позиция ERP — индекс в `payloadItems(draft.items)`, сопоставление по ключу позиции v4. `groupId` — новый uuid на копию.
  - Затем — `tz.documents[{group_id, item_index, file_path, file_name, mime_type: 'application/pdf', size_bytes, uploaded_by}]`.
- **Тип файла — только по сигнатуре байт** (`sniffArtwork`), никогда из `Blob.type`, расширения или меты:
  - `%PDF-` → `application/pdf`, PNG → `image/png`, JPEG → `image/jpeg`, `%!PS` → `application/postscript`;
  - SVG распознаётся по байтам (`<svg`/`<?xml`) и идёт **только** через `planSvgLogo`/`sanitizeSvg` в режиме логотипа: загружается очищенный текст с типом `image/svg+xml`. Не очистился — копируется только `.preview.png` (тоже по сигнатуре), если он есть, иначе отказ шага с номером нанесения;
  - расширение ключа приводится к распознанному типу;
  - сигнатура не совпала с объявленным видом (ТЗ не `%PDF-`, «PNG» с байтами HTML или SVG и т. п.) — отказ шага с номером нанесения;
  - у PDF/AI-макета копируется и `.preview.png`.
- **Секция `attachments`:** `[{item_index, material_index: null, print_key, file_path, file_name, kind: 'print'}]`; для превью бирок — `label_key` и `kind: 'label'`.
  - Ключи `print_key`/`label_key` в номер **переводит стор ERP** (`orderWriteSlice.ts:223–245`, карты `printKeyIndex`/`labelKeyIndex`). Живая `erp_create_order` знает только `print_index`/`label_index`. Файл с неизвестным ключом стор **молча выбрасывает** (`return null` → `filter`).
  - Поэтому ключи берутся ровно из `draft.items[i].prints[j].key` / `labels[j].key` — тех же объектов, что уходят в `createOrder`, а не из `order.items`.
  - После `createOrder` шаг `finish` читает `erp_order_attachments` с `kind in ('print','label')` по `order_id` и сверяет число с планом. Расхождение — предупреждение в итоге «N макетов не привязались к нанесениям — проверьте в производстве». Это не отказ: заказ уже создан.
- **Ключи `erp-attachments`** строит `bridge/erpKeys.ts` (`erpTzKey`, `erpAttachmentKey`) на общем `utils/asciiFileName.ts` — он уже копия `safeFileName` ERP со своим тестом паритета. ERP-утилиты мост импортировать не может.
  - Тест паритета сверяет с `tzFilePath`/`attachmentFilePath` **только префикс (`tz/`, `att/`) и ASCII**.
  - Тесты сторож импортов не обходит: `sourceFiles` по умолчанию без `.test.` (проверка в T0).
- **Писатель `erp-attachments` из Order** — один файл `orderstudio/api/erpFiles.ts`:
  - только `upload`, `upsert: false`;
  - только ключи `^(tz|att)/v4-<uuid>/…` в ASCII;
  - `contentType` — только из белого списка `ERP_FILE_TYPES` (`application/pdf`, `image/png`, `image/jpeg`, `image/svg+xml`, `application/postscript`);
  - предел 20 МБ до запроса;
  - **409 Duplicate — не успех:** отказ шага «Файл с таким именем уже есть в производстве — повторите запуск». Повтор запуска идёт с новым планом ключей (новый `attemptId`), а не по старым;
  - сторож `erpFilesWrites.test.ts`.
- **Сироты** сорвавшейся попытки (файлы есть, `erp_create_order` откатился) уберёт `storage-gc`: он обходит бакет с корня (`listAll('')`), носители — `erp_tz_documents`/`erp_order_attachments`, гейт по возрасту.

Отвергнуто:
- `uploadTzDocument` стора ERP после `createOrder` (п. 5 спеки) — заказ ERP какое-то время жил бы без ТЗ при `tz_required: true`, а сбой дозагрузки оставлял бы его без ТЗ навсегда. Секция `tz.documents` привязывает атомарно;
- детерминированный `group_id` или ключ (из `orderId + itemKey` или `print_key`) — уникальность `(group_id, version)` ломает повторный запуск после «Вернуть менеджеру», а угадываемый ключ позволяет подложить файл заранее (409 приняли бы за успех);
- один файл на N строк `erp_tz_documents` — снятие ТЗ у одной позиции в ERP удалило бы файл у остальных;
- `storage.copy(…, {destinationBucket})` на сервере — SVG ушёл бы в публичный бакет неочищенным: 5а грузит исходный файл, а не очищенный (`useAddArtwork.ts:168`). Мок e2e копирования между бакетами тоже не умеет;
- тип из `Blob.type` или расширения — продавец через REST кладёт SVG со `<script>` под именем `.png` с типом `image/svg+xml`, и по прямой ссылке он исполнился бы на origin Storage;
- импорт `tzFilePath` из `erp/utils` — нарушает белый список трёх модулей.

### К13. Публичность копий — принимаем, как у всего ERP, с точной формулировкой
- У `erp-attachments` на бою `public = true`. Политика чтения `erp_att_read` = `erp_is_member()`, то есть любой active + approved профиль, включая продавцов других команд и дизайнеров. Список бакета доступен им же.
- **После запуска ТЗ и макеты видят по списку бакета все одобренные сотрудники и любой, у кого есть ссылка.** Прежняя посылка «доступ только по прямому URL, ключ с uuid не угадать» неверна: ключи видны в списке.
- Ключи копий не несут id заказа и номера (К12). Поэтому список бакета не раскрывает связь «файл → заказ v4» до создания заказа ERP, и её нельзя использовать для подмены (К15, J).
- До запуска всё закрыто: приватный `order-artworks`, подписанные ссылки на 600 с.
- Записывается в правило вехи и выносится **отдельным пунктом утренней проверки владельцем** («Нужно от владельца», п. 1).
- В ТЗ нет цен: сторож модели (в `tzDocument` нет полей цены) и e2e по тексту pdfjs (нет «₽», нет «руб», нет цифр цены из фикстуры).

Без него admin без строки `erp_employees` прошёл бы проверку и упал бы на `files`. Проба фиксирует, что дают оба предиката у admin и director без строки ERP.

### К15. Два МС одновременно — чужая метка 10 минут от последнего продления, `recheck` перед созданием
- J: если `launch_started_at` моложе **10 минут**, `launch_by <> auth.uid()` и заказа ERP этого запуска ещё нет, ответ — `{ok:false, reason:'Заказ сейчас запускает <Имя> — подождите или попросите коллегу закрыть экран запуска, затем обновите карточку'}`. Метка не сдвигается.

Если статус уже не `ready_to_launch` или метку взял другой, запуск отменяется до создания заказа ERP (`stage: 'recheck'`). Окно между `recheck` и `createOrder` — миллисекунды.
- **Почему 10 минут.** Шаг `files` — скачать PDF групп и макеты (до 20 МБ каждый), очистить SVG, загрузить N копий. При окне в 2 минуты, сравнимом со временем шага, второй МС начал бы копировать параллельно, а проверка подлинности по `launch_by` отказала бы переходу у первого. T7 замеряет шаг `files` на фикстуре 67108 (README «Замеры»). Метка сорвавшейся попытки держит второго МС до 10 минут; текст отказа называет, кто запускает и как освободить.
- То же окно в 10 минут запрещает возврат менеджеру во время чужого запуска (К17).
- Тот же человек в двух вкладках — бэклог. В одной вкладке защищает `inFlight`. Повторная проверка после неудачного `createOrder` идёт от того же `launch_by` и не блокируется.
- В ответ добавлено явное `launched: boolean` (`erp_order_id` стоит). `afterAlready` смотрит **только** на `launched`: J выходит на бой до фронта (решение 26), поэтому запасной признак по форме ответа удалён. Нет `launched` в ответе — отказ `stage: 'check'` «Сервер старой версии — обновите страницу».

Отвергнуто:
- новая колонка «попытка запуска» — DDL `orders` и классификация в страже ради редкого случая;
- окно 2 минуты от первой метки — короче шага `files`;
- отдельное окно 15 минут для запрета возврата — два разных окна для одной метки; `recheck` продлевает метку, поэтому одного окна хватает.

### К22. «К запуску» — пресет списка и экран `/sales/:id/launch`

    - iframe пересоздаётся при возврате на вкладку, если с выдачи ссылки прошло больше 9 минут;

    - сводка запуска (`launchSummary`);
    - маржа «Маржа 18 % (порог 25 %)», ниже порога — со значком и текстом;
    - чек-лист только для чтения, в форме для МС;
    - оплата (К16) с причиной «без оплаты»;
    - маршрут;
    - дата запуска (по умолчанию следующий рабочий день, `nextWorkingDay`, пн–пт) с предупреждениями «позже срока сдачи» и «выходной»;

Подпись техники — `METHOD_LABELS` модели, а не мостовая `METHOD_LABEL` (`bridge/tzToErpDraft.ts:153`): на одном экране одна подпись техники, плюс подпись «Точный маршрут построит производство при запуске».

Отвергнуто:

- отдельный экран-список — дублировал бы `SalesList`.

### К23. Склейка всех ТЗ заказа — сборкой, а не склейкой файлов

### К24. Уборка `order-artworks` — не в 6+7

5. **QR нет**, ссылка на заказ — текстом в подвале (К9).
6. **Знаки вне шрифта блокируют отправку** с названием поля (К10).
7. **ТЗ и макеты копируются в публичный `erp-attachments` при запуске**, как у всего ERP (К12, К13). SVG — только очищенный, тип файла — только по сигнатуре байт. **После запуска ТЗ и макеты видят по списку бакета все одобренные сотрудники и любой, у кого есть ссылка** (а не «только по прямому URL»). Ключи копий — без id заказа и номера. Отдельный пункт утренней проверки.
8. **ТЗ привязывается секцией `tz.documents` в `erp_create_order`**, а не `uploadTzDocument` после создания (п. 5 спеки заменён, К12).
9. **Права МС в ERP проверяет `launch_check`**: нет `order.manage` и `tz.manage` — отказ с текстом до метки (К14). МС без должности в ERP запустить не сможет — назначить должность в производстве.

12. **rop не возвращает заказ менеджеру** — как на сервере с вехи 2 (К17).
13. **Сервер при отправке проверяет PDF у каждой позиции и макет у каждого нанесения, кроме «прочее»** (К18).
14. **Автор во всех RPC — по `is_sales`**, а не по роли `manager` (К20).
15. **Свой признак «Ведёт заказы» / «МС» меняют только admin и director** (К21).
16. **Маршрут на «К запуску» — список техник без стора ERP** (К22).
17. **«Скачать все ТЗ одним файлом»** — сборка, а не склейка (К23).
18. **Уборка `order-artworks`** — веха 8 (К24).
19. **`production → done`** — ручной переход МС или admin/director кнопкой «Отметить: заказ сдан» с `ConfirmDialog` «Заказ PH-… сдан клиенту? Вернуть статус нельзя». Кнопка живёт в итоге «Заказ запущен» экрана `/sales/:id/launch` и в шапке рабочего места; на экране `ready_to_launch` её нет. `STATUS_LABELS.done` = «Сдан». Автоматического «сдан» по ERP нет (бэклог).
20. **Порог маржи — подсказка:** в чек-листе предупреждение, не блокирует. МС видит маржу на «К запуску» строкой «Маржа 18 % (порог 25 %)» (`LaunchSide`, T6).

26. **J применяется до выкладки фронта 6+7** (ответы только дополнены, параметр с умолчанием). Предусловие — H и I на бою, а md5 функций равны литералам живой базы (Global Constraints).
27. **Подлинность связи с ERP.** `transition(production)` получает `p_erp_order_id` — id, который вернул `createOrder` этого запуска. Сервер проверяет, что у каждой позиции этого заказа ERP есть документ ТЗ из объекта `tz/v4-…`, загруженного тем, кто ставил метку (`owner = launch_by`). Та же проверка — в сиротской ветке `launch_check`. Прямую вставку `erp_orders` любым одобренным закрыть может только ERP — записано в риски, ERP заморожен.
28. **Разделение обязанностей.** Свой заказ запускает другой МС или руководитель производства. «Запуск без оплаты», разрешённый тобой, запускает другой. МС отмечает оплату только с `order.manage` и не на своём заказе. Признак `ms` профилю с ролью `rop` ставят только admin и director.
29. **Возврат во время чужого запуска запрещён** (окно 10 минут, К17). В находке было 15 минут; выбрано одно окно с меткой, потому что `recheck` её продлевает.
30. **409 при копии в ERP — отказ шага**, повтор запуска идёт с новыми ключами (К12). Вариант «новый ключ и автоматический повтор» отвергнут: лишняя ветка ради редкого случая.
31. **Сервер при отправке проверяет объекты в бакете:** PDF есть, тип `application/pdf`, ≤ 8 МБ; макет есть, тип из белого списка бакета (К18).
32. **Причина возврата видна продавцу** плашкой над вкладками, пока заказ не отправлен снова (T4 `lastReturn`, T5).
33. **«Отправить в работу» запускается только из раздела «ТЗ и цена».** Кнопка в шапке ведёт туда и показывает число блокирующих пунктов.
34. **Недоступные кнопки — `aria-disabled` с причиной**, а не `disabled`. После успешного RPC фокус переходит на заголовок нового состояния.
35. **Предпросмотр ТЗ — ссылкой, а не `window.open`** (К2).
36. **«Скачать все ТЗ» — только черновик**, после отправки — ссылки на записанные PDF (К23).
37. **Чек-лист у МС — в форме факта** («… — верните менеджеру»), у продавца — в форме действия.
38. **«Следующий к запуску»** в итоге запуска или возврата.
39. **Ссылка подвала — `APP_ORIGIN`** (`VITE_APP_ORIGIN`), а не `location.origin` (К9).
40. **Часовой пояс тестов — Europe/Moscow** (vitest и Playwright), даты — аргументом.
41. **Мок e2e — отдельными модулями**, сторож контракта мока против J (T4).
42. **Целостность PDF ТЗ.** МС при запуске пересверяет хэш модели с путём (`tzcheck`), расхождение блокирует запуск. Подделку байт при верном хэше это не ловит — полная защита серверной сборкой (веха 8).
43. **Мутации SQL гоняет контроллер** сухими прогонами на бою: исполнитель T1 только готовит файлы.
44. **`order_item_prints.zone_id` — веха 8, а не 6**, как ждал план 5б (решение 5): строку матрицы ТЗ даёт имя зоны, неизменное после сохранения (К7).
45. **`tzcheck` блокирует запуск и тогда, когда после отправки сменился справочник** (подвал `tzSettings`, ткани, бирки): хэш модели, собранной МС по текущим справочникам, не совпадёт с путём. Выход — «Вернуть менеджеру» и повторная отправка (PDF пересоберётся по новым справочникам). Текст отказа: «ТЗ не соответствует текущим данным заказа или справочникам — верните менеджеру, он отправит заново». Ослабить проверку (сверять без справочников) — нельзя: это и есть защита решения 42.
