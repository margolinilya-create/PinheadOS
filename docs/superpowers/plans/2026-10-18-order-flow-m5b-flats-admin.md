## Решения контроллера (с выбором и отвергнутыми вариантами)

### К1. История геометрии — `history[]` внутри записи флэта
**Выбрано.** У флэта появляется необязательный список `history: { version: number; views: FlatView[] }[]` — виды прежних версий как есть, вместе с путями своей версии. При выпуске версии N+1 в историю дописывается `{ version: N, views }` из базы. Записи истории никогда не меняются и не удаляются. Это держит не только клиент (`historyPreserved`), но и сервер: триггер-страж миграции I сравнивает OLD и NEW при любой записи, в том числе прямой (Task 2).

Читатели разрешают «флэт на версии V» чистой функцией `flatAtVersion(flat, V)`:
- поле `version` результата = **V**, а не текущая. Иначе перетаскивание или новое размещение на позиции v1 записало бы `flat_version` текущей с координатами v1 — тихий переезд без `remapToFlat`;
- метаданные флэта — текущие, виды — из истории версии V;
- внутри вида геометрия (`polygon_mm`, `safe_inset_mm`, `zone_id`, якоря, масштаб, путь) — из истории, а метаданные зоны (`name`, `tz_row`, `methods`, `default_method`, `max/min_print_mm`) накладываются из текущей версии по `area.id`, если такая зона там есть (К6, решение 11). Запись истории при этом не правится — наложение идёт при чтении.

Почему так:
- одна запись `catalog_put` атомарно выпускает версию и сохраняет прежнюю геометрию — ни второго ключа, ни второго конфликта;
- проверка одна: zod и ветка `catalog_value_check`, та же формула пути с версией записи;
- читатели (`useFlatsCatalog`) уже грузят справочник — лишней сети нет;
- размер: флэт сида весит около 1,3 КБ (46,7 КБ / 35), значит лимита 1 МБ хватит примерно на 700 выпусков. Размер меряется так же, как у сервера (`octet_length` в UTF-8): `new TextEncoder().encode(JSON.stringify(v)).length`, а не `.length` строки — кириллица весит 2 байта.

Отвергнуто:
- (а) отдельный ключ `garmentFlatsHistory` — две записи не атомарны и дают двойной конфликт;
- (б) `flats/<id>/v<N>/geometry.json` в бакете — меняются mime бакета, регулярка пути и сторожи 5а, на каждую старую версию нужен лишний запрос, снимок v1 у сида пришлось бы дописывать задним числом;
- (в) снимок геометрии в `layout` каждого нанесения — дублирование на каждое нанесение; старый клиент 5а пересобирает `layout` без снимка; для мокапа ТЗ нужен вид целиком, а не одна зона;
- (г) без истории, только пометка `stale` (рекомендация разведки) — против минимального объёма задания: старый заказ рисовался бы на чужой геометрии.

### К2. Выпуск версии только геометрии — перенос файлов всех видов
Сервер требует `svg_path` по формуле с текущей версией. Поэтому новая версия получает объекты `v<N+1>` для **всех** видов:
- новый файл — из правки;
- прежний — переносится: свежий `downloadFlatSvg(baseView.svg_path)` → `resolveFlat` (очищенный текст) → `uploadFlatSvgOnce` по новому пути. Кэш холста `loadFlatMarkup` для переноса **не используется**: он кэширует и неудачу (`null`) до перезагрузки вкладки, и повтор после сетевого сбоя не прошёл бы. `flatImages.ts` (5а) не меняется.
- скачивание или разбор вернули `null` → `{ ok: false, kind: 'files' }` с текстом «Не удалось перенести вид «…» прежней версии — нажмите кнопку сохранения ещё раз». Справочник не пишется, новый путь этого вида не загружается.

Отвергнуто:
- Storage `copy` — лишняя операция в писателе, сторож `flatsWrites` и мок, а выигрыш — несколько КБ;
- ослабить формулу (`svg_path` с версией ≤ текущей) — клиенты 5а отбросили бы такие флэты (их `flatsSchema` сверяет точную формулу), и ослабла бы защита M5.

### К3. «Уже есть» при выпуске — сверка содержимого
Ответ `'exists'` от `uploadFlatSvg` верен только для сида. Для редактора новая функция `uploadFlatSvgOnce(path, svg)`:
- объект есть → скачать и сравнить строку с загружаемой (обе — выход `sanitizeSvg`);
- совпало → `'same'` (повтор после сбоя);
- не совпало → `'differs'`. Тогда `saveFlat` берёт следующую версию и перезапускает загрузку всех видов.

**Стартовая версия** = max(версия по справочнику и истории, наибольшая занятая `v<N>` в бакете) + 1. Занятые номера `saveFlat` узнаёт до цикла загрузки чтением `listFlatVersions(id)` (`api/garmentFlats.ts`: `storage.from(FLATS_BUCKET).list('flats/<id>/')`). Это чтение: сторож `flatsWrites` не меняется, `list` добавляется в мок. Без этого любой писатель бакета, а заодно и сироты сохранений, сорвавшихся на P0001 после загрузки, заняли бы `v<N+1…N+5>` и навсегда закрыли бы выпуск версий флэта — DELETE нет.

Лимит 5 попыток остаётся только на гонку двух администраторов. Исчерпан → `files` с текстом «Номер версии занят: другой администратор сохранял этот флэт одновременно с вами. Нажмите «Загрузить свежую версию» — выбранные файлы останутся». Если и следующая попытка упёрлась — «Версии флэта заняты — сообщите администратору».

Номер версии только растёт; пропуски номеров допустимы.

**Сравнение строк требует идемпотентного санитайзера:** `sanitizeSvg(sanitizeSvg(x).svg).svg === sanitizeSvg(x).svg` — тест T1 на всех 67 SVG сида, на выходе `mirrorSvg` и на `flat-evil.svg`. Иначе повтор после сбоя видел бы `'differs'` и уходил в следующие версии без второго администратора.

Отвергнуто: молча принять `'exists'` — справочник указал бы на чужой SVG (осиротевший от сорвавшегося сохранения или от второго администратора).

### К4. Когда файлы попадают в бакет — при сохранении
При выборе файла выполняются sniff, `sanitizeSvg` и показ. Очищенный текст держится в черновике. Загрузка идёт при нажатии «Создать флэт» или «Выпустить версию»: сначала файлы, справочник последним (как у сида).

Почему: DELETE в бакете нет (К5). Загрузка при выборе оставляла бы сироту на каждый отменённый или заменённый файл. Правило проекта «файл, видимый приложенным, обязан быть в бакете» защищает от ссылки на отсутствующий файл. Это здесь соблюдено: до `catalog_put` на файл никто не ссылается.

Отвергнуто: загрузка при выборе (как советовала карта DM) — сироты без возможности уборки.

### К5. DELETE версий — не в 5б
Политики DELETE у `garment-flats` нет (L1 вехи 5а), RPC «версия не упомянута» не заводим. Причины:
- объём мал: 67 SVG — около 1,4 МБ, сироты редки;
- старые версии нужны заказам (`layout.flat_version`), PDF и вехе 6;
- открытые вкладки держат справочник до 10 минут и успевают поставить раскладку на старую версию;
- `storage-backup` копию всё равно хранит.

Сторожа 5а («DELETE нет нигде», «писатель — только `upload`») остаются зелёными без правок. Уборка ничьих версий (возрастной гейт, проверка по `history`, `layout`, `order_items.flat_id` на сервере) — в бэклог; туда же — сироты от сохранений, сорвавшихся на P0001 после загрузки файлов.

**L1 плана 5а («в 5б — delete только неупомянутых версий») отменён решением К5 (18.10).** Это пишется в правило вехи 5б и в раздел «Проверка плана» 5а (Task 8), чтобы DELETE не завели «по плану».

Отвергнуто: политика плюс `security definer` «путь не используется» — гонка с открытыми вкладками, ради экономии килобайт ломается правило «версии неизменяемы».

### К6. Правило версии
**Геометрия (выпуск N+1):** любое изменение `geometryOf(flat)`:
- набор видов; новый SVG вида;
- `scale_mm_per_unit`; `anchors`, включая `axes`; `size_anchors`, `grade_rule`;
- набор зон и их `id`; `polygon_mm`, `safe_inset_mm`, `zone_id`.

`zone_id` относится к геометрии: от него зависят перенос (`remapToFlat`) и имя зоны в нанесении.

**Метаданные (без версии):**
- `name`, `garment_type`, `typical`, `active`, `sku_codes`, `categories`, `fits`, `sizes`/`base_size`;
- у зоны — `name`, `tz_row`, `methods`, `default_method`, `max_print_mm`/`min_print_mm`.

Метаданные зоны правятся только у текущей версии, но видны и читателям старых версий: `flatAtVersion` накладывает их по `area.id` (К1). Исключение — **служебная зона** (`zone_id = null`): её `name` служит ключом нанесения в заказе (`zoneNameOf`, `layout.ts:108`). Поэтому после сохранения оно только для чтения, как название зоны справочника (решение 5).

**Классификация полей — исчерпывающая.** В `flatVersion.ts` заданы явные множества `GEOMETRY_KEYS` и `META_KEYS` для `GarmentFlat`, `FlatView`, `ViewAnchors`, `PrintArea`. Сторож по образцу `orderV4Rights.test.ts` сверяет их с ключами zod-схем: `flatSchema.shape`, `viewSchema.shape`, `printAreaSchema.shape`, `anchorsSchema.shape` (T1 экспортирует две последние). Каждый ключ должен быть ровно в одном множестве. Новое поле без классификации (например, `parts` вехи 6) даёт красный тест, а не тихо уходит в «метаданные».

Кнопка называет результат: «Сохранить флэт», «Выпустить версию N+1» или «Создать флэт». Под кнопкой выпуска — подсказка: «Нанесения в заказах останутся на версии N, пока менеджер не перенесёт их».

### К7. Одна правка — один флэт; конфликт — правило вехи 4
Редактор правит один флэт (адрес `?tab=flats&flat=<id>`).

При сохранении:
- весь справочник пишется так: прочие записи — **сырыми, как есть**, вместе с битыми и полями будущих клиентов; правленая — разобранной и отредактированной;
- `p_base` — значение из свежего `fetchCatalogKey`;
- **перед `putCatalog`** склеенный справочник проверяется так же, как на сервере: `parseFlatsCatalog(merged)` плюс проверки уровня справочника (уникальность кодов моделей среди активных, размер в байтах UTF-8 ≤ 1 048 576). Замечания по **чужим** записям — запрос не шлётся, текст «Флэт «X» в справочнике битый: … — сохранение закроет сервер. Откройте его и исправьте» со ссылкой на флэт. Иначе одна битая запись (прямая запись мимо RPC, SQL Editor, данные, прошедшие H, но не I) давала бы 22023 на сохранении любого флэта;
- **битую запись можно починить:** состояние `broken` открывает её терпимо (недостающее заполняется значениями по умолчанию, замечания подсвечены). После исправления она сохраняется обычной правкой (решение 17);
- отказ сервера 22023 приходит в `saveFlat` видом `invalid` с текстом сервера дословно («Флэты: неверная запись — …»), а не общим «Ошибка сохранения».

Конфликт (P0001):
- плашка вехи 4 `catalogConflictText('Флэты и зоны')`, правки остаются на экране, сохранение закрыто до «Загрузить свежую версию»;
- загруженные файлы остаются и при повторе с тем же файлом принимаются как `'same'`.

Отвергнуто:
- автослияние по флэту — отступление от Пр4, нужно согласие владельца (см. «проверить утром»);
- `useCatalogEditor` как есть — для `garmentFlats` он уходит в `fallback` со значением стора `undefined`, пишет мусорное поле в `useStore`, не сбрасывает кэш `useFlatsCatalog` и не умеет «файлы перед справочником». Для флэтов нужен свой хук `useFlatEditor`. Плашку, текст конфликта, `leaveGuard` и тексты он берёт из вехи 4.

### К8. Строки матрицы ТЗ (`tz_row`) — перечень кодов; справочник зон правится только здесь
- **Модуль констант** `orderstudio/catalog/tzRows.ts` (его же прочтёт `tzDocument` вехи 6):
  - 9 строк матрицы: `front` «Полочка», `front_l` «Полочка Л», `front_r` «Полочка П», `back` «Спинка», `sleeve_l` «Рукав Л», `sleeve_r` «Рукав П», `hood_l` «Капюшон Л», `hood_r` «Капюшон П», `pocket` «Карман»;
  - плюс `other` «Другое».
- **Цепочка выбора строки:** `area.tz_row` (переопределение у зоны флэта, например полочки Л и П у зип-худи) → `zone.tz_row` (справочник зон) → `DEFAULT_TZ_ROW_BY_ZONE[zone.id]` (код) → `other`.
- **Типы и проверка.** `PrintArea.tz_row` сужается до кода; zod и сервер принимают только перечень. В сиде `tz_row` нет — проверено, сужение безопасно.
- **Справочник `zonesCatalog`** получает `tz_row?` и `active?`. Правится только режимом «Зоны нанесения» вкладки «Флэты и зоны».
- **Вкладка `/sku` «Зоны нанесения»** становится просмотром со ссылкой: сейчас она жёстко удаляет зоны, против правила «отключать, не удалять». Запись `zonesCatalog` из `useSkuSave` уходит. Сторож — один писатель.
- Техники по зонам остаются в «Правилах категорий». У зоны флэта `methods` и `default_method` показываются с подсказкой «итог — пересечение с правилами категорий» (так в минимальном объёме задания).
- Колонки техник для ТЗ (Ш, В, Т, DTG, П) — **не в 5б** (YAGNI). Колонка зависит и от исполнителя («П = прочее и подряд», спека, строка 144), а читатель у неё — веха 6. Там и будет `tzColumnOf(method, executor)` с тестом «подряд → П при любой технике» (решение 23).
- **id зоны** — одна константа `ZONE_ID_RE = /^[a-z0-9][a-z0-9_-]{0,62}$/` в `orderstudio/catalog/tzRows.ts`. Её читают `zonesEdit` («Добавить зону») и `flatsSchema` (`zone_id`). Сторож SQL проверяет, что исходник регулярки в обеих ветках I равен `ZONE_ID_RE.source`.
- **Зеркало `ph_zones`.** После ухода записи из `useSkuSave` его никто бы не обновлял, и запасной путь `catalogSlice.ts:111` вечно отдавал бы устаревшие зоны. Решение: `catalogSlice` перестаёт читать `ph_zones` (запасной путь — `ZONES_CATALOG_DEFAULT`), а ключ остаётся в списке очистки `lib/storage.ts`, чтобы старое значение стёрлось при выходе (решение 24).

Отвергнуто:
- `tz_row` только у зоны флэта (план 5а) — нанесение строкой без холста не попало бы в матрицу;
- второй редактор `zonesCatalog` рядом с `/sku` — два писателя одного ключа;
- свободный текст `tz_row` — веха 6 не сопоставит строку.

### К9. Загрузка SVG — WYSIWYG через санитайзер
Принимается только SVG. Порядок проверок:
1. `sniffArtwork(bytes, name)` → `svg`; размер не больше 1 МБ (`FLAT_MAX_BYTES`); текст — `TextDecoder('utf-8', { fatal: true })`, UTF-16 (BOM) или `encoding` не UTF-8 в прологе → «Сохраните SVG в UTF-8».
2. `sanitizeSvg` → `ok`.
3. Есть `<g id="garment">` (иначе не сработает `recolorGarment`) и `viewBox`.

Масштаб: если у `width` физическая единица (mm, cm, pt), то мм / `vb.w`, иначе 1 (договорённость «viewBox — мм»). Если санитайзер что-то вырезал, это показывается списком «Из файла убрано: …» рядом с превью очищенного файла — именно его и загрузим. Список — человеческие подписи по виду («скрипты ×3», «обработчики событий ×12»), не имена из файла, не больше 20 строк: злонамеренный SVG с десятками тысяч `on*` не раздувает интерфейс и `aria-live`.

Отказы с текстом:
- PNG, PDF, AI: «Силуэт — только SVG: сохраните контур в SVG (Illustrator: «Экспорт» → SVG)»;
- нет `garment`: «В SVG нет группы силуэта `<g id="garment">` — без неё силуэт не перекрасится в цвет ткани»;
- нет `viewBox`: «В SVG нет viewBox — масштаб не определить».

Отвергнуто: отказ при любом непустом `removed` (так в тесте сида) — тогда не проходил бы любой SVG из Inkscape или Illustrator с комментариями и метаданными. Сид — эталон и обязан быть чистым, а загрузка администратора видна ему превью.

### К10. Рукава — загрузка вручную плюс «Зеркальная копия» с отражённым SVG
SVG рукавов в сиде нет (в DM они были только из DXF). Администратор загружает SVG одного рукава. Кнопка «Зеркальная копия» создаёт противоположный вид.

Что отражается (`x' = W − x`, где W = `vb.w × scale` — из viewBox, а не `naturalWidth`; дефект 1 DM):
- **якоря:** `sleeve_center_x`, `center_axis_x`, `neckline_point.x`, `axes[].x`, те же поля в `size_anchors`;
- **зоны:** все точки `polygon_mm`;
- **правило ростовки:** у `grade_rule` меняется знак x-дельт.

Что меняется у зон кроме координат:
- `zone_id`: `sleeve-l` ↔ `sleeve-r`;
- `tz_row`: `sleeve_l` ↔ `sleeve_r`;
- имя: меняется, если совпадало с именем зоны в справочнике.

id зон прежние: уникальность нужна только внутри вида, а суффиксы DM пробивают предел `AREA_ID_RE`.

Файл — **отражённый SVG**: содержимое корня оборачивается в `<g transform="matrix(-1 0 0 1 (2·vb.x + vb.w) 0)">`. `transform` санитайзер пропускает, `<g id="garment">` остаётся внутри.

Если целевой вид уже есть — подтверждение «Заменить правый рукав?». Схема требует уникальный `kind`.

Отвергнуто: тот же файл без отражения (DM, «рукав симметричный») — неверно для асимметричных рукавов.

### К11. Калибровка — по известному размеру, вся геометрия вида
Два способа:
- **на холсте** — режим «Калибровать», две точки, ввод реальной длины;
- **с клавиатуры** — поле «Ширина силуэта, мм» (= `vb.w × scale`).

Новый масштаб равен старому, умноженному на `k`. **Все позиции вида** умножаются на `k` (`calibrateView`): якоря, `axes`, `size_anchors`, `polygon_mm`. Так зоны и якоря остаются на тех же точках силуэта (дефект 2 DM). Физические величины не меняются: `safe_inset_mm`, `max/min_print_mm`, дельты `grade_rule`.

Калибровка — правка геометрии, значит выпуск новой версии.

### К12. Зоны-многоугольники
По умолчанию зона — прямоугольник: рамка `Transformer` плюс поля X, Y, Ш, В.

Режим «Многоугольник» — для зон не по осям:
- точки списком (X, Y) с кнопками «Добавить точку после выбранной» и «Удалить точку» (не меньше 3, не больше 256);
- вершины на холсте перетаскиваются ручками `Rect`.

Непрямоугольный многоугольник из данных показывается как есть. В прямоугольник он превращается только по кнопке «Сделать прямоугольником» — молча, как в DM, нельзя.

Проверка «логотип в зоне» на холсте 5а идёт по описывающему прямоугольнику (`polygonToZone`). Это остаётся так; проверка по многоугольнику — в бэклог, подсказка в редакторе это называет.

### К13. Ростовка (`grade_rule`, `size_anchors`, флэты и зоны по размерам) — не в 5б
Требования в спеке нет (проверено grep: «ростовк», «grade»), в сиде ростовки нет.

Поля хранятся и сохраняются как есть. Калибровка и зеркало их преобразуют, чтобы не испортить. Интерфейса нет; если правило задано в данных, видна подпись «Ростовка задана в данных — правится позже».

Размеры (`sizes`, `base_size`) правятся как метаданные:
- сортировка — `sizeOrder` из `store/slices/helpers.ts` (дефект 4 DM);
- удаление размера чистит его ключ в `size_anchors` (дефект 3 DM);
- нельзя удалить базовый размер.

Перенос `grading*`, `gradeRule`, DXF — в бэклог.

### К14. Где лежит код и как он грузится
- **Чистое ядро** — `orderstudio/design/edit/*.ts`:
  - `flatEdit`, `flatSizes`, `flatAreas`, `newFlat`, `mirrorSleeve`, `calibrate`, `flatIds`, `validateFlat`;
  - каталог `edit/` дописывается в `PURE_DIRS` сторожа `designGuards`: без React и без ERP. Новый сторож: `design/edit/**` не импортирует `api/`, `store/`, `lib/supabase` и `useToastStore` — ядро без побочных эффектов.
- **Писатель флэта `saveFlat` — не в ядре:** `orderstudio/admin/flats/saveFlat.ts`, рядом с `useFlatEditor`. Он ходит в `api/garmentFlats`, `catalogAdmin.putCatalog` и `toast`. Его чистые части (`releaseFlat`, `mergeFlatIntoRaw`, `catalogBytes`) лежат в `design/catalog/flatVersion.ts`. Так статический импорт из холста не втянет `catalogAdmin` в чанк холста.
- **`flatAtVersion`** и `geometryOf` — в `design/catalog/flatVersion.ts`: их читают и холст, и редактор. Подписи видов и типов — `design/catalog/flatLabels.ts`. Имя не `labels.ts`: оно созвучно `orderstudio/catalog/labels.ts` (бирки вехи 4).
- **Экран** — `orderstudio/admin/flats/`:
  - `FlatEditor.jsx` — ленивый `import()` из `FlatsTab`, холст статически внутри;
  - `FlatPreview.jsx` — ленивый, для ≤ 760 px, без konva;
  - `ZonesCatalogEditor.jsx`.
- **konva** — только через `design/ui/konva.ts` 5а, без новых фигур: ручки — `Rect` с `cornerRadius`, многоугольник — `Line closed`. Иначе растёт общий чанк `vendor-konva`, а с ним и холст 5а (потолок 100 000 Б).
- **ERP** — в `admin/flats/**` ни одного импорта `/erp/`, как в `design/**`: не трогаем разрезку `ErpStates`/`ErpSkeletons`.

### К15. Холст рабочего места: рукава и версия позиции
- **Виды холста:** `DESIGN_VIEWS` = все четыре вида. Вкладки видов показывают только виды, которые есть у флэта, в порядке перед → спина → левый → правый рукав.
- **Версия позиции.** `itemFlatVersion(prints, flat)` — версия раскладок позиции на этом флэте:
  - одна версия → холст, превью, PDF и preflight рисуют по `flatAtVersion` этой версии, и новые размещения ставятся на неё же;
  - раскладок нет → текущая версия;
  - версий несколько или версии нет в истории → текущая, с пометкой `stale`, как в 5а;
  - во все места размещения (`PlaceCtx.flat` у `applyPlacement`, `newPlacedPrint`, перетаскивания) идёт **разрешённый** флэт `flatAtVersion(flat, itemFlatVersion(...).version)`, а не текущий. Тогда `layout.flat_version` позиции на v1 остаётся 1 и после перетаскивания, и при новом размещении.
- **Плашка (только черновик):** «Силуэт обновлён до версии M. Нанесения стоят по версии N. [Перенести на версию M]». Перенос — `remapToFlat` через `edit`. **Открытие ничего не пишет.**
- **Плашка «точный силуэт» (Р12):** «Для модели появился точный силуэт «…» — [Перенести нанесения]», если `item.flat_id` типовой, а `autoPickFlat` даёт точный.
- **Фильтр зон модели.** Новое размещение предлагает только зоны флэта, у которых `zone_id` входит в `zonesForSku(sku)`. Служебные зоны (`zone_id = null`) — всегда. Уже размещённые не трогаются.

### К16. Ревизия клиента `SALES_CLIENT_REV` не поднимается
Флаг `orderStudio` людям не включён до вехи 8 (план 5а, выкатка).

Старый клиент 5а:
- раскладку рукава разбирает в `null` и не перезаписывает: `placeArtwork` берёт только строки с тем же названием зоны, а зоны рукавов на переде и спине не стоят;
- `history` отбрасывает при разборе, но справочник флэтов не пишет: сид дописывает сырые записи, историю он сохраняет.

Подъём ревизии потребовал бы пересоздать `order_v4_save_full` и `order_v4_save` (порог зашит в оба тела) — риск без пользы. Если флаг включат раньше 5б — вернуться к вопросу.

## Решено контроллером за владельца (проверить утром)
1. **История версий** — `history[]` в записи флэта (К1). Справочник растёт примерно на 1,3 КБ за выпуск. При 80 % от 1 МБ (в байтах UTF-8, как считает сервер) редактор предупреждает; при превышении отказывает ещё до загрузки файлов. Подрезка истории — бэклог.
2. **Удаление версий** — не в 5б (К5). Сироты от сорвавшихся сохранений остаются в бакете до бэклога уборки. Выпуск версий они не блокируют: стартовая версия считается и по бакету (`list`).
3. **Строки матрицы ТЗ** — 9 кодов плюс «Другое» (К8). По умолчанию «Капюшон» → «Другое: Капюшон»: зона `hood` одна, а строк две (Л и П). Капюшон Л или П ставится в справочнике зон или у зоны флэта. Новые зоны `hood-l`/`hood-r` не заводим.
4. **Справочник зон** правится только во «Флэтах и зонах». `/sku` → «Зоны нанесения» — только просмотр со ссылкой (К8).
5. **Название зоны после сохранения не меняется:** оно — ключ в заказах (`SalesPrint.zone`, цена DTG ищет «карман» в названии). Опечатку исправляют снятием зоны и новой зоной. Устойчивый ключ `order_item_prints.zone_id` — веха 6. То же правило распространено на **служебные зоны флэта** (`zone_id = null`): их имя — ключ нанесения, после сохранения только чтение.
6. **Конфликт двух администраторов** — правило вехи 4 без автослияния по флэту (К7).
7. **Ростовка** (`grade_rule`, `size_anchors`, флэты и зоны по размерам) и DXF — не в 5б (К13).
8. **Загрузка SVG** — принимаем очищенный файл и показываем, что вырезано (К9). Не отказываем при любом вырезанном.
9. **Зеркальный рукав** — отражённый файл, а не тот же (К10).
10. **Файлы флэта грузятся при сохранении, а не при выборе** (К4). Отступление от буквы правила «загрузка при выборе» ради «нет сирот без DELETE»; смысл правила соблюдён.
11. **`tz_row`, `methods`, `default_method`, имя зоны, лимиты печати** — метаданные, без новой версии (К6). Правятся у текущей версии, но `flatAtVersion` накладывает их и на старые версии по `area.id`. Значит, правка `tz_row` меняет строку ТЗ и у черновиков на старой версии. Выпущенный PDF — неизменяемый снимок.
12. **Многоугольник проверяется по описывающему прямоугольнику**, как в 5а (К12).
13. **Колорблок** (`parts`, заливка по деталям) — не в 5б. Санитайзер уже сохраняет `id` деталей. В вехе 6 — цвет позиции и список цветов деталей текстом, если владелец не решит иначе.
14. **`SALES_CLIENT_REV` не поднимаем** (К16).
15. **rop** — только просмотр флэтов и зон, как в 5а и на сервере (`v_admin_pair`).
16. **«Копия флэта»** (точный флэт модели из типового: новые id и v1, файлы переносятся) — в 5б. Дешёвое продолжение `saveFlat` под Р12/Р13. Кнопка называется «Сделать точный силуэт для модели».
17. **Битая запись в справочнике флэтов** открывается терпимо и чинится в редакторе (К7). Битые чужие записи не дают сохранить флэт: показывается, какой флэт битый, запрос не шлётся.
18. **Триггер-страж `app_config_order_catalog_guard`** на `app_config` для `garmentFlats` и `zonesCatalog` (миграция I). Даже admin прямой записью не выбросит историю, не понизит версию, не удалит флэт или зону и не переименует зону. DELETE строк этих ключей — только `service_role`. Это правило проекта «права по колонкам — триггер-страж».
19. **I применяется в тот же день, что и мердж 5б.** Между `2-apply-I` и мерджем зоны в `/sku` не правим: старый редактор жёстко удаляет зоны и не проверяет уникальность названий, страж и новая форма отклонят такое сохранение (22023 или 42501, текст сервера на экране).
20. **Метаданные зоны** накладываются из текущей версии и на старые версии (К1, К6). Отвергнутый вариант — «метаданные правятся только у текущей версии».
21. **Новый флэт рождается с зонами по умолчанию** для каждого вида: перед — `front`, спина — `back`, рукав — `sleeve-l`/`sleeve-r`; прямоугольник по центру с отступом. id предлагается транслитерацией имени, сырой «масштаб» спрятан под «Подробно».
22. **Правка силуэта отменяется отдельно:** «Отменить правки силуэта» возвращает геометрию базы и оставляет метаданные. Поля геометрии подписаны «Меняет силуэт — сохранится новой версией».
23. **`METHOD_TZ_COLUMN` отложен в веху 6** как `tzColumnOf(method, executor)`.
24. **`ph_zones` больше не читается:** запасной путь зон — `ZONES_CATALOG_DEFAULT`. Ключ остаётся в списке очистки при выходе.
25. **«Загрузить свежую версию» сохраняет выбранные SVG** и предлагает применить их к свежей записи; прежний черновик держится до явного сброса.
26. **Стартовая версия выпуска считается и по бакету** (`list`), лимит 5 попыток — только на гонку (К3).
27. **L1 плана 5а отменён решением К5** — записывается в правило 5б и в план 5а.
28. **Откат фронта 5б откатывает и I** (миграцией с текстом H и снятием стража) — иначе старый `/sku` не сможет удалить зону. Перед откатом владелец предупреждён: снятые зоны (`active: false`) старый фронт снова предложит в подборе.
