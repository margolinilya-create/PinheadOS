## Решения контроллера (с выбором и отвергнутыми вариантами)

### К1. Как люди попадают в раздел — выбор оболочки по профилю и адресу, без правки ERP
Сейчас флаг живёт в браузере (`?studio` → `localStorage` → `VITE_FEATURE_ORDER_STUDIO` → `false`), кнопки переключения — только у admin/director, кнопка в ERP в замороженном `ErpLayout.jsx`. У продавца, МС и rop устойчивого способа попасть в ТЗ нет: `?studio=1` не переживает F5 на `/sales/:id`.

**Выбор:** новая чистая функция `src/config/shellChoice.ts` — `chooseShell({ search, path, stored, env, profile }) → 'order' | 'erp'`; `App.jsx` зовёт её вместо `FEATURES.orderStudio` в месте выбора оболочки (там, где сейчас читается `FEATURES.orderStudio`; пользователь к этому месту уже известен). `env` — **тройка** (описать в `features.ts`/`shellChoice.ts`): `'0'`/`'false'` — авария, `'1'`/`'true'` — dev/e2e, пусто — по профилю. Порядок, первый сработавший решает:
1. **аварийный выключатель** — `env ∈ {'0','false'}` → `erp` для всех; `?studio=1` его **не** обходит (ссылки с `?studio=1` живут в закладках и письмах);
2. `?studio=1|0` в адресе (на один заход, как сейчас);
3. **путь только раздела ТЗ** (`/sales`, `/sales/…`, `/sales-staff`, `/order-settings`, `/express`, `/sku`, `/prices`) и `canUseSales(profile)` → `order`. F5 на `/sales/:id` остаётся в ТЗ без флага;
4. явный выбор в `localStorage` (`pinhead_feature_orderStudio`): `'1'` пишет кнопка «в ТЗ» у admin/director; `'0'` пишет **только** `LeaveToProduction` (профиль без доступа) и кнопка «в Производство» у admin/director без продаж;
5. **умолчание по профилю:** `canUseSales(profile)` и роль не admin/director → `order` (продавец, МС, rop);
6. `env ∈ {'1','true'}` → `order` (e2e и dev, как сейчас);
7. `erp`.

**Решение принимается один раз за загрузку страницы для данного `user.id`.** App перерисовывается при смене `user`/`profileStatus`/`checkingProfile` (`refreshProfile`, `TOKEN_REFRESHED`); пересчёт по текущему `pathname` на ходу размонтировал бы `OrderStudioApp` посреди работы (admin пришёл по `/sales`, ушёл на `/admin` или `/sku` раздела ТЗ → правило 3 уже не срабатывает, правило 5 даёт `erp`; автосохранение, буфер позиции, `locked`/`conflict` теряются). Это тот же класс ошибок, что описан в комментарии `App.jsx` о «режиме, вычисленном один раз за загрузку». Реализация: обёртка `ShellGate` с `useState(() => chooseShell(...))`, ключ — `user.id` (`<ShellGate key={user?.id ?? 'anon'} …>`); смена `checkingProfile`, повторный `set user` с тем же id не меняют оболочку. Пересчёт допустим только при смене `user.id` (выход/вход) или когда `canUseSales(user)` стал `false` (сняли `is_sales`): тогда уход через `switchToProduction`/`LeaveToProduction`, а не тихая подмена.

Кнопка «в Производство» в `OrderLayout.jsx` — всем, кто проходит `canUseSales` (была только admin/director). **Для продавца, МС и rop она не сохраняет выбор**, а уводит одним заходом: `location.replace('/?studio=0')` — правило 2 действует на эту загрузку, внутренние переходы ERP App не пересчитывает (решение закреплено на загрузку). Иначе записанный `'0'` (правило 4 выше правила 5) запер бы продавца в Производстве при каждом `/`, а кнопки обратно у него нет. Обратно из ERP без кнопки — пунктом «Заказы ТЗ» нельзя (ERP заморожен), поэтому путь назад — адрес `/sales` (правило 3), закладка и просто `/` (правило 5). `canUseSales` App и `shellChoice` импортируют **прямо из `orderNav.ts`**: в нём нет ни одного `import`, `ORDER_NAV` — несколько десятков строк констант, сборщик выбросит неиспользуемое. Отдельный `salesAccess.ts` не заводится; сторож — одна строка в существующем тесте: «`orderNav.ts` без `import`»; вход ≤ 155 000 Б (замер в T5).

Ключи флагов собираются динамически (`LS_PREFIX + name`), поэтому сторож хранилища их не видит. `features.ts` экспортирует `FEATURE_STORAGE_KEYS` (из списка `FeatureName`), `storage.ts` классифицирует каждый: `pinhead_feature_orderStudio` → `APP_KEYS` (выход стирает выбор, на общем устройстве следующий человек получает умолчание своего профиля), `pinhead_feature_styleguide` → `KEEP_ON_LOGOUT` (инструмент разработки, настройка устройства). Сторож: каждый `FeatureName` классифицирован.

**Выключатель и открытые вкладки.** Маркер сборки сейчас — только SHA коммита: redeploy того же коммита с `VITE_FEATURE_ORDER_STUDIO=0` даёт тот же маркер, `isNewerBuild` вернёт `false`, и открытая вкладка узнает о выключении только упавшим ленивым импортом (или не узнает). Поэтому T5: `buildId = SHA + '-' + (env.VITE_FEATURE_ORDER_STUDIO ?? '')` + тест «другое значение флага — другой маркер». Выключатель гасит **только интерфейс**: права на сервере остаются у отмеченных, серверный откат — снять отметки (записано в объявлении и в «Откате включения»).

Отвергнуто:
- **(a) глобальная переменная сборки `=1`** — все, включая дизайнеров и цеха, стартуют в ТЗ и уходят через лишнюю загрузку ленивого чанка; там, где записан `'0'`, не действует; «включение» нельзя сделать по людям;

- флаг в `profiles` на сервере — новая колонка и страж ради того, что выводится из `is_sales`/`is_ms`.

**Следствие:** слияние кода ничего не включает (продавцов и МС 0, admin/director по умолчанию остаются в ERP). **Включение людям = отметка сотрудников в `/sales-staff` по утверждённому владельцем списку, ПОСЛЕ зелёного чек-листа готовности** — по человеку, обратимо; глобальный откат интерфейса — выключатель `VITE_FEATURE_ORDER_STUDIO=0` и redeploy, серверный — снять отметки.

**Имя раздела для людей — «Оформление заказа»** (так подписана шапка оболочки Order). «ТЗ» — только внутреннее обозначение в плане и коде; в объявлении, в «Решено контроллером» и в текстах интерфейса раздел называется «Оформление заказа».

### К5. `zone_id` у нанесения — в 8, одной парой с `orders.notes`
Задание вехи 8 называет `zone_id` прямо (решение 44 плана 6+7). Раз миграция K всё равно правит `order_v4_save`, обе вещи — одной парой «клиент + миграция»:
- `order_item_prints.zone_id text null`, CHECK `zone_id ~ '<ZONE_ID_RE.source>'` — **ровно** исходник `ZONE_ID_RE` из `tzRows.ts` (5б: `^[a-z0-9][a-z0-9_-]{0,62}$`; его же сверяет сторож SQL вехи I с веткой `catalog_value_check`). Один источник правды для ключа: `{0,63}` (было в плане) разрешал бы в нанесении id, запрещённый в справочнике. `order_v4_save` до вставки проверяет формат и отказывает `22023` «Неверный код зоны нанесения» — нарушение CHECK внутри `order_v4_save_full` откатило бы всё сохранение без понятного текста;
- `orders.notes` (колонка есть) — пишется `order_v4_save` только если ключ передан (`p_order ? 'notes'`), длина ≤ 2000 → иначе `22023` (понятный текст). **Длина держится на таблице, и CHECK ставит миграция L — вместе с классификацией `notes` в `order_v4_guard`** (между L и K — мердж PR, пересъёмка эталонов и выкладка, это часы; без CHECK в это окно продавец-автор PATCH-ем через REST пишет в черновик комментарий любой длины, а фронт ревизии 4 печатает его в ТЗ): `alter table public.orders add constraint orders_notes_len check (notes is null or char_length(notes) <= 2000) not valid; alter table public.orders validate constraint orders_notes_len;` (на бою у всех 8 строк `notes` null) — потому что `orders_update` разрешает продавцу-автору PATCH своей строки через REST в обход RPC. Классификация `notes` в `order_v4_guard` и CHECK — **в миграции L, не K** (см. К6 и порядок K/L); проверка длины в `order_v4_save` (K) — только ради понятного `22023`;
- порог ревизии в `order_v4_save_full`/`order_v4_save` — **4**, `SALES_CLIENT_REV = 4`;

## Проверка безопасности
Отдельный агент-атакующий (права, RLS, Storage, RPC, выбор оболочки, уборка). Находки внесены по месту; итог:
- **Выбор оболочки не даёт прав:** оболочка — только интерфейс; все записи — RLS/RPC. `?studio=1` у дизайнера → `LeaveToProduction` один раз; подмена `localStorage` → тот же результат; выключатель — правило 1, `?studio=1` его не обходит, `'false'` тоже выключает; выключатель гасит только интерфейс — серверный откат = снять отметки (К1, T5).
- **Dev-подмена профиля** — только `import.meta.env.DEV && DEV_AUTOLOGIN` и без настоящей сессии; модуль `devProfiles.ts` динамически под `DEV`; сторож `dist` по уникальному маркеру, ключу и чанку, проверен мутацией. `DEV_AUTOLOGIN` вне `DEV` — бэклог (держит `dist-e2e`) (К12, T9).
- **K:** `notes` — понятный `22023` в RPC; длину держит CHECK `orders_notes_len` на таблице, поставленный ещё в L вместе с классификацией `notes` (прямой PATCH продавцом-автором в обход RPC → `23514` с минуты применения L); `zone_id` — CHECK ровно `ZONE_ID_RE.source` + `22023` в RPC; изменяемо только в `draft` (стражи); K не трогает `order_v4_guard` (К5, T2).
- **L:** v3 — отказ стражем, а не политикой: `order_v4_guard` (INSERT/UPDATE) **и** `order_v4_delete_guard` (DELETE); ветка v3 после проверок служебного доступа и веток «родитель удалён»/«заказ ERP удалён» (FK `ON DELETE SET NULL`, SQL Editor, миграции не ломаются); отказ только клиенту. `order_comments` закрыта `revoke` целиком (uuid автора нет, потребителей нет), без `drop`. Журнал признаков пишет AFTER UPDATE-триггер `security definer` с `search_path`, включая служебные смены (`actor` null, `source='service'`); клиенту `revoke` (К6, T2).
- **Порядок и откаты:** L < K по времени и выкатке; md5-цепочка J → L → K → откаты под сторожем; откат K не открывает v3; в файлах контроллера нет `drop`/`delete` (К6, Global Constraints).
- **M:** удаление только после совпадения md5 со снимком; политика — `alter policy`.
- **Уборка:** отдельная функция `order-files-gc`; ворота — `is_admin()` вызывающего (как `storage-gc`, не «только `service_role`»); удаление — только `apply: true` **и** секрет `ORDER_FILES_GC_DELETE='1'`; еженедельный скрипт с ключом `service_role` — без кода удаления; в summary только числа (пути клиентов не попадают в логи Actions); текстовый носитель и страницы со сверкой `count`; `garment-flats` — только недописанные версии (К8, T7).
- **Регресс на бою перед включением** — пункт 11 чек-листа: пробы прав под двумя продавцами, МС, rop, дизайнером, Storage `order-artworks`/`garment-flats`, `get_advisors(security)` без новых ERROR/WARN.
- Миграции: `revoke … from public, anon` → `grant … to authenticated`; `(select auth.uid())` в предикатах; функции-триггеры — `revoke execute` от клиентских ролей.
