# Спека: единый поток заказа «изделие → дизайн → ТЗ PDF → запуск» в стиле ERP

## Context

**Как сейчас.** У менеджера два параллельных пути: визард на главной (сохраняет v3) и «Заказы v4» с переносом «Оформить как заказ v4». Шапка вводится дважды, комментарий и «папка макетов» теряются. Логотипы никуда не загружаются, PDF ТЗ — это `window.print()`. Моста в производство нет, стиль Order не совпадает с ERP, есть мусор: выбор роли, онбординг, Ctrl+K.

**Цель владельца.** Один бесшовный поток с минимумом действий:
1. Менеджер продаж выбирает изделие, ткань поставщика, цвет и размеры.
2. На шаге «Дизайн» ставит логотипы на изделие на холсте из `PNHD-design-maker`. Мм, зоны и техники сами попадают в ТЗ.
3. Получает PDF ТЗ и отправляет «в работу».
4. Менеджер сопровождения (МС) проверяет и запускает в производство.

Админка даёт полное управление, Order выглядит как ERP.

**Критерий успеха.** Первый настоящий заказ прошёл от менеджера до цеха без ручного перебивания данных.

### Решения владельца (16.10)

| Тема | Решение |
|---|---|
| ERP | Боевая: из ERP **берём всё нужное (импорт кода, вызов существующих RPC и стора), код и схему ERP не меняем** |
| Дизайн-мейкер | Переносим в шаг «Дизайн» и выпускаем сразу в потоке |
| Модели без своего флэта | **Типовой флэт по виду изделия** с пометкой в ТЗ. Точные флэты моделей добавляются в админке и автоматически заменяют типовой |
| Удаляем | Канбан v3, аналитику продаж, `/print`. Экспресс-калькулятор оставляем |
| Доступ | Менеджер продаж видит свои заказы. **МС — существующая роль ERP `erp_employees.role = 'manager'`**: видит заказы «в работе» и запускает. admin/director видят всё |
| Оплата | Нужна **отметка оплаты** (предоплата или полная). Запуск без неё — только решением РОПа или директора с причиной |
| КП | Не в этом выпуске |
| Запуск | МС проверил ТЗ и автоматический маршрут, поставил дату, нажал «Запустить». Сложные случаи (подряд, образцы) идут тем же путём, что форма ERP |
| Админка в первом выпуске | Поставщики и палитры; флэты и зоны дизайн-мейкера; бирки и упаковка; правила цены (порог маржи, ставки подготовки) и сотрудники (все заказы, смена менеджера) |

### Допущения, которые владелец может поправить
- МС видит цену заказа. В ТЗ для цеха цен нет.
- Работа идёт с компьютера; на телефоне — только список и просмотр.
- Всё разрабатывается за флагом раздела, который уже есть (`orderStudio`), и включается для людей, когда поток готов целиком.

## Архитектура

### Данные: только сторона Order, ERP не трогаем
- Заказ — существующие таблицы v4 `orders` (`schema_version = 4`), `order_items`, `order_item_prints`, `order_item_labels`. Запись через `order_v4_save_full`.
- **Новые колонки и таблицы Order** (миграции не на `erp_*`):
  - `orders.notes` — общий комментарий (в форме и в ТЗ — веха 8; в 6+7 не печатается, К8 плана 6+7);
  - `orders.paid_at`, `paid_kind`, `paid_override_reason`;
  - `order_items.tz_pdf_path` — PDF ТЗ группы позиций (одно ТЗ на модель, ткань и дизайн; см. «Формат ТЗ»);
  - `order_item_prints.layout` (jsonb) — размещение на холсте, `artwork_path`;
  - таблица `sales_staff_overrides` — при необходимости, для смены менеджера.
- **Каталоги Order:**
  - `catalog_config.suppliers` + `supplierPalettes`;
  - `app_config.labelsCatalog`, `packOptions` (в `prices`), `garmentFlats` (типовые флэты по виду; связь флэт ↔ модель — список `flat.sku_codes` у флэта, а не `flat_id` у SKU — уточнено в вехе 5б, 18.10);
  - `prices.minMarginPct`, `prepFees`.
- **Хранилище:** новый приватный бакет `order-artworks` — логотипы, PDF ТЗ; SVG флэтов — отдельный приватный бакет `garment-flats` (веха 5а, миграция H; уточнено 18.10). Пути только ASCII. Загрузка сразу при выборе файла.
- **Права:**
  - функция Order `sales_is_ms()` — security definer, только читает `erp_employees` с активной ролью `manager`;
  - RLS `orders`/`order_items`/`order_item_*` на команду: автор-менеджер — свои; МС — заказы со статусом `ready_to_launch` и выше; admin/director — всё.

### Статусы v4 (используются существующие)
`draft` → `ready_to_launch` («в работе у МС», после «Отправить в работу») → `production` (после запуска) → `done`. Плюс `archived`. «Вернуть менеджеру» переводит обратно в `draft` с комментарием. Правка заказа — только в `draft`.

### Решения ревью 16.10 (архитектура, тесты, UX, безопасность)
- **Экран заказа — рабочее место, а не линейный визард** (решение владельца):
  - слева список изделий заказа и «+ изделие»;
  - справа редактор выбранного изделия, вкладки «Изделие» · «Дизайн»;
  - сверху вкладки «Клиент и доставка» и «ТЗ и цена».
  - У нового заказа подсказывается порядок, но переход свободный. Тот же экран открывается для правки.
- **Каждый цвет — отдельная позиция** (решение владельца). Кнопка «Дублировать в другом цвете» копирует позицию с дизайном и предлагает другой цвет печати. В ТЗ такие позиции сходятся в одно (строки сетки «ЦВ/РАЗМ»).
- **Клиент** заполняется в любой момент, обязателен только к «Отправить в работу».
- **PDF ТЗ** формируется автоматически при «Отправить в работу»; предпросмотр — по желанию.
- **Статусы и блокировку правки держит сервер**, не только клиент:
  - RPC Order `order_v4_transition(id, to, reason)` проверяет роль и разрешённые переходы;
  - триггер Order запрещает правку позиций, нанесений и шапки не в `draft`.
- **Запуск идемпотентен.** Повтор после частичного сбоя при `23505` находит заказ ERP по `tz_order_id` и дописывает недостающее: ТЗ и связь. Статус `production` ставится последним.
- **Один источник правды — заказ v4.** Редактор держит буфер текущей позиции и синхронизирует его через `wizardAdapter` при каждой правке (автосохранение).
- **Одно размещение на холсте = одна строка нанесения.** Хранятся `flat_id` и версия флэта. PDF ТЗ — неизменяемый снимок.
- **Прототип запуска переезжает во веху 2.** Это главный риск: из Order — `ensureDomainSlices()` (`erp/lazyScreen.js:23`) → загрузка цехов → `createOrder` на моке.
- **Техника по умолчанию** — из правил категории. Предупреждения preflight (DPI, мелкие линии для вышивки) — на холсте. Поля мм и отступа в инспекторе — клавиатурная альтернатива перетаскиванию.
- **Безопасность загрузок:**
  - SVG показывается только как изображение (без `innerHTML`) и очищается при загрузке;
  - тип файла определяется по содержимому; лимит 25 МБ;
  - PDF и AI разбираются `pdfjs-dist` только в воркере;
  - бакет приватный, ссылки подписанные, политики Storage на команду.
- **`sales_is_ms()`** — `security definer`, `search_path = public`, `revoke from public, anon`, `(select auth.uid())`.
- **«К запуску» — один экран:** PDF слева, чек-лист и оплата справа, дата запуска по умолчанию — следующий рабочий день, список отсортирован по сроку.

### Экраны Order (оболочка в стиле ERP)
- Сайдбар:
  - «Новый заказ»;
  - «Мои заказы» (у admin/director — «Все заказы»);
  - «К запуску» (МС);
  - «Экспресс»;
  - «Каталог» (admin/director);
  - переключатель в «Производство».
- **Рабочее место заказа** `/sales/:id`; «Новый заказ» сразу создаёт черновик v4, дальше автосохранение:
  - список изделий слева, у каждой позиции «Дублировать в другом цвете»;
  - **Изделие** — модель, ткань у поставщика, цвет из палитры поставщика, размеры. Шаги визарда `StepGarment` переиспользуются как панель;
  - **Дизайн** — холст дизайн-мейкера: флэт модели или типовой, виды перед/спина/рукава. Загрузка логотипа, перетаскивание в зону, мм, техника по зоне, Pantone. Бирки — здесь же;
  - **Клиент и доставка** — шапка один раз, комментарий, упаковка заказа, срочность;
  - **ТЗ и цена** — сводка, цена, скидка, ручная цена, отметка оплаты, предпросмотр PDF, «Отправить в работу» (чек-лист, PDF формируется сам);
  - «доп. поля ТЗ» позиции (отступ, пошив, упаковка позиции) — раскрывашка из нынешнего `ItemEditor`.
- **Уходят:** главная `/` как отдельный визард v3, `SalesCard` в нынешнем виде, `transferToSales`, `itemSession`/`ItemWizard`.
- **«К запуску» (МС):**
  - список заказов `ready_to_launch`;
  - открытие показывает PDF ТЗ, поля, оплату, маршрут (просмотр) и дату запуска;
  - кнопки «Вернуть менеджеру» и «Запустить».

### Запуск — `orderstudio/bridge/launch.ts` (ERP не меняется)
1. Ленивый `import()` стора ERP (`erp/store/useErpStore`).
2. Загрузка справочников, нужных `createOrder` (цеха). Это существующие действия стора, вызываются без изменений.
3. `tzToErpDraft(order)` → `NewOrderInput` + `tz_order_id`/`tz_number`. Поля шапки уходят через существующий spread `orderFields` в `orderWriteSlice.ts:81`.
4. `useErpStore.getState().createOrder(input)` — тот же путь, что у формы ERP: маршрут, подряд, разработка для образцов. Двойной запуск ловит уникальный индекс `erp_orders_tz_order_uniq`; повтор показывает «уже запущен» со ссылкой.
5. ТЗ-PDF и макеты (веха 6+7, К12): до `createOrder` МС пересверяет хэш ТЗ (`tzcheck`), копирует PDF группы — по копии на КАЖДУЮ позицию ERP — и макеты нанесений и бирок в `erp-attachments` (`api/erpFiles.ts`, ключи `tz/v4-<попытка>/…`, `att/v4-<попытка>/…`, тип по байтам), повторяет `launch_check` (`recheck`) и передаёт их секциями `tz.documents` (`item_index` — индекс позиции в payload) и `attachments` в тот же `erp_create_order` — одна транзакция. `uploadTzDocument` после создания не используется. Переход в `production` — с `p_erp_order_id` созданного заказа (проверка подлинности на сервере).
6. Order пишет `orders.erp_order_id` и `status = 'production'`.

Тяжесть стора ERP — только в чанке экрана запуска. `bundle:budget` подтверждает, что оболочка ERP не растёт.

### Формат ТЗ — по пяти образцам владельца (16.10)
Образцы: 63886 «Эквилент Олд Мани», 67108 «Фертоинг» (образец), 68180 «АО НАВИС» (футболка, свитшот, поло).

**ТЗ — на модель (группу позиций), а не на заказ.** У 68180 три отдельных ТЗ. Цвета одной модели и дизайна идут в одном ТЗ (см. «Решения владельца (раунд 3)»). В ERP — `erp_tz_documents.item_id` = каждая позиция группы.

Страницы PDF повторяют образец один в один:
1. **Шапка:**
   - «ТЕХНИЧЕСКОЕ ЗАДАНИЕ К ЗАКАЗУ № [сделка] название»;
   - менеджер проекта, дата оформления, дата сдачи;
   - вид изделия — название модели или «лекала клиента»;
   - количество;
   - упаковка: нет / БОПП / ZIP / другое + текст;
   - стикеры: нет / бланк / другое + текст, плюс картинка содержимого стикера;
   - без ЧЗ, комментарий заказа.
2. **Полотно:**
   - основное, отделочное, цвет (у колорблока — список цветов деталей), поставщик;
   - матрица «зона × техника» (Ш / В / Т = трансфер DTF и флекс / DTG / П = прочее и подряд) — строится автоматически из нанесений;
   - сетка цвет × размер 2XS–4XL + ONE с итогом;
   - пустая строка «Сборка/швея» для цеха;
   - «Описание модели», «Доп. обработки» (текст + обработки каталога).
3. **Параметры бирок:**
   - отметки «размерник бланк» / «составник бланк»;
   - до 3 превью бирок (картинки);
   - до 3 схем притачивания из набора (горловина с закрытием по центру, левый внутренний боковой шов, …);
   - 3 комментария.
4. **Нанесение № N — страница на каждое:**
   - техника и спецэффекты, ткань (из позиции — не вводится второй раз);
   - размер В × Ш мм;
   - расположение текстом;
   - отступ: число + ориентир (шов горловины / верхний край / шов) + на готовом или на крое;
   - Pantone номером или словом;
   - комментарий; у подряда — подрядчик и срок;
   - **мокап с размерными линиями** (тех-лист дизайн-мейкера) и превью макета на цвете изделия;
   - сетка нанесения;
   - поле «После проверки ____».
5. **Заметки к заказу:** карточки «картинка + подпись» — фурнитура (из каталога фурнитуры или своя), референсы, дизайн упаковки.
6. **Подвал на каждой странице:** текст допусков и оговорка о претензиях. Текст правится в админке (в образцах есть варианты «до 2 см» и «до 10 мм»). Ссылка на заказ — текстом в подвале (`APP_ORIGIN`); QR — нет (новый пакет, решение владельца — веха 8; К9 плана 6+7). Переполнение — пометка «(продолжение на стр. N)»: стрелки «→» в шрифте нет.

**Что добавляется в модель v4** (миграции стороны Order):
- позиция: `supplier` отдельным полем; `model_description`, `extra_processing_note`; `client_pattern` (название лекал клиента — тогда «вид изделия» в ТЗ = оно; базовая модель каталога даёт флэт, зоны и цену, цена может быть ручной); `part_colors` jsonb (колорблок: деталь флэта → цвет палитры);
- бирки: флаг `blank`, `preview_paths[]`, `attach_scheme` (код из набора схем);
- нанесение: `offset_mm` + `offset_from` (горловина / верхний край / шов / центр) + `on`; `effects`; `contractor`, `contractor_days` (техника «прочее/подряд», в том числе эмбоссинг; цена — ручная);
- заказ: `sticker_preview_path`; таблица `order_notes_cards` (картинка, подпись, ссылка, позиция или заказ).

**Решения владельца:**
- «лекала клиента» = базовая модель + название лекал;
- колорблок задаётся цветом деталей на холсте;
- «Сборка/швея» и «После проверки» остаются полями для ручки.

**Эталоны для тестов.** Пять образцов становятся фикстурами `src/orderstudio/fixtures/{63886,67108,68180-tee,68180-sweat,68180-polo}.json`: заказ v4 → `tzDocument()` даёт те же поля, что в образце. Расхождение «350 г / 330 г» в образце 68180 — пример ошибки ручного ввода, который автозаполнение исключает.

### ТЗ в PDF
- Генератор на базе экспорта дизайн-мейкера: jsPDF + svg2pdf, кириллица LiberationSans, векторные флэты с логотипами.
- Разделы по `docs/erp/tz-format-analysis.md`: шапка, полотно и сетка цвет × размер, нанесения блоками (вид, мм, отступ, техника, Pantone), бирки, упаковка, комментарии. Пометка «по типовому флэту», где он использован. Цен нет.
- PDF — на группу позиций: `order-artworks` → `orders/<id>/tz/<uuid>-<PH-XXXX>-g<hash8>-c<hash12>-<модель>.pdf` (веха 6+7, К1: путь `tz/<order>/<groupKey>.pdf` не проходит `order_artwork_path_ok`; хэши группы и содержимого — в начале имени, новая версия — новый ключ, старые — история). Путь — в `order_items.tz_pdf_path` у каждой позиции группы (колонка `orders.tz_pdf_path` не нужна). Менеджер может скачать все ТЗ черновика одним файлом — сборкой тех же групп (`buildAllTzPdf`, К23), а не склейкой.
- **Чек-лист «Отправить в работу»:** ткань и цвет; сетка не пуста; у каждого нанесения есть макет и мм; клиент и срок; PDF сформирован после последней правки.

### PDF ТЗ — проверка по образцам (раунд 3, 16.10): что уточнено
Повторный постраничный разбор пяти образцов выявил, что ещё должен уметь генератор:

| Что в образцах | Решение в генераторе |
|---|---|
| Сетка «ЦВ/РАЗМ» — 4 строки цветов на странице полотна, 3 на странице нанесения | Строк столько, сколько цветов; больше 4/3 — таблица продолжается на следующей странице, а не обрезается |
| Колонки 2XS…4XL + ONE фиксированы | Стандартный набор всегда; размер вне набора (5XL, детские, свой) — доп. колонка, итог считается от всех |
| Матрица зон — 9 жёстких строк (полочка, полочка Л/П, спинка, рукав Л/П, капюшон Л/П, карман) | Зона каталога → строка матрицы через поле `tz_row` в `zonesCatalog` (админка «Флэты и зоны»): `tz_row` — код из перечня (`catalog/tzRows.ts`: 9 строк матрицы + `other`), у зоны флэта — переопределение (`area.tz_row`, например полочка Л/П у зип-худи); цепочка `area.tz_row` → `zone.tz_row` → код по умолчанию → `other` (веха 5б, 18.10); зона без строки → строка «Другое: …» под матрицей. Сторож: у каждой зоны каталога есть строка или «другое» |
| Отступ бывает текстом («согласно комментарию», «2 см от шва вверх» у колорблока) | Структура `offset_mm` + `offset_from` (горловина / верхний край / шов детали / центр) + направление; плюс `offset_note` — свободный текст, если схема не подходит. В ТЗ: «10 см от шва горловины, на готовом» |
| Мокап печати: вид (перед / спина / левый рукав / правый рукав), на нём ВСЕ печати этого вида с размерными линиями (67108 №2–4 — один мокап спины) | Мокап = вид флэта с печатями этого вида; размерные линии Ш, В и отступа у каждой; текущая печать выделена. Рукава — отдельные виды флэта |
| Мокап в цветах изделия, у колорблока — по деталям | Заливка деталей флэта из `part_colors`; без колорблока — цвет позиции |
| «Превью (макет)» — логотип на фоне цвета ткани | Растр/вектор макета на фоне цвета позиции |
| Схемы притачивания — и картинки из набора, и ФОТО (63886) | `attach_scheme`: код из набора ИЛИ загруженное изображение |
| Комментарии к биркам — три колонки под превью | Три поля комментария, по колонке |
| Комментарий на 1-й странице — у каждого ТЗ свой («Футболки FREE FIT с вышивкой…») | Поле `tz_comment` у позиции (разный у цветов группы — «Чёрный: …»); комментарий заказа (`orders.notes`) — веха 8 |
| Стикер: «другое» + текст + картинка содержимого (63886) | Как в плане; картинка — под комментарием 1-й страницы |
| Заметки: сетка 2×2 «картинка + подпись», бывает заголовок раздела («Фурнитура»), ссылка текстом | Карточки с необязательным заголовком группы; > 4 карточек — следующая страница; ссылка печатается текстом и кликабельна |
| «Цвета Pantone»: «1204», «Белый» | Свободный список; номер нити у вышивки — тот же список |
| Допуск в подвале разный («до 2 см» и «до 10 мм» в ОДНОМ документе 68180) | Один текст из админки на все страницы — расхождение образцов не воспроизводим |
| Ткань на странице нанесения вбивалась вручную («330 гр» против «350 гр», «470 гр» против «470 гр/м2») | Всегда из позиции, одна функция подписи (`fabricDisplayName`) для всех страниц |
| «Вид изделия» — имя файла лекал (`Fertoing_T-shirt_Regular_01.10.2025`) | `client_pattern` печатается как есть, перенос строки по ширине поля |
| Размер файла образцов 4.6–5.3 МБ | Картинки ужимаются до 200 dpi по размеру ячейки, JPEG для фото, вектор для флэтов; цель ≤ 8 МБ на ТЗ, сторож в e2e |

**Переполнение полей.** У образца поля фиксированного размера. Правило: шрифт уменьшается до 8 pt, дальше — текст продолжается на странице «Продолжение: <поле>», ничего не обрезается молча. Чистая функция `fitText(box, text)` с unit-тестами.

**Решения владельца (раунд 3):**
- **Одно ТЗ на группу позиций.** Группа — позиции одной модели (или лекал клиента), одной ткани и с одинаковым дизайном (набором нанесений). Разные цвета идут строками сетки «ЦВ/РАЗМ». Ключ группы считает чистая функция `tzGroupKey(item)`. «Дублировать в другом цвете» сохраняет ключ группы. При запуске копия PDF кладётся на КАЖДУЮ позицию ERP группы секцией `tz.documents` того же `erp_create_order` (веха 6+7, К12): ТЗ видно всем цехам маршрута, ERP не меняется. Путь PDF — `orders/<id>/tz/<uuid>-…-g<hash8>-c<hash12>-….pdf` в `order-artworks` (К1), хранится у каждой позиции группы.
- **Подвал по умолчанию:** «…расхождение в расположении до 2 см…». Текст правится в админке.
- **«Дата оформления»** — дата «Отправить в работу». Ставится сама.
