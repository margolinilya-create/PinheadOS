## 2. Место раздела в потоке заказа

```
Шапка заказа → [1] Изделие → [2] ДИЗАЙН → [3] Бирки и упаковка → [4] Расчёт и цена → [5] КП (PDF) → оплата → [6] ТЗ (PDF) → запуск в ERP
                    │              │
                    │              └─ на входе: позиция с sku_code, flat_id, сеткой «цвет × размер»
                    └─ здесь выбираются модель (sku_catalog), посадка, ткань, цвета (палитра поставщика)
```

**Контракт шага «Дизайн».**

**Вход** — `order_items`:

- `sku_code`, `product_type`, `fit`, `flat_id`;
- `size_grid` (`rows[].color`, `sizes`);
- `main_fabric`, `color_supplier`, `part_colors`.

**Выход** — строки `order_item_prints` (одна строка = одно нанесение), в каждой:

- `method`, `zone_id`, `zone`;
- `width_mm`, `height_mm`;
- `offset_mm`, `offset_from`, `offset_dir`;
- `colors`, `pantone[]`, `textile`, `print_on`, `effects[]`, `sizes[]`;
- `artwork_path`, `layout` (jsonb).

Цена позиции пересчитывается сразу. В КП уходят мокапы. В ТЗ уходят схема размещения и файлы печати.

**Правило шага:** дизайн **необязателен**. Менеджер может заполнить нанесение руками (зона + мм + метод) без холста, как сейчас в форме. Холст — ускоритель, а не обязательный путь (решение 27.09: «layout optional, mm can be entered by hand»).

**Кто работает в шаге** (решение 27.09):

- **менеджер** делает черновую раскладку для КП;
- **дизайнер** доводит её для ТЗ. Очередь дизайнера сортируется по сроку заказа автоматически.

## 4. Что берём из BlankBuilder (и чем делаем лучше)

| BlankBuilder | Pinhead Order: решение |
|---|---|
| Три панели: выкройка, 3D, свойства | Три панели: **флэт (рабочий холст)**, **превью в цвете ткани**, **свойства нанесения и цена**. 3D — позже (D9) |
| Пресеты «Поставить на место»: грудь, лого слева, низ, спина, под воротом, рукава, бирка, принт-бирка | **Пресеты зон из флэта.** У каждой `print_area` есть точка по умолчанию, размер по умолчанию и разрешённые методы. Один клик ставит макет по стандарту Pinhead (например, «лого слева 90 мм, 70 мм от шва горловины») |
| Размер подписан на детали («26 × 10,2 см») | Размер и **отступ от шва горловины** подписаны на холсте. Это то, что пишется в ТЗ |
| Смена модели не сбивает дизайн | При смене флэта или посадки раскладка переносится по `area_id` и якорям. Если не влезает — предупреждение |
| Ткань: любой цвет, градиент | Цвет ткани — **только из палитры поставщика** (`suppliers.palette`), строки `size_grid` переключаются вкладками. Мокап совпадает с тем, что сошьют |
| Слои, текст, фигуры, ⌘V, отмена | Слои = нанесения позиции. Вставка из буфера, отмена и повтор. Текст — с конвертацией в кривые для производства (D4) |
| Изнанка, бирка в вороте, принт-бирка | Зона `label` уже есть на флэтах. Связать с `order_item_labels` (принт-бирка — тоже нанесение) |
| Экспорт: файлы печати 300 dpi, техкарта PDF, панели для сублимации | **Файлы печати** (PNG/исходник в натуральную величину) + страница размещения в **ТЗ PDF** (`tz-pdf`) + мокапы в **КП PDF** |
| Тарифы и облачный рендер | Не нужно: внутренний инструмент |
| Чего у них **нет** | **Живая цена и срок по методу, проверки производства (DPI, мин./макс. размер, число цветов для шелкографии, белая подложка), Pantone, градация по размерам, передача в ERP** — это наше преимущество |

### 5.1. `order_item_prints.layout` → v2 (обратная совместимость с v1)

CHECK меняется на `v in (1, 2)` (≤ 8 КБ сохраняется). Клиент читает v1 и v2, пишет v2.

```jsonc
{
  "v": 2,
  "flat_id": "hoodie-regular", "flat_version": 2,
  "view": "front",                      // front | back | sleeve_left | sleeve_right | hood | pocket | label
  "area_id": "chest-left",
  "anchor": "neck_seam",               // от чего меряем: neck_seam | top_edge | part_seam | center
  "x_mm": 0, "y_mm": 70,               // смещение центра макета от якоря (а не абсолют SVG)
  "rotation_deg": 0, "flip_h": false, "flip_v": false,
  "lock_ratio": true,
  "source": {                           // что лежит в нанесении
    "kind": "image",                   // image | text | shape
    "asset": {
      "type": "png|jpg|svg|pdf|ai|psd|tif",
      "px_w": 1122, "px_h": 1402,
      "dpi": 300,                      // прочитано из файла; null у вектора
      "vector": false,
      "intrinsic_w_mm": 95, "intrinsic_h_mm": 118.7,
      "size_estimated": false,
      "preview_path": "orders/<id>/previews/<uuid>.png",
      "colors_detected": 2,            // для шелкографии
      "has_transparency": true
    },
    "text": null                       // для kind=text: { "value", "font", "weight", "size_mm", "tracking", "align", "color_hex", "outlined_path" }
  },
  "grading": [                          // необязательно: размер по группам размеров
    { "sizes": ["2XS","XS","S"], "scale": 0.9 },
    { "sizes": ["M","L","XL"], "scale": 1.0 },
    { "sizes": ["2XL","3XL","4XL","5XL"], "scale": 1.1 }
  ],
  "checks": { "dpi_ok": true, "inside_safe": true, "min_size_ok": true, "colors_ok": true },
  "designer_final": false              // true — дизайнер довёл до ТЗ
}
```

Зачем менять координаты: в v1 `x_mm`/`y_mm` — абсолютные координаты в SVG флэта. Это ломается при новой версии флэта. В v2 отсчёт идёт **от якоря** — так же меряют в цеху и пишут в ТЗ. `offset_mm` и `offset_from` вычисляются из `anchor` и `y_mm`; источник истины — колонки (их читает ТЗ и мост).

**[проверить в коде]**: как холст 5а считает `offset_mm` и где лежит функция «layout → колонки». Её нужно расширить, а не дублировать.

### 5.4. Градация по размерам

Колонка `sizes[]` в `order_item_prints` уже есть — нанесение «только для этих размеров». Варианты:

- **А (проще):** одно нанесение = один размер на все размеры, плюс в ТЗ «допуск до 2 см» (как сейчас).
- **Б:** `layout.grading[]` с коэффициентом по группам размеров. ТЗ печатает таблицу «размер → ширина × высота → отступ».
- **В:** отдельная строка нанесения на группу размеров (через `sizes[]`).

Рекомендация: начать с **А** и подготовить данные под **Б**. Решает владелец — вопрос Q3 в разделе 12.

### 5.5. Хранилище

В `order-artworks/orders/<uuid>/` добавляются папки (ASCII):

- `artworks/` — исходники клиента (есть);
- `previews/` — PNG-превью для AI/PDF/PSD/TIFF;
- `mockups/` — мокапы позиции по видам и цветам для КП;
- `print-files/` — файлы печати в натуральную величину для ТЗ и цеха.

### 6.2. Действия и поведение

1. **Добавить нанесение:**
   - загрузка файла: перетащить, выбрать или вставить через Ctrl/⌘+V;
   - или «Без макета» — только зона и размер (ручной режим, как сейчас).
2. **Пресет зоны** — один клик: вид, зона, размер по умолчанию, отступ, метод по умолчанию.
3. **Перемещение и размер:** ручки, стрелки (1 мм, с Shift — 10 мм), ввод в мм. Пропорции заблокированы по умолчанию.
4. **Снап:** к центральной оси, якорю горловины, краям safe-зоны. Подсветка, когда центр на оси.
5. **Подписи на холсте:** `90 × 72 мм` и выносная линия «70 мм от шва горловины». Это ровно та строка, что попадёт в ТЗ.
6. **Ткань:** переключатель цветов из `size_grid.rows` позиции. Флэт перекрашивается (SVG fill по `part_colors`, детали разных цветов тоже).
7. **Копировать нанесение:** в другую позицию заказа, на другой вид (зеркально левый ↔ правый рукав), во все позиции заказа («лого везде»).
8. **Смена флэта** (другая посадка): нанесения переносятся по `area_id`. Если не влезает — жёлтая плашка «уменьшить до максимума зоны?».
9. **Режим дизайнера** (право `order.design_final` или роль `designer`) **[проверить существующие роли]**: кнопка «Готово для ТЗ» ставит `designer_final = true`; редактирование в заказе после `draft` — только у дизайнера, пока ТЗ не сформировано.
10. **Горячие клавиши:** Del, Ctrl/⌘+D (копия), Ctrl/⌘+Z/Shift+Z, ←↑→↓, Shift+стрелки, 1–6 (виды).
11. **Пустое состояние:** «Добавьте макет или выберите стандартную раскладку». Ниже — 3–4 частые раскладки Pinhead.
12. **Онбординг:** тур из 4 шагов при первом входе (как у BlankBuilder): загрузить → поставить на место → проверить цену → далее.

### 6.3. Проверки (живые, на холсте и при «Далее»)

| Проверка | Уровень | Источник правила |
|---|---|---|
| Макет вышел за safe-зону области | ошибка (ТЗ не сформировать), менеджер может отметить «осознанно» с комментарием | `polygon_mm` и `safe_inset_mm` |
| Размер больше максимума зоны или метода | ошибка | `max_w_mm`, `methodRules` |
| Размер меньше минимума метода | ошибка | `methodRules.min_w_mm` |
| Эффективный DPI при печатном размере < `min_dpi` | ошибка; от `min_dpi` до `rec_dpi` — предупреждение | asset.px, `width_mm` |
| Шелкография: цветов в макете больше `screenMaxColors` или указанного числа | предупреждение | `colors_detected` |
| Метод не разрешён для зоны | ошибка | `print_areas.methods` |
| Растр без прозрачности под DTF или DTG на цветной ткани | предупреждение «будет белый фон / нужна подложка» | asset |
| Вышивка: деталь мельче `min_detail_mm` | предупреждение | эвристика по размеру и текст < 5 мм |
| Флэт не той категории, что модель (баг B1) | ошибка | `flat.categories` vs `sku.category` |
| Нанесение без `zone_id` (кроме `other`) | ошибка | B2 |

Все проверки — чистые функции в `orderstudio/design/checks.ts` с юнит-тестами. Сервер повторяет критичные (размер, зона, категория флэта) в стражах `order_v4_save` и `order_v4_launch_check`.

## 7. Цена и срок — живой расчёт

1. Холст меняет `width_mm`, `height_mm`, `method`, `colors`, `effects` → вызывается **тот же калькулятор**, что считает позицию в шаге «Расчёт» **[проверить: catalogSlice / pricing-модуль Order]**. Второй калькулятор не пишем.
2. Формат для шелкографии и DTG (`screenFormats`: A4/A3/A3+/Max) выводится из размера автоматически. Менеджер видит «A3 → 210 ₽».
3. DTF: метраж плёнки из размера и раскладки на ширине `dtfFilmWidth` × тираж → `dtfSteps`.
4. Вышивка: стежки ≈ площадь × `embStitchesPerCm2` × `fill` → `embTiers`, `embColorAdd`, `embAreaAdd`.
5. Срок: метод добавляет дни (шелкография — сетки; подряд — `contractor_days`). Подсказка «+2 дня» в итоге позиции.
6. Наценка и порог РОП (решение 27.09: ниже порога — согласование РОП) — в шаге «Расчёт», дизайн только показывает итог.

Тест: для 3–5 реальных заказов владельца (эталоны) цена после раскладки на холсте совпадает с ценой формы ±1 ₽.

## 8. Выходы раздела

### 8.1. Мокапы для КП

- PNG по видам (перед и спина, плюс виды с нанесениями) × по цветам из `size_grid` → `mockups/`.
- Рендер на клиенте (canvas/Konva → toBlob) в 2× для ретины. Сервер не нужен.
- Сцена — фирменный стиль Pinhead: фон, логотип, подпись модели и цвета. Настройка в админке (аналог «Сцена» у BlankBuilder, но один фиксированный стиль).
- КП PDF берёт мокапы из `mockups/` **[проверить: каким движком собирается КП — по решению 27.09 был спайк jsPDF vs edge]**.

### 8.2. ТЗ PDF (edge-функция `tz-pdf`)

На каждую позицию — страница «Размещение»:

- флэт в цвете ткани с нанесениями;
- размерные линии: ширина × высота, отступ от якоря;
- таблица: № | Зона | Метод | Размер, мм | Отступ | Цвета/Pantone | Эффекты | Размеры | Комментарий;
- если включена градация — таблица по группам размеров;
- подвал из `tzSettings` («Допуск по размещению — до 2 см»).

### 8.3. Файлы печати

- Для каждого нанесения: исходник клиента плюс подготовленный файл в натуральную величину (PNG 300 dpi с прозрачностью; для вектора — исходник).
- Имя: `<номер-заказа>_p<позиция>_<zone_id>_<метод>_<Wx H>mm.png`, ASCII.
- Пакет ZIP — по кнопке в заказе (для менеджера и дизайнера).
- При запуске — копия в `erp-attachments` (см. 8.4).

### 8.4. Мост в ERP (не трогая ERP)

`order_v4_launch` уже переносит нанесения в `erp_item_prints` (`method`, `zone`, `width_mm`, `height_mm`, `offset_note`, `pantone`, `special`, `garment_kind`) **[проверить точное сопоставление в RPC запуска]**. Добавляем только на стороне Order:

- `offset_note` собирается из `offset_mm`, `offset_from`, `offset_dir` («70 мм от шва горловины вниз»);
- `comment` — плюс «Метод по зоне: …, градация: …»;
- файлы печати и страница размещения уходят как вложения вида `print` (виды вложений `print`/`label`/`note` уже есть в ERP — миграция `erp_attachment_kinds_print_label_note`) через существующий путь `tz.documents`.

Если для этого нужна правка `erp_*` — **стоп**, вынести владельцу отдельным решением (аксиома A1).

## 13. Риски

| Риск | Мера |
|---|---|
| Колонки и `layout` расходятся (менеджер правит мм руками в форме) | Источник истины — колонки; `layout` пересчитывается из колонок при ручной правке; тест на взаимную сходимость |
| Флэты неточные (масштаб SVG) → неверные мм в ТЗ | Калибровка по двум точкам в админке; эталонная проверка на одном изделии с линейкой в цеху |
| Тяжёлые AI/PSD тормозят браузер | Превью генерируется один раз и кешируется в `previews/`; лимит бакета 25 МБ уже есть |
| SVG клиента с JS | Показ только через `<img>` (правило миграции C) |
| Затирание справочников двумя админами | `catalog_put` с `p_base` (уже есть) |
| Соблазн «поправить чуть-чуть ERP» для моста | Аксиома A1 + `erpFrozen.test.ts`; любые нужды ERP — отдельное решение владельца |
| Раздувание `layout` > 8 КБ (текст, градация) | Полигоны и пути текста хранить в файле, в `layout` — только ссылки и параметры |
