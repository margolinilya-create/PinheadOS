## A. Останавливает работу прямо сейчас

### A1. `is_admin()` не проверяет `active` и `approved` — уволенный админ возвращает себе доступ

```sql
CREATE FUNCTION public.is_admin() ... AS $$
  SELECT EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin');
$$;
```

Для сравнения, `erp_is_member()` проверяет оба флага — то есть ERP-контур закрыт, а
Order Studio нет. Политики `orders_*`, `app_config_*`, `catalog_config_*`, `order_audit_select`
проверяют только `p.role`.

Документированный способ увольнения — soft-delete `active=false` — не трогает `auth.users`,
поэтому refresh-токен продолжает выдавать валидный JWT. С ним бывший сотрудник правит цены и
каталоги, читает и удаляет заказы Order Studio и — главное — `insert into profiles` с
`role='admin', approved=true` проходит: он заводит себе новый профиль и возвращает полный доступ.

Клиент не страхует: `App.jsx:59` проверяет только `user.approved === false`, а вычисленный
`profileStatus === 'disabled'` не читается нигде.

**Чинить:** `and active is true and approved is true` в `is_admin()`; ветка `disabled` в `App.jsx`;
`auth.admin.signOut(user_id)` при отключении — иначе живой токен переживёт правку RLS. **M**

### A2. Заказ-подряд с материалом подрядчика получает НОЛЬ этапов и не закрывается никогда

`utils/routes.ts:40,140,162-165` → `ordersSlice.ts:200` → `stageUi.ts:47` → `warehouseSlice.ts:121`

1. `BASE_CHAIN.outsource = ['supply']` — единственный этап;
2. ОТК не добавляется: `hasProduction` считает этапы, отличные от `supply`;
3. `buildItemRoute` при `material_source === 'contractor'` вырезает `supply` → **маршрут пуст**;
4. `createOrder` кладёт позицию с `stages: []` без проверок;
5. `isOrderReadyToShip` возвращает `false` при `stages.length === 0`;
6. склад отгружает только через `shipOrder`.

Кладовщик жмёт «Отгружено» и получает отказ без объяснимой причины. Заказ висит активным
вечно и портит все счётчики. Тот же исход у `no_product` с единственным методом нанесения `other`.

`buildItemRoute` не покрыт ни одним тестом, хотя объявлен единым источником маршрута.

**Чинить:** гейт в форме «маршрут пуст — так нельзя» + правило «нет этапов → судим по подряду/складу». **S/M**

### A3. Возврат брака не переоткрывает параллельную ветку нанесения

`utils/routes.ts:114-120` даёт всем веткам нанесения **один и тот же** `sortOrder`
(в цикле `sort` не инкрементируется). `utils/stageDefect.ts:41` и `stagesSlice.ts:156`
отсекают `mid.sort_order >= hi`.

Маршрут `закрой(20) → [вышивка(30), шелкография(30)] → швейка(40)`. Вышивка возвращает 20 бракованных
кроёв в закрой. Шелкография (30) отсекается как `>= hi` и остаётся `done` с полным количеством.
Закрой перекраивает, вышивка обрабатывает, швейка ждёт обе ветки — ждать нечего.

**20 изделий уходят в пошив без печати.** Обнаружится на ОТК или у клиента.

**Чинить:** считать переоткрываемые по графу `depends_on` (транзитивные потомки), а не по интервалу
`sort_order`. Заодно исчезнет зависимость от совпадения номеров. **M**

### A4. Материальный гейт не различает позиции заказа

`utils/routes.ts:209-217` фильтрует материалы только по `kind`; поле `item_id` игнорируется,
а вызывающие передают весь `order.materials`.

Заказ из 4 позиций, ткань на 4-ю задерживается на неделю → закрой по позициям 1–3 показывает
«Ждём материалы», хотя их ткань принята складом. Три позиции стоят из-за четвёртой.

**Чинить:** `m.item_id === null || m.item_id === item.id`. **S**

### A5. Замена файла ТЗ гарантированно падает на уникальном индексе

Индекс в проде: `CREATE UNIQUE INDEX erp_tz_documents_current_idx ON erp_tz_documents (group_id) WHERE is_current`.

`tzSlice.ts:110` вставляет новую версию с `is_current: true`, **пока старая ещё `is_current = true`**,
и только потом снимает флаг → гарантированный `23505`.

Комментарий в коде, правило в `pinhead-react/CLAUDE.md` («новая версия + снятие `is_current`
со старой, именно в таком порядке») и юнит-тест `useErpStore.test.ts:2065` — все трое закрепляют
неверный порядок. Баг латентный только потому, что `erp_tz_documents` в проде пуст.

**Чинить:** сначала `update is_current=false`, затем insert; либо RPC одной транзакцией.
Поправить тест, комментарий и оба CLAUDE.md. **S**

### A6. «Записать результат» с преднабранным остатком молча закрывает этап

`StageActionsPanel.jsx:83` — `useState(String(remaining || item.qty))`: в поле уже стоит весь остаток.
Один тап → `newDone >= total` → `status = 'done'`, следующий цех открыт на полный тираж, без
подтверждения. Соседняя кнопка «Завершить этап» тот же результат подтверждает через `confirmStageDone` —
ради чего эта утилита и написана.

**Чинить:** пустое поле по умолчанию; при `qty_done + N >= total` — тот же `confirmStageDone`. **S**

### A7. Смена пользователя не сбрасывает ERP-стор

`useAuthStore.logout` чистит localStorage, но `useErpStore` не трогает. Флаги `loaded`/`myDeptLoaded`
остались `true`, поэтому `ErpLayout` не делает ни одного запроса. На общем цеховом планшете
работник B видит заказы работника A и его цех. Само не восстанавливается.

Отдельно: `APP_KEYS` в `lib/storage.ts` — руками поддерживаемый список из 10 ключей, и
`erp_order_draft` (черновик формы создания заказа) в нём **нет**. Следующий пользователь открывает
«Новый заказ» и видит заказчика и тираж предыдущего.

**Чинить:** `resetErpStore()` в `logout()`; страж-тест «`APP_KEYS` ⊇ всех объявленных ключей». **M**

### A8. `moveStageToDepartment` откатывает UI поверх закоммиченной записи

`stagesSlice.ts:412-459`: исходный этап уже `done` в БД, целевой не открылся, а `set({orders: prev})`
показывает состояние «до переноса». Через секунду realtime применяет `done` — задание исчезает из
обоих цехов. Позиция остаётся без единого открытого этапа, повторить перенос нечем.

**Чинить:** не откатывать закоммиченное — компенсирующий `update` либо честный текст
«Этап закрыт, но не открыт в «X»». **M**

## B. Рубежи: правила есть, но их можно обойти

### B1. Матрица прав не применяется на сервере — только в браузере

Ни одна политика в схеме `public` не ссылается на `erp_role_permissions` и ни одна не сверяет цех
через `erp_employees` (проверено полной выгрузкой `pg_policies`). Все 10 прав и `canActIn` живут
исключительно в React, а RLS проверяет лишь `erp_is_member()` — «активный одобренный профиль».

Любой сотрудник одним `PATCH /rest/v1/erp_item_stages` закрывает этап в чужом цехе, меняет
исполнителя и приоритет, редактирует срок и тираж любого заказа. Аудит зафиксирует, но не остановит.

**Чинить:** `erp_has_permission(p)` и `erp_can_act_in(dept)` в `USING`/`WITH CHECK`, начиная с
`erp_item_stages` и `erp_orders`. **L**

### B2. Четыре политики `USING (true)` — доступ до одобрения администратором

`erp_tz_documents`, `erp_tz_assignments`, `erp_dictionaries`, `erp_role_permissions` читаются любым
авторизованным, включая неодобренного (регистрация открыта, триггер заводит профиль с `approved=false`).
`erp_tz_documents` содержит `file_path` — а бакет публичный (B3). **S**

### B3. Публичные бакеты без ограничений

Оба бакета `public=true`, `file_size_limit=null`, `allowed_mime_types=null`. Политик в схеме `storage`
всего три: два INSERT с единственной проверкой `bucket_id` и один DELETE. Следствия:

- ТЗ-PDF и вложения заказов раздаются по прямой ссылке без аутентификации; отозвать ссылку нельзя;
  путь вложений `${orderId}/${Date.now()}.${ext}` перебираем в пределах заказа;
- любой авторизованный льёт файлы любого типа и размера;
- **UPDATE-политики нет ни одной**, DELETE для `sku-photos` нет вовсе → `upsert: true` в коде
  не работает и не мог работать, `deleteSkuPhotoByUrl` всегда возвращает `false`.

**Чинить:** `erp-attachments` → приватный + `createSignedUrl`; `WITH CHECK ... AND erp_is_member()`;
лимиты MIME/размера на самих бакетах; добавить UPDATE/DELETE-политики. **M**

### B4. Комментарии Order Studio читает любой авторизованный

`orders_select` изолирует менеджеров (`created_by = auth.uid()`), но `order_comments_select/insert` —
`auth.role() = 'authenticated'` без связи с заказом. Переписка по чужим заказам читается и пишется
любым зарегистрировавшимся. **S**

### B5. Аудит производства пишется с клиента и «по возможности»

`store/shared.ts:26-40` — `logStageEvent` fire-and-forget, одна повторная попытка, дальше тост.
Этап уже переведён. Закрытая вкладка или потеря сети = событие потеряно, движение осталось.
`actor` хранится **именем строкой**, не id профиля: переименовали сотрудника — история порвалась,
тёзки неразличимы.

Смежное: `erp_materials`, `erp_order_items`, `erp_procurement_tasks`, `erp_subcontracting`,
смена `assignee` не логируются вообще — а именно эти правки срывают заказ.

**Чинить:** события триггером БД (механика уже отработана для плановых дат), `actor` как uuid,
общий триггер аудита на перечисленные таблицы. **M**

### B6. Прочее по безопасности

- `erp_create_order` берёт `created_by`/`uploaded_by` из payload без сверки с `auth.uid()` — подпись
  под документом может врать. **S**
- Нет security-заголовков на Vercel (CSP, `frame-ancestors`, `Referrer-Policy`). **S**
- Проверка утёкших паролей в Supabase Auth выключена. **S**
- Dev-байпас авторизации завязан только на `import.meta.env.DEV` — `npm run dev --host` даёт вход
  без пароля с правами админа. **S**
- `react-router-dom` 7.13.1: два advisory про открытый редирект. Эксплуатации в коде не нашлось
  (все `navigate()` по статическим путям), но обновиться стоит. **S**

## C. Воспроизводимость и эксплуатация

### C1. Схема прода не воспроизводится из репозитория

58 миграций в проде против 42 файлов. **18 миграций существуют только в БД**, среди них:

| Что | Последствие при развёртывании с нуля |
|---|---|
| `handle_new_user()` + триггер на `auth.users` | регистрация мертва: профиль не создаётся ни у кого |
| `erp_clamp_stage_qty()` + триггер | нет защиты `0 ≤ qty_done ≤ item.qty` (CHECK тоже нет) |
| `create_sku_photos_bucket_and_policies` | загрузка фото SKU не работает |
| 5 миграций security-hardening | RLS-ужесточение мая и июля отсутствует |
| 9 миграций `copy_*_catalog` | нет цен, SKU, тканей, фурнитуры |

Плюс `create table order_templates` отсутствует, хотя политики для неё в миграции есть, — реплей
падает на `42P01`. `supabase/config.toml` нет вовсе: CLI не инициализирован, `db reset`/`db push`
невозможны в принципе.

**Чинить:** выгрузить недостающие миграции, `supabase init` + `link`, прогнать реальный реплей.
Затем шаг `supabase db diff --linked` в CI — он ловит ровно ту болезнь, которая уже случилась. **M**

### C2. Storage не бэкапится ничем

Бэкапы Supabase и PITR покрывают Postgres, но **не объекты Storage**. Версионирования у бакетов нет,
код удаляет через `remove()` — hard delete. Копий нигде. Одна ошибка при замене файла ТЗ ломает
техзадание у всех цехов группы, восстановить нечем.

Сейчас в бакетах 5 объектов на 134 КБ — ночная выгрузка настраивается за час. **S**

### C3. Глубина бэкапов БД не подтверждена

План Pro = ежедневные бэкапы, 7 дней. PITR — платный аддон, признаков включения нет.
Инцидент в 17:00 → откат на ночной бэкап → **теряется весь рабочий день цехов**: перемещения
этапов, `qty_done`, брак, приёмка. Процедуры восстановления в документации нет ни строки. **S**

### C4. `main` не защищена; три последних релиза ушли в прод с красным CI

Ни одна ветка не защищена, обязательных проверок нет. Гейт в `ci.yml` написан правильно
(lint → 1342 unit → build → 105 e2e), но ничего не гейтит — он сообщает постфактум.

Текущий `main` (`297a294`) **красный**. Разобрано: упал единственный тест
`erp-mobile.spec.ts:38 «затемнение закрывает меню»` по таймауту. Причина — сам тест:
он кликает в центр затемнения (x≈187), а открытый сайдбар шириной 236px этот центр перекрывает.
Тест проходил только потому, что успевал попасть в 180 мс анимации выезда. На загруженном раннере
панель успевала встать на место. `retries` в конфиге не задан, поэтому один проигранный race валит job.
Дерево фронтенда между зелёным прогоном PR и красным на main идентично (`git diff` пуст).

Продукт исправен: для пользователя свободна полоса x = 236…375. Чинить нужно тест —
клик в непокрытую зону. **S**

### C5. Preview-окружения не существует

`VITE_SUPABASE_*` заданы только для Production. В превью-бандле они заинлайнены как `undefined`,
а `lib/supabase.ts` бросает на импорте модуля → превью открывается пустой страницей.
Единственный способ увидеть сборку в браузере — влить в main и выкатить в прод. Так и происходит:
4 production-деплоя за сутки.

**Развилка:** дёшево — задать те же переменные для Preview (но тогда превью пишет в боевую БД,
и это требует явного баннера); правильно — отдельный Supabase-проект, что упирается в C1. **S/M**

### C6. Самообновление визуальных эталонов узаконивает регресс

Три свойства складываются в дыру: `continue-on-error: true` на job `visual` (расхождение никогда
не красит сборку) + «пустая папка эталонов ⇒ `--update-snapshots`» (то есть **удаление PNG —
это команда «принять текущий рендер за норму»**) + коммит бота с `[skip ci]`, который Vercel всё
равно деплоит в прод. Механизм применялся дважды, ревью самих PNG нет — они идут прямо в main
мимо PR. Любой визуальный регресс фиксируется как новая норма одним удалением файлов.

**Чинить:** снять `continue-on-error`; убрать «пустая папка ⇒ обновить», оставив явный
`workflow_dispatch`; коммитить эталоны в PR, а не в main. **S**

### C7. Наблюдаемости нет

Sentry нет; `ErrorBoundary` делает `console.error` в браузер пользователя. Vercel Web Analytics
отключён. Runtime Errors пусты и будут пусты всегда — приложение статическое, серверного рантайма
нет, ошибка в React-компоненте туда не попадает физически. Алертов ноль.

О белом экране в цеху узнают по телефону, через часы, без возможности воспроизвести. **S**

Это `kontora24-prod` — отдельный боевой продукт в той же организации. Скрипт запускается с

молча перезаписал каталоги другого продукта. **S**

### C9. Прочее по эксплуатации

## D. Производительность — с цифрами из реальной сборки

### D1. chart.js (63 кБ gzip) на критическом пути ERP-оболочки, где нет ни одного графика

`vite.config.js:15` перечисляет `'vendor-react': ['react','react-dom','react-router-dom']`,
но **не** `react/jsx-runtime`. Rollup отдал его следующей группе — `vendor-charts`. Теперь любой
чанк с JSX статически тянет chart.js, и Vite ставит его в `modulepreload` (проверено в `dist/index.html`).
Ради 1.2 кБ приезжает 180.8 кБ.

Функциональная форма `manualChunks` (собрано и замерено): критический путь
**852.2 → 672.5 кБ raw, 242.7 → 179.5 кБ gzip**. Дописывание `'react/jsx-runtime'` в массив
не помогает — хеши чанков не меняются. **S**

### D2. `loadAll()` тянет все активные заказы целиком, 9 вложенных отношений, без лимита

Замерено на живой БД: `erp_item_stages` = 611 Б/строку, средний заказ 4.8 кБ. Сегодня 76 активных
заказов → 366 кБ. На 1000 × 5 × 6 — **≈ 20.8 МБ JSON одним ответом**, уже на 300 заказах ≈ 6 МБ.
Убивает не сеть (gzip справится), а `JSON.parse` и объектный граф: 30 000 объектов-этапов
≈ 60–100 МБ heap. На планшете с 2 ГБ это выгрузка вкладки.

**Чинить:** развести «список» (агрегаты, серверный расчёт) и «карточка» (полный select, уже есть
в `loadOne`). Промежуточный шаг — убрать `*` из вложенных select: этапы дают 86% полезной нагрузки,
а спискам нужно 8 полей из этапа. **M → L**

### D3. Канбан перерисовывает всю доску ~60 раз в секунду при перетаскивании

`onCardDragOver` создаёт новый объект на каждый `dragover` — бэйлаут React не срабатывает.
`KanbanCard` не обёрнут в `memo` (во всём `src/erp` мемоизированы ровно два компонента).
Сегодня это 86 карточек × 60 = 5 160 выполнений тела компонента в секунду; на 1000 заказах — 5 010 карточек.

Смежное: `memo` на `OrderRow`/`OrderCardMobile` не работает — колбэки `onDelete`/`onShip`
пересоздаются каждый рендер без `useCallback`. **S/M**

### D4. Каждое realtime-событие пересчитывает счётчики по всем заказам 21 раз

Один и тот же обход `orders → items → stages` выполняется 8 раз в `ErpLayout`, 12 в `DepartmentQueue`
и дважды в `withNewWorkToast`. На 1000 заказах — **≈ 140 мс на событие** на CPU сервера,
≈ 0.85 с на планшете. Когда в цеху работают 5–10 человек, UI залипает на каждое чужое нажатие. **M**

### D5. Прочее

- 144 кБ блокирующего CSS, из них ~128 кБ — стили Order Studio, не нужные в ERP-оболочке. **S/M**
- Google Fonts блокируют первый рендер: два лишних хендшейка, а при недоступности CDN — белый экран
  ~3 с. Локального `@font-face` нет. **S**
- `agentation` (42 кБ gzip, dev-виджет) уезжает в прод: гарды `import.meta.env.DEV` нет, пакет
  в `dependencies`. Комментарий «tree-shakes out of prod» не соответствует коду. **S**
- Ни один длинный список не виртуализирован и не пагинирован; `ProductionBoard` упрётся первым
  (строка = позиция). **M**
- 10 realtime-подписок без фильтров; `eventsPerSecond` не задан — при превышении дефолта
  события молча дропаются, ресинхронизации по таймеру нет. **M**
- N+1 при создании заказа (5 позиций = 7 round-trip, на цеховом Wi-Fi 1.5–3 с) и в `maybeCloseSupply`. **M**
- PWA-манифест есть, service worker'а нет: в standalone-окне обрыв Wi-Fi даёт системную страницу
  «нет сети» без адресной строки. Обработчиков `online`/`offline` в коде ноль. **S/L**

## E. UX: правила заявлены, применение точечное

- **Планшет цеха получает десктопную вёрстку.** `useMediaQuery('(max-width: 760px)')`, а Android-планшет
  в портрете — 768–800px. Тач-оптимизированная `QueueCard` не показывается **ни на одном** реальном
  цеховом устройстве; при 768px рабочая область уезжает вбок на ~250px, и колонка «Действия»
  оказывается за краем экрана. `playwright.config` гоняет 1280 и 375 — 768 не покрыт ничем. **M**
- **`ScrollHintBox` применён к 2 блокам из 19.** Правило записано, разведено по коду точечно.
  Без подсказки прокручиваются матрица прав (9 колонок), производственный план, заказы, склад,
  закупка, подряд, история. Правка `/load`, влитая сегодня, закрыла один симптом из восемнадцати. **S**
- **Самописные пустые состояния: 19 против 3 использований `ErpStates`.** Самое дорогое —
  очередь цеха показывает «Под фильтры ничего не подошло» **без кнопки «Сбросить»**, а фильтры
  живут в URL и переживают перезагрузку: рабочий видит «работ нет» и уходит. **S**
- **Триада ошибка → скелетон → пусто неполна на 6 экранах**; в `EmployeesScreen` кнопка «Повторить»
  показывается только когда загрузка **прошла**. **S**
- **96 глобальных `btn btn-*` против 2 файлов с примитивом `Button`.** В форме цеха «Заблокировать»
  (`btn-danger`, 11px, uppercase, без скругления) стоит рядом с «Отмена» (`btn-ghost`, 13px,
  обычный регистр, скруглённая) — две кнопки одной формы из разных продуктов. **L**
- **Контраст.** Все три типа тостов ниже AA (success 3.07:1, warning 3.57:1, error 4.17:1), причём
  через warning идут сообщения, которые обязаны быть прочитаны дословно («Введено больше остатка —
  засчитано 60 шт»). Плюс `.stepperDotActive` 2.15:1 — это номер текущей стадии маршрута. **S**
- **Клавиатурной альтернативы перетаскиванию на канбане нет**, хотя правило числит её выполненной:
  Enter/Space открывает карточку заказа, а не заменяет один из трёх жестов доски. **M**
- **Диалог необратимых действий** собран на 14 фолбэках `var(--token, X)` при объявленных токенах,
  `z-index: 9999` вместо `--z-modal`, поле причины 40px без coarse-медиазапроса. **S**
- **Ни одно цеховое действие не подтверждается успехом** — «Взял», «Записал», «Завершил», «Брак»
  проходят молча, а блок «Завершено недавно» по умолчанию свёрнут: задание просто исчезает.
  Отличить «сохранилось» от «откатилось после ошибки» нельзя. **S**
- **Пять форматов даты**, две из них без защиты от UTC-сдвига (`new Date('2026-08-14')`) — в поясах
  западнее UTC дата отгрузки покажется на день раньше. **S**
- **Ошибки цеховых действий** сведены к «Не удалось обновить этап»; `translateSupabaseError`
  в ERP не используется ни разу. Отказ прав, обрыв сети и конфликт выглядят одинаково,
  тост живёт 3 секунды, кнопки «Повторить» нет, обработки офлайна нет вовсе. **M**

## F. Тесты: 1342 зелёных, и перевёрнутая пирамида

Плотность: `erp/utils` 22 файла / 17 тестовых · `erp/store/slices` 13 / **0** (всё через один файл) ·
`erp/screens` 52 / **2** · `hooks` 7 / 1.

Самый глубокий слой тестов лежит на чистых функциях, где цена ошибки уже снижена типами и размером.
Сборочные слои — форма создания заказа на 783 строки, дровер заказа, побочные эффекты подряда —
не покрыты вовсе, хотя именно там живут переходы состояний и потери данных.

**Тесты, дающие ложную уверенность:**

- цена проверяется как `expect(screen.getByText('ИТОГО')).toBeInTheDocument()` поверх полностью
  замоканного `utils/pricing` — считаемое значение не ассертится нигде. 44 теста в двух файлах
  не упадут, если сломать проводку цены до КП клиента;
- `Dashboard.test.jsx` мокает `recharts`, которого в проекте нет (используется `react-chartjs-2`) —
  мок инертный; проверяются подписи, а не агрегаты;
- четыре e2e не могут упасть в принципе: `toBeGreaterThanOrEqual(0)` в тесте про фильтрацию,
  тело теста внутри `if (await card.isVisible())`, `locator('main')` вместо дашборда,
  тавтологический regex по URL.

**Системный перекос:** happy path покрыт почти везде, ветка ошибки — почти нигде. Это прямое
следствие глобального мока в `setupTests.js`, который всегда отдаёт `{data: [], error: null}` и
не умеет отдавать ошибку; `clearMocks`/`restoreMocks` в конфиге не включены.

**Ни один e2e не совершает производственного действия** — мок отвечает фикстурой на любой метод и
состояние не меняет. Сквозная цепочка «взял → частично 40/100 → завершил → следующий цех» существует
только в store-тестах поверх ручного мока. Спеки Order Studio мок не ставят вовсе и идут в
**реальный** Supabase из `.env`.

**Визуальные эталоны:** 5 сценариев × 2 вьюпорта, только светлая тема, только «загружено и наполнено».
`threshold: 0.15` без `maxDiffPixelRatio` — сдвиг лейаута ловится, изменение оттенка в пределах 15%
проходит. Ровно тот класс регресса, который чинила волна UX-3.

## G. Продукт: разрыв «обещано — сделано»

**Не начато:** мост ТЗ → производственный заказ (два независимых мира заказов, менеджер вводит
дважды); генерация ТЗ-PDF (есть только загрузка готового файла); Bitrix24 (одно текстовое поле
без уникальности); 1С (ноль строк); календарное планирование (`erp_calendar_slots` создана и мертва —
а `spreadsheet-analysis.md` называет это «то, что ERP должен автоматизировать в первую очередь»);
себестоимость и расход материалов; аналитика производства (дашборд — снимок «сейчас», без плана/факта,
времени цикла, брака по цехам и динамики).

**Объявлено в типах и не реализовано:** частичная отгрузка (`'partial'` не выставляется нигде),
приоритет заказа (`priority` не пишется и не сортирует), буфер дней (пишется, читается только
в истории), дробление партий.

**Данные, которых не хватает для разбора «почему сорвали срок»:**

- `erp_stage_events.qty_done` смешивает дельту и абсолют (`reportProgress` пишет прирост,
  «Завершить этап» — полный тираж) → любой отчёт по выработке завышен и не восстановим;
- реальную длительность этапа посчитать нельзя: `started_at`/`finished_at` перезаписываются при
  повторном входе, брак обнуляет `finished_at` без события, статуса `ready` в БД не существует;
- возврат брака не оставляет следа на откаченных этапах — они молча уходят из `done` в `waiting`;
- процент брака по цехам не строится: причина — свободный текст, структурный `cause_type` есть
  только там, где заводится задача закупки;
- загрузка цеха на дашборде считается в **штуках этапов**: позиция на 5 шт весит столько же,
  сколько на 5000.

**Готовность к SaaS — честно:** мультиарендности нет ни в каком виде (ни `tenant_id`, ни схем);
маршруты зашиты константами по кодам цехов (участок в админке завести можно, в маршрут он попадёт
только с релизом); набор ролей — enum в коде; справочники покрывают 4 вида, остальное — CHECK-констрейнты;
бизнес-логика живёт в клиенте, а при RLS «всё разрешено» правила не являются правилами.
Операционного слоя (биллинг, лимиты, self-serve, экспорт) нет.

## Что сделано хорошо

- **Чистые утилиты ERP** — образцовые. `routes`, `stageDone`, `stageDefect`, `stageMove`, `progress`,
  `queueEntries`, `tz` покрыты тестами на смысл, а в комментариях зафиксировано *почему*.
  Необратимое действие считает чистая функция, она же формулирует текст последствий — текст не может
  разойтись с фактом. Это редкость даже в зрелых ERP.
- **Дисциплина стора:** ни одного объектного селектора без `useShallow` во всём репозитории;
  `patchStageIn` сохраняет идентичность нетронутых заказов; `_pendingMutations` корректно защищает
  от гонки с realtime; realtime патчит точечно, полный `loadAll` остался задебаунсенным фолбэком.
- **TypeScript:** в 157 файлах `src/erp` ни одного `any`, `as unknown as`, `@ts-ignore`.
- **Границы модулей чистые**, циклов нет; `shared.ts`/`orderHelpers.ts`/`types.ts` разведены осознанно.
- **Каскады БД и частичные индексы** расставлены под инварианты продукта: один выбранный поставщик
  на материал, одна текущая версия ТЗ в группе. Осиротевших строк в проде нет.
- **Code splitting по маршрутам работает** как заявлено; `mobile-drag-drop` подключён образцово
  (динамический импорт только на тач); ленивый архив постранично с честным «Показать ещё».
- **E2E волны UX-2** — единственное место, где сбой сети смоделирован честно (`route.fulfill(500)`,
  проверка «это не читается как „работы нет“», восстановление через «Повторить»). Это шаблон,
  который стоит тиражировать.
